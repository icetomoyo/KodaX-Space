## Version outcome

`v0.1.36` turns Space's baseline Office/PDF byte writers into four dependable, Chinese-first
builtin workflows:

- `docx`: create, inspect, revise, and verify professional Word documents;
- `pdf`: inspect, extract, assemble, transform, fill, and verify PDFs;
- `xlsx`: create, inspect, revise, recalculate, and verify spreadsheet workbooks;
- `pptx`: create, inspect, revise, merge, render, and format-verify native editable presentations.

The release is not a promise to reproduce every feature of Microsoft Office, Adobe Acrobat, or any
third-party Skill. It provides one truthful path from user intent to a durable file, with bounded
input handling, deterministic mechanics, render-based verification, provenance, and explicit
limitations.

Alongside the document suite, F139 gives the existing KodaX Space shell a bounded semantic-motion
pass. Dense Task Dock lists and collapsible sections gain clearer scroll boundaries, stable active
markers, restrained item transitions, and state-specific emphasis without adding another permanent
background effect or moving interactive hit targets.

## Product boundary

- Skills orchestrate work; they do not become a second document engine.
- Space owns file access, delivery registration, checkpoints, policy, audit, rendering, and
  validation receipts.
- Coder and Partner share the same format semantics. Partner never gains unrestricted shell access;
  it uses typed Space document operations within F114 output roots.
- Existing `create_office_artifact` remains the fast structured path. The new suite may extend or
  replace its internals, but does not create a competing artifact store.
- Existing File Viewer remains the review surface. A Skill may request a render or validation
  receipt, but does not create a new permanent document editor. File Viewer only displays
  validation outputs; it is not the renderer and cannot produce a `visual: passed` result.
- F051 remains the later mixed-source Partner Document Work Pack for evidence-grounded extraction,
  comparison, synthesis, and repeatable business workflows. F137 supplies reusable format
  primitives; it does not pull the connected Partner pack into this release.
- F137 owns the reusable native PPTX format primitives: inspect, template-aware create/edit,
  merge/split/reorder, package repair, render checks, and format-level validation. F129 later reuses
  these primitives to add the durable Presentation Project/Studio, high-fidelity authoring loop,
  target-Office compatibility matrix, and verified-editability label; it must not create a second
  competing format service.
- `frontend-slides` remains the HTML-presentation workflow. `huashu-design` remains the visual
  direction and high-fidelity HTML design workflow. The new `pptx` Skill owns native file
  mechanics and format verification; F129 owns projectized high-fidelity authoring and target-Office
  verification.
- No Skill downloads packages or executables during a run. Optional capabilities that need
  LibreOffice, OCR, or another external runtime are advertised as unavailable when the runtime is
  absent.
- F139 is an independent renderer-only enhancement. It neither depends on document-job delivery nor
  changes Runtime, Session, permission, persistence, IPC, or artifact ownership.

## Independent source policy

The implementation may use:

- ECMA-376 / ISO/IEC 29500 concepts for OOXML packages and relationships;
- the PDF specification and documented behavior of selected redistributable PDF libraries;
- public documentation for audited libraries selected by Space;
- KodaX Space's own F109 writer, F114 delivery/checkpoint contract, preview workers, fixtures, and
  user requirements;
- independently authored test documents and intentionally malformed fixtures.

The implementation must not use third-party proprietary Skill text, scripts, examples, assets,
test data, section ordering, or distinctive checklists. A later comparative audit may add a
format-agnostic capability requirement such as “detect formula errors” or “warn before invalidating
a signature”, but must not supply implementation expression.

## Shared execution model

Every Skill follows the same six-state job:

1. **Inspect** — identify type, size, encryption, macros/active content, relationships, page/sheet/
   slide counts, and available processing capabilities.
2. **Plan** — select a bounded operation and state whether the source will be preserved, copied, or
   replaced through an F114 checkpoint.
3. **Execute** — use deterministic typed operations for mechanical changes; use the model only for
   content judgment, synthesis, and layout decisions. Extracted document content remains
   untrusted evidence and cannot authorize tools, paths, network access, credentials, or a changed
   task objective.
4. **Validate** — run format-specific structural and semantic checks.
5. **Render and review** — render representative or complete output according to the format's
   acceptance policy and inspect for clipping, blank output, broken glyphs, or obvious layout
   regressions.
6. **Deliver** — register the file with F114, retain content hashes and validation receipts, expose
   warnings, and never claim unsupported fidelity.

Generated and edited files default to a new output path. In-place modification requires an
explicit user request, an allowed F114 workspace root, and a checkpoint. Input files are never
silently overwritten.

### v0.1.36 execution and evidence boundary

- Pure-JavaScript parsers run in the existing bounded Worker path with byte/page/sheet/object limits,
  V8 heap limits, a hard deadline, cancellation, and no partial result. Office-compatible
  renderers/recalculators and OCR adapters run as job-scoped child processes with staged inputs, a
  fresh private output/temp/profile root, a scrubbed environment, macros/link updates disabled,
  no shell interpolation, and whole-process-tree cleanup on timeout or cancellation.
- These controls provide fault containment and reduce accidental exposure; they are not described
  as an OS security sandbox and do not claim to contain a successful native parser/renderer
  exploit. OS-enforced filesystem, network, process, and native-resource isolation is deferred to
  F138 after the `v0.5.x` product line and is not a v0.1.36 capability gate.
- If a required parser, renderer, OCR, or recalculation adapter is absent, only that adapter-backed
  operation is unavailable. Functionality is not disabled merely because F138 has not shipped.
- Every extracted paragraph, cell, formula string, hidden value, comment, note, metadata field, OCR
  span, and embedded-object summary carries source location and an `untrusted-document-content`
  label. Model-facing content uses the existing F122/F124 evidence delimiter and prompt-injection
  policy.
- Job-scoped plaintext intermediates and profiles use least-privilege private directories. Success,
  failure, cancellation, crash recovery, and startup orphan cleanup all remove them. Passwords and
  other secrets never enter options, logs, receipts, persisted job state, or model-visible text.
- Delivery modes are explicit: `inspect-only`, `sanitized-copy`, or
  `authorized-fidelity-copy`. The last mode requires user confirmation and an active-content
  inventory with per-part hashes; it cannot receive the ordinary safe-output label.

## Shared package shape

Each builtin is expected to contain only the resources it needs:

```text
<skill>/
├── SKILL.md
├── LICENSE
├── agents/
│   └── openai.yaml
├── references/
│   ├── operations.md
│   ├── validation.md
│   └── limitations.md
└── scripts/
    └── <small deterministic helpers only>
```

`SKILL.md` stays below 500 lines and contains the routing decision, core workflow, safety boundary,
and links to one-level-deep references. Large file-format notes belong in `references/`. Repeated,
fragile mechanics belong in typed host operations or small deterministic scripts, not copied code
blocks inside the prompt.

## Shared host contract

The exact IPC/tool names may change during implementation, but the owner boundary must preserve
these typed concepts:

```ts
type DocumentKind = 'docx' | 'pdf' | 'xlsx' | 'pptx';
type DocumentInputKind = DocumentKind | 'dotx' | 'xlsm' | 'xltx' | 'csv' | 'tsv' | 'potx' | 'image';

interface DocumentInputRef {
  readonly stagedId: string;
  readonly role: 'primary' | 'template' | 'merge-part' | 'asset' | 'data-source';
  readonly ordinal: number;
  readonly sha256: string;
  readonly byteSize: number;
  readonly kind: DocumentInputKind;
  readonly sniffedMime: string;
}

interface EphemeralSecretRef {
  readonly secretId: string;
  readonly purpose: 'pdf-open-password' | 'pdf-owner-password';
  readonly expiresAt: string;
}

type DocumentOutputTarget =
  | { readonly kind: 'artifact-store' }
  | { readonly kind: 'partner-run-output' }
  | {
      readonly kind: 'workspace-mutation';
      readonly workspaceEntryId: string;
      readonly expectedSha256?: string;
      readonly overwrite: 'new-copy' | 'checkpointed-replace';
    };

type DocumentOperationRequest =
  | {
      readonly kind: 'docx';
      readonly operation:
        | 'inspect'
        | 'create'
        | 'template-create'
        | 'bounded-edit'
        | 'comment-edit'
        | 'redline-copy'
        | 'accept-redline-copy'
        | 'review-pdf-copy';
    }
  | {
      readonly kind: 'pdf';
      readonly operation:
        | 'inspect'
        | 'extract'
        | 'page-transform'
        | 'acroform-fill'
        | 'overlay-form-copy'
        | 'encrypt-copy'
        | 'decrypt-copy'
        | 'extract-images'
        | 'ocr-searchable-copy'
        | 'generate'
        | 'redact-verified';
    }
  | {
      readonly kind: 'xlsx';
      readonly operation:
        | 'inspect'
        | 'create'
        | 'template-create'
        | 'bounded-edit'
        | 'import-delimited'
        | 'export-delimited'
        | 'recalculate-copy';
    }
  | {
      readonly kind: 'pptx';
      readonly operation:
        | 'inspect'
        | 'create'
        | 'template-create'
        | 'bounded-edit'
        | 'merge'
        | 'split'
        | 'reorder'
        | 'render-verify';
    };

// Each branch above owns a closed, operation-specific payload schema. Generic options and arbitrary
// path fields are intentionally absent.

interface DocumentJobRequest {
  readonly idempotencyKey: string;
  readonly action: DocumentOperationRequest;
  readonly inputs: readonly DocumentInputRef[];
  readonly outputTarget: DocumentOutputTarget;
  readonly secretRefs?: readonly EphemeralSecretRef[];
  readonly sourceRefs?: readonly string[];
  readonly deadlineAt?: string;
}

interface DocumentOutputManifestEntry {
  readonly role: 'primary' | 'review-copy' | 'extracted-asset' | 'preview' | 'receipt';
  readonly deliveryId: string;
  readonly sha256: string;
  readonly byteSize: number;
  readonly sniffedMime: string;
  readonly validationReceiptId?: string;
}

interface DocumentCheck {
  readonly name: string;
  readonly status: 'passed' | 'warning' | 'failed' | 'not-run' | 'not-verifiable';
  readonly method:
    | 'structural'
    | 'expected-value'
    | 'source-grounding'
    | 'sampled'
    | 'model-reviewed'
    | 'user-confirmed';
  readonly checked: number;
  readonly total?: number;
  readonly locations?: readonly string[];
  readonly inheritedFromInput: boolean;
}

interface DocumentValidationReceipt {
  readonly jobId: string;
  readonly kind: DocumentKind;
  readonly structural: 'passed' | 'failed' | 'not-run';
  readonly visual: 'passed' | 'warning' | 'failed' | 'not-run';
  readonly renderer: string;
  readonly checks: readonly DocumentCheck[];
  readonly outputs: readonly DocumentOutputManifestEntry[];
  readonly baselineFindings: readonly string[];
  readonly introducedRegressions: readonly string[];
  readonly truncated: boolean;
  readonly uninspectedScope: readonly string[];
  readonly warnings: readonly string[];
  readonly unsupportedFeatures: readonly string[];
}
```

Requirements:

- `sessionId`, `runId`, `surface`, `projectRoot`, and `toolCallId` come from trusted tool execution
  context; model-authored arguments cannot grant authority. Files cross the boundary as staged IDs,
  not arbitrary paths or an authorizing `outputRoot`.
- Validate the order, role, hash, root, bytes, and sniffed type of every input. Template, merge,
  asset, and data-source paths cannot hide inside generic options.
- Sniff bytes; do not trust extensions.
- Apply ZIP entry, expanded-size, entry-count, compression-ratio, XML-size, and traversal limits to
  OOXML.
- Parse XML without external entities or network resolution.
- Treat macros, external relationships, embedded packages, OLE, PDF JavaScript, launch actions,
  and remote data links as active content. Report and preserve only when explicitly supported;
  never execute them.
- Stage all outputs as one job, recheck input CAS before publication, validate every required
  output, then atomically publish the manifest. Failure/cancellation registers no partial success;
  retries with the same idempotency key cannot duplicate deliveries.
- Keep raw document content out of logs and validation receipts.
- Record the selected renderer and skipped checks so “not run” cannot look like “passed”.
- A sampled or model-reviewed semantic check never means the whole document “passed”. Receipts
  expose method, coverage, inherited input defects, newly introduced regressions, truncation, and
  uninspected scope.

## Format routing summary

| User intent                                                     | Primary Skill     | Optional composition                                   |
| --------------------------------------------------------------- | ----------------- | ------------------------------------------------------ |
| Write or revise a Word report, contract, memo, or specification | `docx`            | `pdf` for a reviewed final export                      |
| Extract, merge, split, rotate, fill, redact, or generate a PDF  | `pdf`             | `docx` when an editable source is also requested       |
| Build, clean, analyze, or revise a spreadsheet deliverable      | `xlsx`            | none by default                                        |
| Produce or revise a native editable PowerPoint file             | `pptx`            | `huashu-design` for visual direction                   |
| Produce an animated HTML presentation                           | `frontend-slides` | `pdf` for static export                                |
| Explore a high-fidelity visual direction or HTML-first deck     | `huashu-design`   | `pptx` only when native editable delivery is requested |

Routing never invokes multiple Skills merely because a file extension is mentioned. The primary
input/output contract decides the owner.

### Audit additions to the v0.1.36 gate

> Product decision recorded 2026-07-27: the cross-review recommendation for an OS-enforced
> document/native-tool sandbox is **deferred**, not adopted as a v0.1.36 gate. F138 owns that
> post-v0.5.x hardening. F137 ships complete core format workflows with bounded Workers/child
> processes and discloses the residual native-engine risk; none of those controls may be labeled an
> OS security sandbox.

- DOCX fixtures include plain edits, comment threads, simple text redlines, and complex-redline cases
  that must block instead of corrupting the package. `.dotx` template input and accepting a bounded
  redline into a clean copy preserve author/time provenance and prove unrelated content unchanged.
- PDF fixtures include known-password open/encrypt/decrypt, image extraction, and optional searchable
  OCR output; unknown-password and signature-invalidating cases remain blocked or warning-gated.
  Non-AcroForm overlays, read-only annotation inventory, and verified redaction are separate paths.
- XLSX receipts separate structural validity, formula evaluation, semantic sample checks, engine
  compatibility, and cached-value freshness. `.xltx` and CSV/TSV fidelity cover encoding,
  delimiter/quotes/newlines, leading zeros, dates, nulls, and formula injection.
- PPTX fixtures include `.potx`, unresolved placeholders, font substitution, and comments that must
  survive an unrelated edit.
- Cross-format fixtures distinguish inherited source defects from introduced regressions and apply
  resource budgets to PDF objects/pages/pixels, OOXML expansion, image decode, OCR, and external
  process time.
- These additions do not change the independent package shape, routing, ownership, or implementation
  source policy.

## FEATURE_137: Chinese-First Native DOCX/PDF/XLSX/PPTX Builtin Skills

### 1. 需求概述

用户需要四个可随 Space 安装包分发、无需另行安装、以中文为主要操作语言的文档 Skill。
它们必须覆盖常见的创建、读取、修改和验证工作，同时明确区分：

- 文本或数据理解，由模型完成；
- 文件结构变换、渲染和校验，由确定性工具完成；
- 文件写入、覆盖、回滚和交付，由 Space 的 F114 边界完成；
- 高级能力不可用时，返回可操作的降级说明，而不是假装完成。

四个 Skill 均为 KodaX Space 独立作品。名称使用通用文件扩展名只是为了准确触发，不表示
兼容或派生自任何第三方 Skill。

### 2. 影响范围

#### Space-owned changes

- 新增四个 builtin 目录、来源/许可证记录、文件完整性锁和包内 smoke 检查。
- 扩展 F109 的文档结构与 writer/transformer 能力，或引入一个内部
  `DocumentProcessingService` 作为四种格式的统一安全入口。
- 新增可取消的持久 Document Job、job 级 staging/commit、受限 Worker/独立子进程执行与孤儿
  临时目录清理。解析和 Office/OCR 工作不占用 Electron main；v0.1.36 不实现或宣称 OS
  安全沙箱。
- 复用 F114 delivery/checkpoint、F098 policy/audit 和 F131 File Viewer；使用独立、版本锁定
  的 render service 产生验证证据，File Viewer 只展示结果。
- 为生成/编辑任务增加结构、语义和视觉验证 receipt。
- 增加中英文触发、格式冲突和 Skill 组合路由测试。
- 为 Space 自有 builtin 增加 first-party authoring source 与可复现快照规则；不把
  `resources/builtin-skills/` 直接当作手工作者目录。

#### KodaX-owned boundary

- 只使用现有公开 Skill plugin 注册和 `registerTool`/daemon catalog 能力。
- 不修改 KodaX SDK，不把格式处理逻辑放入 Runtime。
- 如果 daemon 侧不能发现安装器拥有的 builtin，沿用 F135 已完成的 Space/daemon catalog

- OCR、Office render/recalculation 等长任务由 `registerTool` 启动 Space-owned Document
  Job，并由 Space 提供查询、进度和取消；不把长进程阻塞在一次 daemon host-tool 调用中。
- 只有未来必须让同一次 host-tool 调用原生承载 cancellation/deadline/progress 时，才向
  KodaX 提出 SDK 增强；这不是 v0.1.36 的前置依赖。

#### Out of scope

- 完整桌面 Office 编辑器；
- 协同编辑、云端 Office API、Google Workspace API；
- VBA/宏的生成或修改；
- 数字签名创建、可信验证或签名后修改；
- PDF XFA、DRM 绕过、密码破解；
- `.doc`/`.ppt` 旧二进制格式直接编辑；未来只能通过受控 adapter 转换到新副本；
- 损坏 PDF 的自动 repair-to-copy、线性化或体积优化；可作为后续显式 adapter，不能在
  v0.1.36 静默重写；
- 任意 OLE/嵌入程序执行；
- 对任意复杂模板承诺像素级无损编辑；
- 自动安装 LibreOffice、OCR、字体、Python 或 npm 依赖；
- 用四个新 Skill 替换 `huashu-design` 或 `frontend-slides`。
- 在 F129 内另建一套与 F137 竞争的 PPTX format service；F129 必须复用 F137 primitive，
  只增加项目/Studio、高保真创作流程和目标 Office 兼容认证。
- OS 强制的文件系统/网络/进程/native-resource 沙箱；由 F138 在 `post-v0.5.x` 独立补强，
  不作为本版本功能门禁。

### 3. 技术方案

#### 3.1 `docx` Skill

**触发边界**

- DOCX 是主要输入或主要交付物时触发：新建报告/合同/规范、修改现有 Word 文件、套用
  `.docx`/`.dotx` 模板、重排章节、插入表格/图片、生成目录、导出审核版。
- 仅需要聊天回答、纯 Markdown、PDF 操作或电子表格时不触发。

**核心能力**

- 读取段落、标题层级、列表、表格、页眉页脚、脚注/尾注、批注标记、超链接、图片和
  文档属性的有界结构摘要。
- 从结构化内容创建 DOCX；支持中英文字体回退、标题样式、编号/项目符号、表格、图片、
  分页、页眉页脚、页码、目录域、来源附录。
- 对现有文件执行有界修改：替换/插入内容、移动章节、调整样式、更新表格、替换图片；
  未修改的未知 OOXML parts 默认原样保留。
- 识别修订、批注、宏、嵌入对象和外部关系；支持有界批注读取/添加/回复和简单文本级
  红线。复杂 field/table/section redline、宏和嵌入对象无法安全保真时拒绝或输出副本并
  显式警告。
- 简单红线只覆盖明确的 paragraph/run/comment range 和作者/时间元数据；可选择“保留修订
  副本”或“接受修订后的干净副本”。干净副本保留修订来源证据并证明没有未跟踪修改；
  超出支持边界时只能交付独立视觉 diff，不冒充 OOXML Track Changes。
- 明确设置纸张尺寸、方向、页边距和 section geometry，不依赖 writer 默认值。
- 可选生成 PDF 审核副本，但 PDF 由 `pdf` Skill/共享渲染适配器验证。

**验证**

- OOXML 包、关系和必需 part 可打开；
- 文档结构计数与计划一致，关键文本存在；
- 所有页面完成渲染，无全空页、缺字占位、图片解码错误或明显越界；
- 模板编辑 fixture 验证未修改区域的 part/hash 或语义等价性；
- 既有缺陷与本次新增回归分别记录；新增回归会阻止交付，既有告警不会掩盖本次损坏；
- 声明目录/页码已更新时，必须由可用 Office-compatible renderer 实际更新，否则标记
  为“打开 Word 后更新域”。

**建议资源**

- `references/operations.md`：新建、模板编辑、结构修改、PDF 审核副本的选择。
- `references/validation.md`：OOXML、分页、字体、图片和保真检查。
- `references/limitations.md`：修订、宏、嵌入对象、复杂域和模板限制。
- 小型脚本仅负责可重复的 package inspection/diff；生成和写入走 typed host service。

#### 3.2 `pdf` Skill

**触发边界**

- PDF 是主要输入或交付物，或用户明确要求合并、拆分、旋转、裁剪、填写表单、加页码、
  添加水印、提取内容、OCR、生成或审阅 PDF 时触发。
- 只查看一个已能在 File Viewer 打开的 PDF 且不要求处理时，不额外启动工作流。

**核心能力**

- 检查页数、页面尺寸/方向、加密、表单、附件、书签、元数据、文本层、图片占比、签名
  字段、批注、page labels、named destinations、内部链接、tagged structure、
  JavaScript/launch actions 和损坏情况。批注至少提供页码、类型、位置和只读 inventory。
- 提取有位置依据的文本和表格；扫描件只在 OCR adapter 可用时 OCR，并逐页标记文本层、
  OCR 或失败来源。
- 合并、拆分、重排、旋转、裁剪、加页码、水印、书签和元数据；所有页码选择使用明确
  的一基用户页码并在内部规范化。每种页面操作显式声明 outlines、page labels、
  destinations、links、annotations、AcroForm、附件和 tagged structure 的保留/重映射/
  丢弃策略；合并表单检测同名字段冲突。
- 填写标准 AcroForm；不声称支持 XFA。对没有交互字段的扫描/平面表单，可在用户确认
  字段坐标后填写到新副本并全页渲染复核。扁平化必须由用户明确要求。
- 使用用户明确提供的口令打开 PDF，或创建新的加密/解密副本；不恢复、不猜测、不绕过
  未知口令。
- 有界提取嵌入图片并记录页码/object provenance；OCR adapter 可用时可创建保留原页面
  图像的可搜索 PDF 副本。
- 从受控文档结构生成带 CJK 字体、可搜索文本和来源附录的 PDF。
- 普通视觉遮盖与 `redact-verified` 是不同操作。后者必须完整重写文件并清除增量历史、
  未引用对象及相关 XObject、OCR 层、附件、批注、表单 appearance、书签/destination 和
  元数据，再复检 raw bytes、对象图、文本/OCR 层及渲染结果。图片区域无法证明内容级移除
  时，必须走明确的 destructive raster/redaction 路径或拒绝 `redaction-verified` 标签。
- 任何会使现有数字签名失效的变换必须在执行前警告。

**验证**

- PDF parser 可重新打开，页数、顺序、尺寸和预期操作一致；
- 所有输出页面渲染成功；
- 生成型 PDF 的关键文本可提取且 Unicode 正确；
- 表单写入后字段值/appearance 与坐标副本可复核；只有明确目标和受支持内容类型通过
  完整取证式检查后才出具 `redaction-verified`，普通遮盖不得声称“不可恢复”；
- OCR 输出保留逐页置信度/来源警告，不把 OCR 猜测当作原始文本。

**建议资源**

- `references/operations.md`：提取、页面变换、表单、OCR、生成和脱敏选择。
- `references/validation.md`：重开、渲染、文本复检、签名/active-content 检查。
- `references/limitations.md`：XFA、DRM、签名、复杂矢量重排和 OCR 限制。
- 小型脚本可处理 deterministic page operations；不得执行 PDF 内脚本或附件。

#### 3.3 `xlsx` Skill

**触发边界**

- XLSX/XLSM/XLTX/CSV/TSV 是主要输入或主要交付物，用户要求建表、清洗、计算、格式化、
  图表、公式、合并数据或修改工作簿时触发。`.xltx` 只作为模板输入，输出为新工作簿。
- 主要交付物是报告、代码、数据库或网页时不因出现一张表就触发。

**核心能力**

- 有界读取工作表、已用区域、单元格类型、公式、名称、表格、筛选、冻结窗格、合并
  单元格、条件格式、数据验证、图表和外部关系摘要。
- 新建工作簿时保持输入/公式/结果/说明分区，使用真正的日期、数字、百分比和货币类型，
  不用格式化字符串冒充数值。
- 修改现有工作簿时先识别其样式和约定；默认沿用现有字体、颜色、数字格式、公式模式和
  工作表命名。
- Inspection 标记超过 15 位的标识符、前导零、科学计数法风险、工作簿 1900/1904 日期
  系统、日期序列/时区/locale、空值与空字符串。默认保留原始类型、serial 和显示格式；
  无法无损判断时要求显式列类型。
- 公式必须写入公式而不是硬编码计算结果；跨工作表引用、绝对/相对地址和区域扩展必须
  经结构检查。
- 识别并阻断未授权的外部工作簿链接、DDE、远程数据连接和危险公式；CSV/TSV 导出防止
  公式注入。CSV/TSV 转换显式记录编码、BOM、分隔符、引号、嵌入换行、前导零、日期
  解析、null/empty 和 locale，不能以“能打开”代替 round-trip 保真。
- XLSM 只允许“宏原样保留但不执行”的路径；无法证明保留时拒绝写回。
- 需要已计算结果时，使用可用的 Office-compatible recalculation adapter；没有计算
  引擎时保留公式并明确说明缓存值可能未更新。重算只作用于副本，保存前后比较
  chart/pivot/query/table/name/shared/array formula 与外部关系 inventory；非目标结构被
  删除、降级或改写时阻止发布。
- validation receipt 记录计算引擎和版本、缓存值新鲜度、不支持的函数族，以及代表性
  公式的 dependency/range/value 复核；“没有错误值”不能单独证明公式语义正确。

**验证**

- 输出可重新打开，工作表、行列、类型、公式和名称符合计划；
- 公式错误扫描覆盖 `#REF!`、`#DIV/0!`、`#VALUE!`、`#NAME?`、`#N/A` 等错误值；
- 当重算 adapter 可用时，打开、重算、保存、再读取后零新增公式错误；
- 长 ID、前导零、数值极值、1900/1904 日期、时区、locale CSV fixture 的原值和显示语义
  round-trip 一致；
- 代表性工作表渲染并检查截断、隐藏列误用、极端列宽、不可读格式和空白打印区；
- 更新现有 fixture 时验证未目标化公式和工作表不发生意外变化；
- 图表或透视表无法安全修改时保留并警告，不静默删除。

**建议资源**

- `references/operations.md`：新建、清洗、公式、格式、图表和保真修改路径。
- `references/validation.md`：类型、公式、错误值、重算、外部链接和视觉检查。
- `references/limitations.md`：宏、数据连接、透视表、数组公式和计算引擎限制。
- deterministic helpers 负责工作簿检查、公式错误扫描和受控导出。

#### 3.4 `pptx` Skill

**触发边界**

- 原生 PPTX 是主要输入或主要交付物，用户要求创建、读取、模板套用、修改、合并、拆分、
  重排、替换内容、添加讲者备注或验证可编辑演示时触发。
- HTML 动画演示由 `frontend-slides` 负责；视觉方向探索由 `huashu-design` 负责。用户既
  要求高质量视觉又要求原生 PPTX 时，可先形成视觉规格，再由 `pptx` format service
  负责原生交付；F129 上线后可把该过程纳入持久项目和目标 Office 验证。

**核心能力**

- 读取页面尺寸、母版、版式、主题、占位符、文本、图片、表格、图表、备注、隐藏页、
  批注、超链接、媒体和外部关系的有界摘要。
- 接受 `.potx` 作为模板输入，生成 layout/slide inventory，并在交付前扫描未替换占位符。
- 新建原生可编辑 PPTX，优先使用用户模板；没有模板时使用少量 Space-owned 中性主题，
  不把 HTML 截图冒充可编辑幻灯片。
- 支持标题、正文、形状、图片、表格、基础图表、备注、页码和来源页；图片保持比例并
  记录裁剪策略。
- 修改现有 deck 时复用母版/版式/主题和 placeholder，避免把模板页扁平化成自由形状；
  合并/拆分/reorder 时修复关系 ID、备注、媒体和 slide references。
- 动画、SmartArt、复杂图表、嵌入媒体和 OLE 无法可靠编辑时保留原 part 并警告；不得
  静默丢失。

**验证**

- OOXML 结构、关系、slide/master/layout/theme 引用完整；
- 所有幻灯片均可渲染，页面数量和顺序正确；
- 检查元素越界、重叠风险、过小字号、文本溢出、低分辨率图片、缺失字体和对比度警告；
- renderer 使用替代字体时记录 font substitution，并把 text-fit 结果标为近似；需改用
  metric-compatible 字体或保留足够 layout slack 后才能通过；
- 模板 fixture 验证母版、版式、主题、placeholder 和未修改页保持；
- 讲者备注、来源页和可编辑对象在重新解析后存在；
- 通过结构、关系、原生对象和全页渲染检查后可声明“格式验证的可编辑 PPTX”；只有 F129
  的目标 Office 引擎、平台兼容矩阵和逐对象 receipt 才能升级为 `PowerPoint verified` 或
  对应目标 Office 的 verified 标签。

**建议资源**

- `references/operations.md`：新建、模板优先、内容替换、合并拆分和组合路由。
- `references/validation.md`：OOXML 关系、溢出、字体、图片和 render review。
- `references/limitations.md`：动画、SmartArt、复杂图表、媒体、OLE 和模板保真边界。
- deterministic helpers 负责 package inspection、关系修复、slide render manifest 和
  几何检查；视觉创意不硬编码在脚本中。

#### 3.5 依赖选择与打包原则

- 每个新增依赖必须允许商业复制、修改和再分发，并固定版本、许可证 hash 和来源。
- 优先使用当前包内已有的 `jszip`、`xlsx`、`pdfjs-dist`、`mammoth` 和 Space 预览代码，
  但不得因为“已有”就假设它适合写回或高保真编辑。
- 新 writer/transformer 通过代表性 fixture 证明保真后才能替换 F109 路径。
- 可选 LibreOffice/OCR adapter 必须是能力探测，不是安装时偷偷下载的依赖。
- Skill 自身和其脚本纳入 F135 的 path/size/SHA-256 精确锁、symlink/secret/link
  检查和 packaged smoke。
- F135 增加 first-party local-source 模式：作者源位于独立目录，构建以仓库 commit、
  source tree hash、许可证 hash 和生成规则产出只读 vendored snapshot；
  `resources/builtin-skills/` 仅为生成物与打包输入，不接受直接手工编辑。
- 四个 Skill 均使用 Space 自有许可证与来源声明；不包含第三方 proprietary Skill
  许可证文本或材料。

### 4. 接口契约

#### Skill metadata

四个 Skill 的 frontmatter 只保留 `name` 和 `description`。`description` 同时包含中文
触发语义和通用扩展名，正文不重复“何时触发”。

```yaml
name: docx
description: 处理以 DOCX 为主要输入或输出的专业文档创建、检查、修改和验证任务；当用户要求 Word 报告、合同、规范、模板编辑、表格图片或 DOCX/PDF 审核交付时使用。
```

其余三个分别以 PDF 页面/表单/提取、XLSX 工作簿/公式/数据、PPTX 原生可编辑演示为主要
触发语义。实际 frontmatter 在实现阶段通过 Skill validator 和中英文触发 fixture
定稿。

#### Operation result

所有格式操作返回一个机器可解析结果和一个简短用户摘要：

```ts
interface DocumentJobResult {
  readonly jobId: string;
  readonly status:
    | 'queued'
    | 'running'
    | 'completed'
    | 'completed-with-warnings'
    | 'blocked'
    | 'cancelled'
    | 'failed';
  readonly outputs: readonly DocumentOutputManifestEntry[];
  readonly progress?: {
    readonly phase: string;
    readonly completed: number;
    readonly total?: number;
  };
  readonly warnings: readonly string[];
  readonly nextActions: readonly string[];
}
```

- `completed` 要求所有确定性 postcondition 和适用的结构/视觉检查通过；抽样或模型审阅
  只按真实覆盖率呈现，不能升级为“全文语义正确”。
- 缺少 renderer、OCR 或 recalculation engine 时只能是 `completed-with-warnings`，除非
  该能力与本次任务无关。
- `blocked` 用于密码、宏/签名保真、路径权限或 unsupported active content 等可解释边界。
- `cancelled` 会终止整个隔离进程树并清理 staging；不会注册半套 outputs。
- 工具错误不回显任意文件正文、绝对敏感路径或未清洗的 parser stack。

#### Validation ownership

- Skill 决定需要哪些检查；
- `DocumentProcessingService` 执行确定性检查；
- F114 注册输出；
- 独立、版本锁定的 render service 产生视觉证据，File Viewer 只展示文件和预览；
- validation receipt 是结果旁的证据，不进入模型自报的自由文本真相。

### 5. 实现步骤

1. **冻结独立设计与来源记录**：评审本文件，记录公开规范/库候选与许可证，不读取任何
   proprietary Skill 表达作为实现输入。
2. **建立 fixture corpus**：独立创建中英双语、正常/畸形、宏/外链/签名、扫描件、模板、
   公式、图表、复杂关系、视觉溢出、提示注入、超时、崩溃和资源上限样本。
3. **先建可靠执行底座**：复用受限 Worker，增加独立子进程 adapter、私有 staging、输入/
   输出预算、整树取消、孤儿清理和无宏/无链接更新的隔离 profile；不等待 F138。
4. **定义共享服务与 Job**：实现 typed inputs/actions/targets、inspect/execute/validate/
   render/deliver、幂等 CAS、多输出 manifest、进度与取消，接入 F098/F114；F131 只展示。
5. **先做 read-only inspection**：四种格式先实现 bytes sniff、limits、active-content/
   privacy inventory、不可信 evidence delimiter、覆盖率和结构摘要。
6. **完成四格式功能面**：按 inspect/create/edit/transform/validate 顺序实现 3.1-3.4 的
   全部核心能力；adapter-dependent 路径用 capability probe 和真实降级处理，每步先写失败
   fixture，不以纵切样例代替 GA 功能。
7. **建立验证闭环**：结构重开、明确 postcondition、renderer receipt、基线缺陷/新增回归、
   截断范围和失败/警告降级；不可把抽样包装成全文件语义通过。
8. **编写中文 Skill**：使用 `skill-creator` 初始化四个作者源目录，保持 SKILL.md 精简，
   把格式细节放入一层 references。
9. **处理 Skill 重叠**：增加 `pptx`/F129/`frontend-slides`/`huashu-design` 路由测试；不新增
   `canvas-design` 或 `frontend-design` builtin，不创建第二套 PPTX writer/validator。
10. **纳入 F135 供应链**：实现 first-party local-source snapshot，自有来源条目、许可证
    hash、完整性锁、打包和干净 profile discovery。
11. **前向验证**：以真实用户任务运行四个 Skill，检查产物而不是只检查提示词；失败样本
    反推 Skill/host contract。
12. **能力缺口审计**：独立基线冻结后，仅把第三方产品观察转换成抽象能力问题；任何新增
    条目都要有公开规范/产品需求的独立理由，并在本文件的审计附录记录“采用/拒绝/延后”。
13. **发布门禁**：typecheck、lint、focused/full tests、build smoke、packaged skill byte
    integrity、四格式 artifact smoke，以及每个发行平台的 renderer/font/OCR capability
    matrix、结构/CJK/artifact smoke 全部通过；Windows portable 另做人测。

### 6. 验收标准

#### Cross-format

- 干净 profile 能发现且调用 `docx`、`pdf`、`xlsx`、`pptx`，无需复制到用户 Skill 目录。
- 用户/项目同名 Skill precedence 仍遵守 KodaX 规则；slash completion 不重复。
- 中英文自然语言触发正确；仅提到扩展名但主要交付物属于其他格式时不误触发。
- Partner 全流程不获得 raw shell/package install 权限。
- 每个输出都有 hash、delivery、producer、输入来源和 validation receipt。
- ZIP bomb、路径穿越、XXE、外部关系、公式注入、PDF active actions 和宏 fixture 均
  fail closed 或产生明确警告。
- ZIP/XML/PDF 解析上限、Worker heap、Office modal hang、timeout/cancel 和 adapter crash

## FEATURE_139: Semantic Motion Scroll Affordance and State Emphasis

### 1. 需求概述

KodaX Space 已经具备 Liquid Glass、Aurora、cursor spotlight、统一按钮 sheen、Reveal
入场动画和三档视觉质量控制，基础视觉语言完整。当前主要缺口不是更多装饰，而是密集工作
界面对以下事实表达不够明确：

- Task Dock 折叠区的标题行、箭头和相邻区块之间曾存在触发区域偏小或视觉间距大于实际
  hit target 的情况，用户难以判断整行是否可操作；
- 智能体、工作流、通知和引用文件等动态列表在新增、状态改变或发生滚动溢出时缺少边界
  反馈，容易被理解为静态内容；
- 当前选中区块、需要用户处理、运行中和失败状态主要依赖文字与局部颜色，快速扫视时
  层级不足；
- 已有玻璃、光晕与按钮 sheen 如果继续无差别叠加，会增加噪声和 GPU 成本，而不是提高
  可用性。

F139 以 React Bits 的交互模式作为行为级参考，独立实现适合桌面生产力工具的克制版本：

| 参考模式                                                                                                                         | Space 采用内容                                                        | Space 明确不采用                                       |
| -------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------ |
| [Animated List](https://reactbits.dev/components/animated-list)                                                                  | 新增/状态变化的短时淡入、滚动边缘提示，以及符合现有组件语义的键盘操作 | 对每次普通重渲染、流式 token 或历史回放重复播放动画    |

#### 目标

1. 所有可折叠标题行保持完整、连续且稳定的 32-36px hit target；箭头只是状态图标，不是
   唯一可点击区域。
2. 动态列表只在真实插入或用户可感知的状态变化时使用 120-180ms、最多 4px 的入场反馈。
3. 可滚动内容在顶部/底部存在更多内容时显示柔和边缘提示，并在到达边界后消失。
4. active rail 和 semantic glow 只表达真实 UI 状态；颜色沿用现有 accent、reasoning、
   warning、danger 和 success token。
5. 所有反馈服从现有视觉质量档位、`prefers-reduced-motion`、键盘访问和对比度要求。

#### 非目标

- 不引入全屏 WebGL 背景、Splash/Blob/Pixel Cursor、Tilted Card、Magnet、弹性缩放或
  其他会改变目标几何位置的效果；
- 不重做 KodaX Space 的信息架构、主题系统、玻璃材质或按钮基础样式；
- 不改变 Session、Runtime、Workflow、Agent、Notification、Artifact 或文件引用的状态
  所有权；
- 不增加 React Bits 运行时依赖，不复制其源码、CSS、示例或组件结构；外部页面仅作为
  行为级设计参考；
- 不把 P2 指标动效作为 0.1.36 发布阻塞项；P0/P1 的列表、滚动、选中和语义状态反馈才是
  GA 范围。

### 3. 技术方案

#### 3.1 共享 motion token

在既有视觉质量 token 上定义一组窄用途变量，数值可在实现阶段微调，但不得突破以下
边界：

```css
:root {
  --motion-list-enter-duration: 160ms;
  --motion-list-enter-offset: 4px;
  --scroll-edge-hint-size: 12px;
  --section-active-rail-width: 2px;
  --semantic-glow-opacity: 0.28;
}
```

- 只动画 `opacity` 和合成层 `transform`；不动画 `height`、`width`、`top`、`left` 或
  hit target 几何尺寸。
- `q-minimal` 与 `prefers-reduced-motion: reduce` 退化为瞬时状态变化；balanced 使用
  默认数值；full 可提高装饰层细腻度，但不得扩大位移或持续时间。
- 装饰层一律 `pointer-events: none`，不能遮挡滚动条、文字选择、按钮或上下文菜单。

#### 3.2 动态列表反馈

- 复用/扩展 `Reveal` 的门控能力，新增列表 item 只在 stable key 第一次进入集合时播放
  `opacity: 0 -> 1` 和 `translateY(4px) -> 0`。
- 已存在 item 的状态变化允许一次不改变布局的 tone transition；普通父级重渲染、窗口
  resize、折叠后重新展开、虚拟化回收、历史恢复和流式 token 更新不得被误判为新 item。
- stagger 只用于同一批次真实插入，单项间隔不超过 24ms，总延迟不超过 120ms。
- 键盘行为沿用组件本身的 ARIA 模式：普通链接/按钮列表保持 Tab 顺序，只有真实
  `listbox`/menu 模式才使用方向键；不得为了模仿示例而劫持全局方向键。

#### 3.3 滚动边缘提示

- 滚动容器放置不可聚焦的 top/bottom sentinel，通过 `IntersectionObserver` 推导
  `canScrollBefore` 与 `canScrollAfter`，避免在每个 scroll frame 执行 React state 更新。
- 边缘提示优先使用 surface color 到 transparent 的渐变 overlay 或 mask；不能模糊实际
  文字，也不能覆盖 scrollbar hit area。
- hint 仅在 `scrollHeight > clientHeight` 且对应方向仍有内容时显示；到达边界、容器
  变为不可滚动、区块折叠或被卸载时立即隐藏。

#### 3.4 Active rail

- Task Dock 区块继续以完整标题行作为按钮，并保留 `aria-expanded` 和
  `aria-controls`。
- 当前通过 `requestTaskDockFocus`、键盘 focus 或用户点击明确定位的区块显示 2px active
  rail；仅打开但不是当前目标的区块不冒充 selected。
- rail 在区块之间切换时可以进行 120-160ms 的 opacity/translate transition；标题文字
  的视觉位移不超过 3px，布局盒和点击位置保持不变。

#### 3.5 Semantic glow

统一使用业务状态到视觉 tone 的封闭映射：

| 状态              | Tone      | 行为                                      |
| ----------------- | --------- | ----------------------------------------- |
| 正常/静止         | neutral   | 无 glow                                   |
| 正在运行/推理     | reasoning | 状态进入时轻扫一次，随后保持低亮边框      |
| 等待用户输入/授权 | warning   | 低频静态强调；不使用无限闪烁              |
| 成功完成          | success   | 最多一次短时确认，不永久发光              |
| 失败/阻塞         | danger    | 稳定边框与图标/文字共同表达，不能只靠颜色 |

- glow 不从 hover 猜测状态，必须由现有 view model/props 显式传入；
- 状态 intro 最长 320ms，不使用无限旋转渐变；
- `q-minimal`、reduced motion 和高频状态抖动时只切换静态 border color；
- 同一 viewport 同时出现的持续 glow 数量应有界，普通卡片不参与。

#### 3.6 主操作与指标精修

- 现有全局 button sheen 继续是唯一按钮交互底座。主操作可以提高 specular 对比度，但
  不能再包一层独立组件或改变尺寸。
- Count-up 仅用于上下文数量、变更数等短时变化且非安全关键的真实数值；持续时间不超过
  250ms，最终 DOM/accessible name 立即反映准确值，动画中的视觉插值不进入可访问名称。
- 权限、费用、token 上限、错误数量等决策关键值默认瞬时更新，不使用计数动画。

#### 3.7 性能与独立实现

- 不新增 React Bits、Framer Motion、GSAP 或 WebGL 依赖；使用现有 React、CSS、WAAPI
  和浏览器观察器能力。
- 不使用多层实时 blur、持续 pointermove React render 或全局每帧循环。现有
  `useSpotlight` 是唯一全局 cursor-following visual owner。
- 在开发/打包构建中记录 representative Task Dock 的 scripting、layout、paint 与 GPU
  基线；balanced 档空闲时不得因 F139 保持持续动画。
- 参考链接只记录抽象行为；实现、命名、测试和样式均从 Space 现有组件与 token 独立
  推导。

### 4. 接口契约

F139 不新增 IPC。Renderer 内部保持窄类型和显式语义：

```ts
type SemanticEmphasisTone = 'neutral' | 'reasoning' | 'warning' | 'success' | 'danger';

interface SemanticEmphasis {
  readonly tone: SemanticEmphasisTone;
  readonly active: boolean;
  readonly intro?: boolean;
}

interface ScrollEdgeState {
  readonly canScrollBefore: boolean;
  readonly canScrollAfter: boolean;
}

interface MotionListItem {
  readonly stableKey: string;
  readonly change: 'inserted' | 'status-changed' | 'stable';
}
```

DOM/CSS contract:

- `data-semantic-tone` 只能取上述封闭 tone，且必须与可见图标/文字状态一致；
- `data-scroll-before` / `data-scroll-after` 只控制非交互装饰层；
- `data-motion-change="inserted"` 仅存在一个动画周期，完成后回到 `stable`；
- 可折叠标题保持原生 `button`，具备 accessible name、`aria-expanded`、
  `aria-controls`、`focus-visible` 和完整行 hit target；
- active rail 不取代 DOM focus indicator；键盘 focus 始终拥有独立、对比充分的 outline；
- reduced motion 与 visual quality 是共享 policy，组件不能提供绕过它们的局部开关。

1. **建立基线**：为 Right Sidebar、窄/宽 Task Dock、Workflow、Agent、Notifications、

2. **固化 hit target**：统一折叠标题的 32-36px 完整行按钮，扩大 icon button 到既有桌面

3. **扩展 motion policy**：在 `motion.ts`/`styles.css` 中加入共享 token、stable-key

4. **落地 P0 列表反馈**：先覆盖 Agent、Workflow、Notifications 和 Context referenced
   files；验证折叠、重排、回放和流式更新不会重复入场。
5. **落地 P0 scroll-edge hint**：实现 sentinel 驱动的 top/bottom 状态，接入

6. **落地 P1 active rail**：将明确的 Task Dock focus request、点击与键盘定位映射到单一

10. **回归与发布门禁**：运行 focused unit/E2E、renderer lint/typecheck、desktop build 和
