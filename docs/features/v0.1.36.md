# v0.1.36 - Task and Capability Governance

> Status: Planned
> Features: F089, F090, F091
> Depends on: F116 Runtime Host Adapter

## Batch decision

The Task Dock becomes the truthful desktop projection of three related questions:

1. What is the current plan and what evidence completed it?
2. Which runtime capabilities are healthy, degraded, or missing for this session?
3. What effort, autonomy, provider/model, and assurance facts are active?

Space displays Runtime-owned facts and explicit host policy. It does not create a parallel task engine, capability registry, or provider router.

## FEATURE_089: Task Plan Timeline and Completion Receipt

### User outcome

Users can see the current plan, bounded changes to that plan, drift warnings, completed/blocked/skipped work, and a session completion receipt that links claims to tool, test, diff, artifact, Workflow, and External Agent evidence.

### Contract and design

- Consume Runtime `todo.updated` and `todo.warning` events through F116.
- Maintain one renderer projection shared by the Plan popout and Task Dock.
- Record a bounded in-session change timeline with event sequence/time and source correlation.
- Restore only data supported by transcript/Runtime state. Do not persist a Space-authored Todo truth that can diverge from KodaX.
- Completion receipt sections:
  - requested outcome;
  - final plan status;
  - changed files/diffs when available;
  - verification/tool evidence;
  - created artifacts/deliveries;
  - Workflow/External Agent tasks;
  - blockers, limitations, and unverified claims.
- Copy/export creates an artifact from the receipt snapshot; it does not mutate the plan.

### Gate

Current-state and in-session timeline can ship on Runtime events. Durable todo editing/querying across hosts remains out of scope until KodaX exposes a public todo service; KX-F113 is a watchlist dependency, not a hidden assumption.

### Acceptance

- Plan and Task Dock never show different current items.
- Empty todo update clears current state without deleting the historical receipt.
- Drift warnings are session-scoped and recoverable.
- Completion receipt references available evidence and labels missing verification.
- Resume behavior is explicitly current-only or durable according to the SDK contract actually present.

## FEATURE_090: Runtime Capability Health and Resume Diagnostics

### User outcome

When a session is resumed or a run degrades, users can tell which MCP servers, Extensions, deferred tools, Skills, External Agents, and Runtime services are available, missing, stale, reconnecting, or policy-disabled.

### Contract and design

Consume:

- `runtime.catalog` providers/models/commands/skills/extensions;
- `runtime.mcp` server/tool state and reload;
- Runtime status/diagnostics and capability requirements;
- `tool.exposure.planned` events;
- External Agent dispatchable catalog and preflight;
- session/resume metadata when publicly available.

Views:

- **Summary**: healthy/degraded/blocked counts and the current Runtime mode/isolation.
- **Session capabilities**: capabilities available for this session/run, including policy-disabled reasons.
- **MCP and Extensions**: restored, missing, stale, disabled, reload/retry actions.
- **Tools and Skills**: resident/deferred/reachable facts from Runtime, not renderer inference.
- **External Agents**: dispatchability and adapter/capability gaps without exposing credentials.

Actions are shown only when the Runtime advertises them. “Continue degraded” is descriptive and never silently broadens permissions.

### Acceptance

- Resume with a missing MCP/Extension produces a visible degraded reason.
- Reload/retry targets the Runtime owner and reports success/failure.
- Disabled-by-policy and unavailable-by-runtime are distinguishable.
- A2A/MCP Tasks/governed HTTP remain hidden or explicitly unsupported until conformant adapters exist.
- Diagnostics never reveal keys, endpoints with credentials, raw config secrets, or task content.

## FEATURE_091: Effort, Assurance, and Route Receipt

### User outcome

Users control effort and autonomy without understanding provider-specific reasoning flags, and can inspect the provider/model/effort/assurance facts that the Runtime truthfully exposes.

### Design

- Keep canonical Space effort choices mapped to KodaX effort.
- Keep autonomy (`plan`, `accept-edits`, `auto`) separate from effort.
- Compact receipt fields:
  - requested and effective effort;
  - provider/model;
  - permission/autonomy mode;
  - context window/budget state when public;
  - assurance class or verification requirement when public;
  - fallback/route facts when public.
- Unsupported combinations are disabled or explained from SDK capability metadata.
- A “why this route” sentence appears only when KodaX exports resolved route/fallback facts. Until then, Space says what is selected/effective, not why the engine chose it.
- KX-F265 can add assurance/cost fields later through additive capability negotiation.

### Explicit non-goals

- No task-class selector that changes KodaX semantics.
- No Space-owned provider router or LLM classifier.
- No coupling between high effort and broad permissions.
- No fabricated explanation from model/provider names.

### Acceptance

- Effort and autonomy remain independent and persist with documented precedence.
- Effective provider/model/effort matches the Runtime session/run state.
- Fallback/degradation is visible when reported.
- Missing route/assurance contracts degrade to a smaller truthful receipt.

## Release acceptance

- The Task Dock uses one derived projection for plan, capability health, and effective run facts.
- Resume/degradation E2E covers missing MCP/Extension and provider fallback.
- No new durable store competes with Runtime-owned sessions, todos, catalog, or task ledger.

## Rollout and rollback

- Gate plan history, capability actions, and route receipts separately; a missing resolved-route contract must not hide basic effort controls.
- Rollback removes Space projections/actions only. Runtime sessions, todos, catalog state, and task-ledger records remain authoritative and untouched.
- Unknown capability fields render as unavailable with diagnostics, never as false healthy/disabled states.
