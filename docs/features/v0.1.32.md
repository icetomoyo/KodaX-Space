# v0.1.32 - Platform Trust and Semantic Control

> Status: Planned
> Features: F055, F069, F120
> Depends on: the `v0.1.31` Runtime adapter diagnostic boundary

## Batch decision

Before browser, connectors, refreshable artifacts, or broader beta distribution, Space needs a trustworthy packaged origin, a coherent diagnostic log, and one governed semantic control plane. This release closes those foundations and adds natural-language control without creating a second agent engine or letting an LLM drive arbitrary DOM interactions.

## FEATURE_055: Packaged Renderer `app://space` Origin

### User outcome

Packaged Space loads its own renderer and application resources from a standard privileged application origin. Navigation policy, CSP, artifact embedding, and future browser surfaces can distinguish application content from arbitrary `file://` paths.

### Current evidence and gap

Production currently loads the renderer from a packaged `file://` prefix and relies on exact path/navigation guards. The guards prevent common arbitrary-file navigation, but `file://` is not a strong long-term origin for interactive artifacts and browser-like surfaces.

### Design

- Register `app` as a privileged, standard, secure, CORS-enabled scheme before app ready.
- Serve only the packaged renderer root through `app://space/` with canonical path resolution.
- Reject traversal, encoded separator ambiguity, symlink/alias escape, directory listing, and unknown hosts.
- Keep development on the Vite origin; production-only behavior must have an explicit test mode.
- Update CSP, navigation guards, window-open policy, preload assumptions, asset URLs, source maps, and updater smoke.
- Keep user/local file references as data references; do not reinterpret arbitrary `file://` URLs as application resources.

### Security boundary

- `app://space` serves immutable packaged assets only.
- Artifact documents keep their existing sandbox/CSP rules and never inherit application privileges.
- No generic `app://` file proxy is exposed to the renderer.
- External URLs continue to use the system browser or a future governed browser surface.

### Acceptance

- Dev, packaged Windows, packaged macOS, and packaged Linux boot paths resolve assets correctly.
- Arbitrary paths, traversal variants, alternate hosts, and encoded escapes fail closed.
- CSP and navigation tests pin the application origin.
- Interactive HTML artifacts remain opaque-origin sandboxed.
- Auto-update and packaged smoke find all expected assets.

## FEATURE_069: Structured Main-Process Logging and Diagnostic Export

### User outcome

Users and maintainers can export a bounded diagnostic bundle that explains Space startup, Runtime capability state, recoverable failures, and release configuration without exposing prompts, API keys, credentials, or private document content.

### Current evidence and gap

Electron main currently uses `console.*` across dozens of production and test files. Messages have inconsistent levels, context, retention, and redaction. The earlier estimate of 33 files is stale; the 2026-07-12 audit found roughly 57 Electron files containing `console.*`.

### Design

- One main-process logger with `debug`, `info`, `warn`, and `error`.
- Structured fields: timestamp, component, event, session/run/task correlation when safe, release version, SDK version, platform, and error category.
- Daily/size rotation with bounded retention and atomic file handling.
- Central redaction for provider keys, authorization headers, URL credentials/query secrets, environment values, home paths where appropriate, prompt/tool payloads, and document bodies.
- Renderer errors cross a capped zod IPC envelope; renderer cannot choose log paths or arbitrary structured keys.
- KodaX tracing remains separately owned. Space logs correlation identifiers and capability state, not duplicated model/tool content.
- Diagnostics export includes manifest, redacted recent logs, capability ledger snapshot, updater/channel state, and known-degradation list.

### Migration

1. Add logger/redactor/rotation tests.
2. Migrate startup, Runtime adapter, updater, provider, permission, workflow, Partner, and External Agent paths.
3. Migrate remaining production `console.*` calls.
4. Enable lint enforcement for production Electron/renderer code with narrow test/script exceptions.
5. Add diagnostic export and size/content guards.

### Security boundary

- Logging defaults to metadata, never task content.
- Redaction happens before serialization and disk write.
- Diagnostic export is explicit user action and previews included categories.
- No remote upload is added.

### Acceptance

- Production Electron code passes the scoped `no-console` rule.
- Secret fixtures never appear in log files or exported bundles.
- Rotation/retention survives restart and concurrent writes.
- Correlated Runtime/workflow/external-agent failures are diagnosable without raw content.
- Export size and file count are bounded, and corrupt logs do not block application startup.

## FEATURE_120: Natural-Language Space Control

### Decision and user outcome

After at least one Provider is configured, users can describe an explicit Space control intent in ordinary language from either Coder or Partner—for example, “switch to dark theme”, “open MCP settings”, “use deep reasoning by default”, or “show the Task Dock at half width”. KodaX interprets the request and invokes a bounded Space-owned tool. Space resolves one typed semantic action, validates it against current state and window/session authority, executes it through the same implementation used by ordinary UI controls, and shows an inspectable receipt with undo when supported.

The product target is not “the model can click anything”. The target is:

> Every eligible Settings and top-level shell control has one stable semantic action ID. Buttons, Command Palette, slash compatibility paths, and LLM tool calls reuse that action instead of implementing parallel behavior.

Every user-facing Settings or shell control must therefore be classified as one of:

1. `controllable`: safe to expose through a typed action;
2. `confirm`: exposed, but execution requires a trusted user confirmation surface;
3. `user-only`: the action may navigate to or explain the control, but the model cannot provide or approve the sensitive value;
4. `not-semantic`: pointer/scroll/drag implementation detail with no stable product meaning.

The coverage denominator is a generated manifest of every interactive Settings row and top-level Shell control rendered by a supported platform/feature flag, plus every existing Command Palette or local slash action that already changes those states. A compound row counts once per independently invocable control. `controllable` and `confirm` entries require descriptors and executors; `user-only` and `not-semantic` entries require one of the reviewed exclusion codes defined by F120, not free-form omission. Conditional controls remain in the manifest with their availability gate.

Release acceptance requires 100% classification coverage and 100% executor parity for every `controllable`/`confirm` entry. It does not require pretending that secrets, permission decisions, native file selections, or arbitrary pixel operations are safe model actions.

### Current evidence and gap

Space already has the ingredients but not one contract:

- `commandSources.ts` has a small renderer-only action list for new session, theme cycling, and clearing the visible conversation.
- `BottomBar.dispatchSlashAction()` contains a large independent dispatcher for local UI and IPC operations such as status, Memory, MCP, session selection, fork, rewind, and deletion.
- Settings controls call typed IPC such as `settings.setLanguageMode`, `settings.setRuntimeDefaults`, and `settings.kodaxConfig.setCompaction` directly.
- Shell navigation/layout state is split across Zustand/localStorage, `SurfaceStore`, `Shell` component state, Floating Surface Host state, and main-owned settings.
- Space already registers in-process KodaX tools and attributes them with `session-run-context.ts`, but there is no Space-control tool or semantic action catalog.

Consequences today:

- A natural-language request is treated as ordinary task text unless it happens to map to an existing KodaX task tool.
- UI buttons, Command Palette, slash commands, and settings can drift because they do not share an executor.
- The model cannot discover current safe UI state or know which Space controls are available.
- Adding “natural-language UI control” by parsing assistant prose or dispatching DOM clicks would be brittle, untestable, and unsafe.

### SDK and capability contract

F120 does **not** require a new KodaX feature for the `v0.1.32` inline Runtime path. The exact published `@kodax-ai/kodax@0.7.67` baseline already provides:

- `@kodax-ai/kodax/coding.registerTool()` for host-owned local tools;
- required tool `sideEffect`, `planModeAllowed`, `interruptBehavior`, and classifier-projection metadata;
- `KodaXToolExecutionContext.sessionId`, `toolCallId`, `executionCwd`, `gitRoot`, and `agentProfile` for trusted run attribution;
- F116 inline Runtime execution with Space-owned callbacks/tool registration preserved.

Space remains the owner of action definitions, UI state, policy, confirmation, persistence, undo, and receipts. KodaX owns natural-language reasoning and tool-call generation. Space must not add a separate intent model, prompt classifier, or agent loop.

Capability gate:

```text
F116 inline Runtime ready
AND registerTool available
AND tool execution context resolves session + surface
AND primary renderer action broker ready
=> natural-language Space control supported
```

If any gate fails, UI buttons, Settings, Command Palette, and existing slash behavior continue to work; only the LLM control entry is reported unavailable. A KodaX version comparison alone is not a gate.

Worker/daemon transport is explicitly outside the `v0.1.32` gate. Those modes will need a future transport-safe host-tool registration/callback contract before they can execute renderer-owned actions. F120 must not serialize functions into Runtime DTOs or silently fall back mid-turn.

### Semantic action contract

The shared schema package defines metadata and bounded inputs; execution implementations remain in their state-owning processes.

```ts
type SpaceActionEffect =
  | 'observe'
  | 'ui-ephemeral'
  | 'preference-write'
  | 'state-mutation'
  | 'destructive'
  | 'sensitive-user-only';

type SpaceActionOwner = 'renderer' | 'main';
type SpaceActionConfirmation = 'none' | 'explicit-intent' | 'dialog' | 'user-only';

interface SpaceActionDescriptor {
  readonly id: string;
  readonly version: 1;
  readonly titleKey: string;
  readonly descriptionKey: string;
  readonly owner: SpaceActionOwner;
  readonly effect: SpaceActionEffect;
  readonly confirmation: SpaceActionConfirmation;
  readonly surfaces: readonly ('code' | 'partner')[];
  readonly planModeAllowed: boolean;
  readonly revisionKey: string;
  readonly inputSchema: JsonSchema;
  readonly receiptSchema: JsonSchema;
  readonly availability: SpaceActionAvailability;
  readonly undo?: { readonly supported: true; readonly ttlMs: number };
  readonly aliases: readonly string[];
}

interface SpaceActionRequest {
  readonly requestId: string;
  readonly actionId: string;
  readonly args: Record<string, unknown>;
  readonly origin: {
    readonly sessionId: string;
    readonly projectRoot: string;
    readonly surface: 'code' | 'partner';
    readonly toolCallId: string;
  };
  readonly expectedRevision: number;
  readonly preconditionToken: string;
}

interface SpaceActionReceipt {
  readonly requestId: string;
  readonly actionId: string;
  readonly status: 'applied' | 'unchanged' | 'denied' | 'cancelled' | 'failed' | 'unknown';
  readonly summaryKey: string;
  readonly safeDetails: SpaceActionReceiptDetails;
  readonly revision: number;
  readonly undoToken?: string;
}
```

Rules:

1. Action IDs are stable product API, not component names or DOM selectors.
2. Arguments are parsed again by the owner immediately before execution.
3. Availability is derived from current state and capability negotiation, never trusted from the LLM.
4. `SpaceActionAvailability` is `{ available, reasonCode?, currentRevision, preconditionToken, safeState? }`. The opaque, short-lived token is issued by inspect and binds action ID, owner, renderer/main instance ID, origin session/surface, revision key, revision, and expiry. `safeState` and receipt details use per-action allowlisted schemas; they are not open string maps.
5. Revisions are monotonic per `owner + rendererInstance + revisionKey`, not global. Inspect returns the relevant revision and token. Apply requires both and rejects omission, expiry, action/argument mismatch, or owner/instance mismatch. Unrelated actions discovered together do not invalidate one another; a conflicting mutation of the same key does.
6. LLM execution requires `sessionId + toolCallId + actionId + canonical-argument-digest`. A process-local, bounded 10-minute/1,024-entry LRU returns the prior receipt for an exact retry and rejects reuse with different arguments. Missing `toolCallId` fails closed. Restart clears the cache; actions themselves must still be idempotent when possible.
7. Receipts contain localized keys and values accepted by the descriptor's receipt schema, never secrets, prompts, raw paths when avoidable, or arbitrary renderer error strings.
8. Multi-action requests execute in model call order as separate actions with separate receipts. A failure stops dependent follow-up actions; independent actions require a fresh apply call. There is no grouped transaction or grouped undo.
9. Main resolves the authoritative session from `sessionId`, derives surface from the Space session/agent profile, and rejects a tool-context/profile mismatch. Project-scoped actions require the authoritative session project or an explicitly selected catalog target; the model cannot supply an arbitrary root.
10. Every LLM-exposed F120 action is desired-state and replay-safe (`set dark`, `set open`, `set pinned=true`), never a blind toggle/increment/create-side-effect. `ui.session.new` means idempotently enter the existing no-current-session landing state; actual Session creation remains the existing next-send lifecycle.

### LLM tool surface

Register two small tools rather than embedding the complete action catalog in every prompt:

#### `space_control_inspect`

- `sideEffect: 'readonly'`;
- accepts a short `query` plus optional action ID;
- returns matching action descriptors, current safe state, availability, confirmation level, and argument shape;
- never returns secrets, credential status beyond existing redacted provider facts, prompt content, or unrestricted paths.

#### `space_control_apply`

- `sideEffect: 'mutates-state'`;
- accepts exactly one `actionId`, bounded `args`, and the mandatory `expectedRevision + preconditionToken` returned by inspect; apply never substitutes current state when the model omits or races either value;
- declares `planModeAllowed: true` at the coarse KodaX tool layer, then **must** re-check the trusted origin session in `KodaXHost` and admit only descriptors with `planModeAllowed: true`; v0.1.32 permits only `ui-ephemeral` and explicitly listed non-security preference writes in plan mode;
- resolves the trusted session context from the tool execution context/ALS and calls `SpaceActionService`;
- returns the canonical receipt, not improvised prose.

Both tools use progressive disclosure (`shouldDefer`) so ordinary coding/knowledge turns do not pay the full control-description cost. Tool descriptions instruct the model to act only on an explicit user control request; ambiguous language must use `ask_user` or explain available actions rather than guessing.

`explicit-intent` is a UX policy for low-risk reversible actions, not a security proof: main cannot trust the model to attest what the user meant. Any action whose abuse matters uses `dialog` or `user-only`, regardless of how explicit the prompt appears. Confirmation is bound to a Space-generated token covering request ID, action ID, canonical argument digest, revision, origin session, renderer instance, and expiry; it requires a direct user gesture and is single-use. AskUser/model output cannot satisfy it.

Partner receives the same semantic control entry through a frozen Partner tool-policy scope named `space-control`. Tool-name admission alone is insufficient because `space_control_apply` multiplexes actions: inspect filters descriptors by `surfaces`, and apply enforces the same per-action surface matrix again. Partner receives appearance, navigation, layout, panel, and non-sensitive Partner-compatible preferences; Coder-only Memory/runtime/project actions remain absent/denied. This does not grant Partner Coder shell/edit/write/workflow/subagent capabilities. Ambiguous Partner requests may be answered as a normal clarifying assistant turn; F120 does not depend on an additional Partner `ask_user` entitlement.

### UX and data flow

#### In-session flow

```text
User: “切到深色主题，把任务栏调成一半”
  -> KodaX calls space_control_inspect("theme task dock half")
  -> Space returns ui.theme.set + ui.taskDock.widthMode.set
  -> KodaX calls space_control_apply twice
  -> main validates origin and descriptor
  -> renderer action broker applies semantic actions
  -> renderer acks each request
  -> main returns two canonical receipts
  -> conversation shows one compact local receipt group with Undo where supported
```

The UI may switch surface/session while the originating run is still completing. The receipt remains attributed to the origin session, and the run continues under its original session owner. A navigation action must not rebind the active run to the newly visible session.

#### No-provider and degraded flow

- Before a Provider is configured, natural-language interpretation is unavailable by definition. Existing onboarding, Settings, buttons, Command Palette search, and slash commands remain deterministic.
- If all configured Providers fail, Space shows “Natural-language control unavailable” and offers generic deterministic entry points (Command Palette and Settings). It does not claim to know the matching control without a completed inspect result and does not use regex rules to impersonate LLM understanding.
- A configured Provider is insufficient when the active Runtime capability snapshot cannot preserve inline host tools. Space reports the failed capability gate and keeps deterministic controls; it does not attempt Worker/daemon execution or legacy mid-turn fallback.
- Sensitive setup requests may navigate to the correct Settings field, but credentials are typed by the user directly into the protected control.

#### No-active-session flow

`v0.1.32` does not add a second hidden agent engine. The primary supported entry is the normal Coder/Partner composer, whose existing lazy-session behavior supplies a trusted run context. With a current project but no Session, a control-only first turn therefore creates the same visible Session as any other first composer turn; this is accepted and covered by human acceptance rather than hidden. With no current project there is no trusted run context, so natural-language control is unavailable and deterministic theme/Settings/Command Palette controls remain the fallback. A later release may add a bounded ephemeral `space-control` Runtime profile if session clutter is measured and KodaX publishes/retains the required profile/tool-visibility contract; F120 does not block on that extension.

User-only/excluded controls for this release:

- API keys, authorization tokens, credential references, and keychain reads/writes;
- arbitrary Base URL/header/env entry, because values may contain secrets or create network-policy changes;
- permission/AskUser/confirmation answers—the model cannot approve itself;
- native file/folder picker selection and OS credential dialogs;
- Provider testing, destructive deletion, application exit/restart, installer/update acceptance, arbitrary project-file mutations, MCP installation/config writes, and external network sends;
- scroll position, caret placement, drag coordinates, hover state, animation progress, and other non-semantic UI mechanics.

For an excluded control, the action catalog may expose a safe navigation action such as `ui.settings.section.open`, `ui.providerSettings.open`, or `ui.workspacePicker.open`; it must not expose the sensitive value mutation or treat picker navigation as user selection. Session/project organization and security-sensitive defaults are `planModeAllowed: false`. Plan mode permits only appearance, surface/panel/layout navigation, and non-widening preferences explicitly marked in the descriptor.

### Process ownership and execution architecture

```text
KodaX inline run
  -> space_control_inspect / space_control_apply
  -> SpaceActionService (Electron main authority)
       -> shared descriptor registry + policy + idempotency + receipts
       -> main-owned executor
            -> SettingsStore / provider/session/project IPC services
       -> RendererActionBroker
            -> push spaceControl.actionRequested
            -> primary renderer validates request + current revision
            -> Zustand / SurfaceStore / Shell semantic executor
            -> invoke spaceControl.actionResolved
       -> optional ConfirmDialog broker
  -> canonical tool result + local receipt event

Buttons / Command Palette / slash compatibility
  -> same SpaceActionService or renderer semantic executor
  -> same descriptor, validation, receipt, and undo rules
```

Renderer actions require a request/response broker modeled after `PermissionBroker` and `AskUserBroker`: bounded pending map, timeout, shutdown/session cancellation, primary-window authority, request IDs, and stale-response rejection. Auxiliary/artifact windows cannot execute or acknowledge control requests.

The broker handles both `inspect` and `apply` so main does not mirror arbitrary renderer state. Inspect returns only descriptor-approved safe state plus the owner instance, per-`revisionKey` revision, and an opaque precondition token. Apply uses a prepare/apply/readback protocol: the broker validates the token against the still-current owner instance/revision, applies, advances the key revision, persists according to the existing owner, then returns canonical readback. Renderer reload changes the instance ID even when a numeric revision repeats, so stale pre-reload tokens fail. If apply may have committed but the acknowledgement is lost, main returns `status: 'unknown'`, blocks automatic retry, and performs one bounded readback reconciliation by request/idempotency key. It reports `applied` only after matching state is observed; otherwise the receipt remains unknown and tells the user to inspect state. Late acknowledgements can reconcile an unknown receipt but cannot apply again.

Confirmation tokens are issued and consumed by the primary renderer broker, require a trusted click/keyboard gesture, and are bound to the canonical request fields and current revision. Navigation, renderer reload, timeout, cancellation, conflicting revision, or first consumption invalidates them.

Undo is a receipt-local **user-only** control in `v0.1.32`; the model cannot invoke it. The action owner stores the descriptor-approved before-state in a bounded in-memory token table. Tokens are single-use, expire after the descriptor TTL, do not survive restart, and fail on renderer-instance or revision conflict. Undo produces its own canonical receipt. Multi-action receipt groups expose independent undo controls only.

Renderer-only state stays renderer-owned. F120 must not move every transient layout bit into main merely to make it controllable. Main persists only values already owned by Settings/project/session services and coordinates renderer actions through typed push/ack channels.

Trusted buttons and Command Palette entries call the same descriptor schema and semantic executor with `origin: 'trusted-ui'`. Renderer-owned controls may use the local executor directly; they do not impersonate an LLM request or bypass a main-owned setting executor. The parity contract is the descriptor/executor/readback result, while LLM-only idempotency, confirmation, and origin checks remain enforced in `SpaceActionService`.

### Security and permission boundary

- Natural language is untrusted input; the model output is also untrusted input.
- Composer copy warns users never to paste credentials into chat. Once a secret is submitted in a prompt it may already have reached the configured Provider; F120 refusal cannot retroactively redact it. Local pre-send secret detection is a separate feature and is not claimed here.
- There is no generic `invoke(channel, payload)`, JavaScript evaluator, DOM selector, CSS selector, click coordinate, shell command, filesystem path, URL, or arbitrary Zustand key in the tool schema.
- Action IDs and argument schemas are allowlisted at build time.
- The main process derives window, origin session, project, surface, current target, confirmation policy, and availability from trusted state.
- `explicit-intent` means the tool may be used only for a clearly requested reversible preference/UI action. It is guidance and an audit classification, not trusted authorization and not permission to chain unrelated actions.
- `dialog` confirmations use Space-owned text from the descriptor and safe arguments. LLM-authored confirmation text is never authoritative.
- `user-only` actions cannot be upgraded by prompt wording, auto mode, Partner mode, a remembered permission, or an LLM tool retry.
- Undo tokens are opaque, single-use, bounded by time, bound to the original action/window, and invalidated by conflicting later mutations.
- F069 logs only action ID, effect class, result, duration, safe correlation IDs, and redacted failure category; it never logs the original prompt or sensitive arguments.
- Tool visibility and execution fail closed when the action catalog, renderer broker, or capability snapshot is unavailable.
- Partner/Coder surface policy, plan-mode policy, confirmation, and user-only classification are enforced from trusted descriptor/session state again at apply time; inspect output and model-selected IDs are never authority.

### Compatibility and migration

1. Build the action inventory without changing behavior.
2. Move existing Command Palette actions to semantic executors.
3. Move Settings and shell buttons family by family; each migration keeps the same visible behavior and persistence key.
4. Route compatible slash actions through the registry while preserving slash names and transcript/local-notice behavior.
5. Register LLM tools only after UI parity tests pass for the corresponding family.

No persisted preference is renamed solely for F120. Action descriptors refer to current owners and adapters. Existing localStorage/settings values remain readable. Rollback removes LLM tool exposure and keeps deterministic UI/slash paths operational.

### Explicit non-goals

- Building a Space-specific LLM, classifier, planner, or second agent runtime.
- Letting the LLM control the app through screenshots, accessibility-tree traversal, DOM clicks, or computer-use automation.
- Claiming every pointer gesture is a semantic product action.
- Allowing the model to enter/read credentials, grant permissions, confirm its own mutation, or bypass current Provider/project/session policies.
- Natural-language control before Provider configuration.
- Worker/daemon host-tool transport in `v0.1.32`.
- Cross-device control, remote administration, voice input, macros/automation scheduling, or background execution.
- Replacing buttons, menus, keyboard shortcuts, Command Palette, or slash commands. Natural language is an additional entry to the same control plane.

### Implementation slices

#### P0 - Control inventory and frozen behavior

- Enumerate Settings rows, Shell controls, Command Palette actions, and local slash actions.
- Assign action ID, owner, effect, confirmation, undo, and exclusion reason.
- Freeze current behavior/persistence fixtures before refactoring.
- Define reviewed exclusion codes and freeze the v1 action-ID catalog before implementation leaves P0.
- Add a coverage test that fails when a manifest entry has no classification, when a `controllable`/`confirm` entry lacks a descriptor/executor, or when an exclusion lacks a reviewed code.

#### P1 - Shared schema and registry

- Add `space-control` schemas/channels to `space-ipc-schema`.
- Implement descriptor registry, catalog query, availability, revision, result, and safe receipt formatting.
- Reject duplicate IDs, schema drift, unsafe metadata, and unbounded aliases/details.

#### P2 - Main service and renderer broker

- Add main-owned `SpaceActionService` with idempotency, serialization, confirmation routing, undo tokens, and audit hooks.
- Add primary-renderer request/ack broker with timeout, stale-request rejection, cancellation, and shutdown cleanup.
- Implement compact receipt/undo UI as local client notices, not assistant claims.

#### P3 - Deterministic UI convergence

- Route Command Palette, theme/language/surface/session/layout controls, panel opening, field-specific runtime defaults, recent-workspace preference/picker navigation, compaction, configured-provider default/navigation, and reversible session/project organization through semantic executors.
- Migrate compatible slash actions without breaking command names or history behavior.
- Keep excluded controls explicitly user-only.

#### P4 - KodaX tool integration

- Register inspect/apply tools against the exact published SDK.
- Bind run context, surface policy, plan-mode exception for the bounded preference/UI subset, classifier projection, progressive disclosure, and abort handling.
- Register a Partner `space-control` policy without widening Partner's ordinary tool surface.

#### P5 - Hardening and release acceptance

- Concurrency, retry/idempotency, stale session/window, renderer crash/timeout, undo conflict, localization, and malformed-model-output tests.
- F069 redacted action diagnostics.
- Packaged smoke over the F055 `app://space` origin.
- Bilingual manual, self-manual topics, capability status, and human test guide.

### Automated acceptance

### Rollout and rollback

- Gate LLM tool exposure independently from the semantic action registry. Deterministic UI migration can ship dark while tool exposure remains off.
- Enable action families progressively: appearance/navigation, layout/panels, non-sensitive Settings, then reversible organization.
- Keep per-family kill switches only during rollout; remove them after the patch reserve unless evidence requires retention.
- On LLM-policy rollback, stop new applies, reconcile or mark pending requests unknown, unregister/hide the KodaX tools, and cancel uncommitted broker requests. Do not roll back persisted user preferences.
- Semantic-executor regressions require a normal binary rollback, so current persistence formats remain backward-compatible and downgrade smoke reopens the last release against preferences written by F120. The implementation retains the old deterministic adapter only until every parity fixture is green; it is not a permanent second path.
- `v0.1.33-v0.1.34` remain patch reserve for origin/logging/control regressions.
