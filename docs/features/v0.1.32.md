## Batch decision

The unreleased `v0.1.32` patch reserve is reassigned to F121. Coder moves toward one profile-scoped shared daemon truth for Space, terminal, and IDE clients. Partner explicitly remains Space-owned embedded inline and is not part of the daemon migration.

## FEATURE_121: Coder Shared Daemon and Multi-Client Live State

### Decision and user outcome

A user can start a Coder run in a terminal, open the same session in Space, and immediately see its current state without transferring or restarting the run. Space shows transcript streaming, thinking/tool activity, elapsed time, Todo progress, managed-task state, queued input, permission prompts, AskUser prompts, completion, cancellation, and errors from the same daemon truth. An authorized client can answer or control the run, and another attached client observes the result.

The user-visible behavior is equivalent to multiple terminal clients attached to one core:

- attaching or closing Space does not start, clone, cancel, or take ownership of the run;
- all clients converge after reconnect without duplicated transcript or terminal events;
- run initiation is attributed to a client, but run lifetime belongs to the daemon;
- Partner continues to behave exactly as it did in `v0.1.31` and is not blocked by daemon availability.

### Release scope

F121 covers the Coder shared-session core:

- daemon attach/auto-start, identity, version and capability negotiation;
- session list/load/create/settings plus active and queued run state;
- atomic live observation, ordered event replay, reconnect and cursor recovery;
- assistant/thinking/tool/Todo/managed-task live projections and semantic spinner state;
- run start/abort, same-session FIFO starts, after-turn input and truthful interrupt input;
- daemon-owned pending permission and AskUser requests with multi-client response;
- secure credentials for Space-started daemon runs;
- Space-only host capabilities, including Artifact and F120 Space Control, for explicitly Space-started runs;
- deterministic failure, rollback, profile isolation, diagnostics and process-distinct conformance tests.

The `v0.1.32` ship target is **default-on shared daemon for Coder**. Intermediate slices may land behind an internal diagnostic flag, but that dark rollout does not make F121 Completed and is not the release outcome. Before the version is cut, Space generates a manifest of every Coder action exposed by the released `v0.1.31` baseline. Every generally available entry—including Workflow, MCP and Reference External Agent paths—must have daemon parity and pass its regression fixture. Already capability-gated experimental/future entries such as incomplete Memory/Learning actions may remain gated. Shared mode never routes an unsupported action to a hidden inline Coder owner; any deliberate removal of a released Coder action requires a separate reviewed roadmap rebase rather than an implicit F121 degradation.

### Current evidence and gap

KodaX `0.7.69` provides the published-type substrate consumed by the current Space integration:

- daemon mode uses a named pipe on Windows or a Unix domain socket on Linux/macOS;
- clients using the same resolved home/profile attach to one Runtime owner;
- Runtime exposes sessions, runs, ordered events, replay, permissions, workflows, catalog, MCP, artifacts, status, diagnostics, agents and agent tasks;
- same-session `runs.start()` calls are queued, and closing a daemon client detaches without stopping the daemon or its runs.

Space now consumes that model, but the current public contract still leaves these release-relevant gaps:

- daemon session `surface` is filterable metadata, but no public server-enforced Coder-only admission rule prevents direct loading/mutation of an inline Partner session ID;
- a late join cannot atomically recover current managed-task state because it is available only through future events;
- the observation snapshot has no transcript revision/token that proves transcript and live state came from one boundary;
- queued-run metadata does not identify the after-turn input/request sufficiently for truthful late-join queued bubbles and targeted cancellation;
- the client has no transport disconnect callback, so Space currently detects loss through bounded status polling;
- a Space-sourced credential/host binding is connection-bound, so an accepted queued run cannot yet be guaranteed independent of the originating Space process;
- Runtime event payloads remain `unknown` rather than a public discriminated payload map;
- Space settings `agentMode` and `autoModeEngine` are not represented in `RuntimeSessionSettings` and therefore cannot participate in daemon CAS;
- durable notification acknowledgement, operation/host-call reconciliation and the full administrative rollback preflight remain unavailable.

Existing `events.subscribe()` plus `events.replay()` is useful but insufficient as the final join protocol. A separate status read followed by subscribe has a race window; replaying an unbounded event history is also not a reliable current-state query for in-memory Todo, partial assistant output, active tools, or pending interaction state.

An event journal is a change log, not the complete query model. The daemon must update the live projection before publishing the corresponding durable event. Space consumes the snapshot as the current truth and the journal as ordered changes after its cursor.

### Required KodaX SDK and daemon contract

The existing daemon API is the foundation, but F121 cannot ship from Space changes alone. The upstream contract must be published, versioned, capability-negotiated, and tested across distinct processes. Version strings alone are not a gate.

This section records Space's release-blocking **observable semantics** and one viable contract shape. Every TypeScript block and method/type name below is a **non-normative example**, not a mandate for KodaX's internal implementation. The upstream team may satisfy the same behavior with a different public design; Space consumes only the final published, capability-negotiated contract. Tests assert observable outcomes, not the example names or private persistence mechanism.

#### 1. Client identity and handshake

Extend client identity with:

```ts
interface RuntimeClientIdentityV2 {
  clientId: string; // stable installation/profile identity
  instanceId: string; // new for each process launch
  name: string;
  title?: string;
  version?: string;
}

interface RuntimeConnectionIdentity {
  connectionId: string;
  runtimeId: string;
  profile: string;
  protocolVersion: number;
  capabilities: Readonly<Record<string, { version: number }>>;
  eventHeadSeq: number;
}
```

`clientId` is not accepted as an arbitrary caller string. A stable client must prove a current-user-bound registration across process restarts; the upstream storage/handshake mechanism is its choice. Losing that proof creates a new client identity rather than inheriting leases/notifications. `RuntimeRunStatus` also exposes a sanitized `initiatedBy` record. Identity remains attribution and a policy input, not authorization by name; transport authentication and server operation policy remain authoritative.

Because Space keeps Coder and Partner session files in the existing shared session directory, the published boundary must also enforce an operation-admission rule that reserves Partner-owned sessions from daemon mutation while allowing read-only discovery. The exact tag, namespace or lease design is not prescribed here; the cross-owner rejection behavior and deterministic legacy classification are required.

#### 2. Atomic live observation

Add public session- and profile-scoped operations equivalent to:

```ts
runtime.live.observeSession({ sessionId, cursor? })
  -> { snapshot, cursor, subscription }

runtime.live.observeProfile({ cursor? })
  -> { snapshot, cursor, subscription }
```

The cursor is `{ runtimeId, seq }`, not a naked sequence number. The server guarantees that each snapshot represents state at cursor `C` and that its subscription delivers changes after `C` without a gap. A changed `runtimeId` returns a typed cursor-reset result and forces a fresh observation. Exact API naming may differ, but these semantics are release-blocking.

The live snapshot includes:

```ts
interface RuntimeSessionLiveSnapshot {
  session: RuntimeSessionSummary;
  transcriptRevision: string;
  transcriptThroughEntryId?: string;
  lastTerminalRun?: RuntimeRunTerminalSummary;
  activeRun?: RuntimeRunStatus;
  queuedRuns: readonly RuntimeRunStatus[];
  assistantDraft?: { text: string; startedAt: string };
  thinkingDraft?: { text: string; startedAt: string };
  activeTools: readonly RuntimeActiveTool[];
  todos: readonly RuntimeTodoItem[];
  managedTask?: RuntimeManagedTaskSnapshot;
  queuedInputs: readonly RuntimeQueuedInput[];
  pendingPermissions: readonly RuntimePermissionRequest[];
  pendingUserInputs: readonly RuntimeUserInputRequest[];
  cursor: { runtimeId: string; seq: number };
}
```

`sessions.transcript` must accept the immutable `transcriptRevision` returned by observation, or observation must return an equivalent consistent paginated transcript cursor. Space begins buffering post-cursor events before loading that exact transcript revision. If the revision is no longer available, it discards the partial join and starts a new observation; it never combines a latest transcript with an unrelated live cursor. `lastTerminalRun` preserves completion/cancellation/error/stop reason when Space attaches just after a run ends.

The profile snapshot contains current session summaries, active/queued runs, each session's last terminal run ID/state/reason, pending permission/user-input requests, unacknowledged durable notifications for the stable client, and the profile cursor:

```ts
interface RuntimeProfileLiveSnapshot {
  sessions: readonly Array<{
    session: RuntimeSessionSummary;
    activeRun?: RuntimeRunStatus;
    queuedRuns: readonly RuntimeRunStatus[];
    lastTerminalRun?: RuntimeRunTerminalSummary;
  }>;
  pendingPermissions: readonly RuntimePermissionRequest[];
  pendingUserInputs: readonly RuntimeUserInputRequest[];
  notifications: readonly RuntimeClientNotification[];
  cursor: { runtimeId: string; seq: number };
}
```

Run-terminal and interaction notifications have stable IDs, bounded content/retention and an idempotent per-stable-client acknowledgement operation. On cursor reset, profile observation returns still-unacknowledged notifications and the per-session terminal summary, preventing both silent loss and repeated notification after acknowledgement. This gives global completion and interaction notifications the same atomic join guarantee as the selected-session stream.

Drafts and tool payloads are bounded. A cursor-expired response is typed and tells the client to reload a consistent transcript revision plus a fresh live snapshot; it never causes a run or tool to replay.

#### 3. Typed event protocol

Replace transport-facing `payload: unknown` with a versioned discriminated event map for every event used by Space. Every envelope keeps stable `id`, monotonic `seq`, `time`, `sessionId`, `runId`, optional `turnId`, and typed payload.

At minimum, schemas cover run/turn lifecycle, assistant/thinking deltas, tool lifecycle, Todo, managed-task state, queue, permission, user input, workflow, provider recovery and terminal events. Unknown future event types may be ignored only when capability/version rules declare that safe.

#### 4. Daemon-owned user input

Add a Runtime user-input service with operations equivalent to:

- `listPending({ sessionId?, runId? })`;
- `respond(requestId, answer, clientRequestId)`;
- `dismiss(requestId, reason, clientRequestId)`.

The daemon durably records and owns the pending request before emitting `user_input.requested`. The first valid answer wins atomically; later answers receive a typed resolved/conflict result. Abort, timeout, run termination and daemon shutdown resolve or dismiss every pending request exactly once.

This replaces function callbacks as the Coder AskUser transport. Partner continues using the existing inline callback broker.

#### 5. Permission request and persistent grants

Pending permission requests remain daemon-owned and respondable by any authenticated same-user client admitted by the operation policy below. The daemon durably records the pending request before emitting `permission.requested`. `allow_always` must create or match a daemon/profile-owned grant rather than being an alias for `allow_once`.

The public API must support bounded grant list/create/revoke semantics, normalized tool/path/command scope, revision or compare-and-set protection, expiry where applicable, and audit attribution. Simultaneous responses follow the same first-valid-response-wins rule as AskUser. Abort, timeout, run termination and crash recovery close each pending request exactly once with a typed reason; all clients remove the stale prompt from the resulting event/snapshot.

#### 6. Run queue and user input queue

Keep daemon-owned FIFO serialization for same-session run starts. Add stable, idempotent input queue operations equivalent to:

- `inputs.submit({ sessionId, text, delivery: 'after_turn' | 'interrupt', clientRequestId })`;
- `inputs.list({ sessionId })`;
- `inputs.cancel(inputId, clientRequestId)`.

`interrupt` is advertised only when the engine can safely deliver it. Space must not label an after-turn enqueue as an interrupt. A retry with the same request ID returns the same accepted input instead of duplicating it.

#### 7. Credential lease for Space-started runs

Add an authenticated local contract for a client to provide a run/provider-scoped credential lease. The secret:

- travels only over the authenticated local transport;
- is kept in daemon memory, never status, event payload, journal, log, diagnostic export or disk;
- is bound to the provider, initiating run/request and stable initiating `clientId` rather than one ephemeral `instanceId`;
- survives the initiating client disconnect once bound to an accepted queued/active run, so detaching Space does not break daemon ownership;
- exposes `expiresAt` and a renewal operation; the daemon requests renewal before expiry and does not begin a provider call without the configured safety window;
- enters a typed `waiting_credential` run phase if an accepted queued/active run reaches expiry before renewal, then fails after a bounded wait instead of silently changing credential sources;
- is zeroed/dropped on terminal state, cancellation or final expiry; an unbound lease is dropped on disconnect;
- cannot be requested back by any client.

CLI-started runs may continue to use daemon environment/config credentials. A Space-started run with no valid credential source or a lease too short for the configured minimum queue window fails before it enters the run queue. Disconnect alone neither revokes nor renews a bound lease. Long-queue, expiry-before-provider-call, renewal-from-reconnected Space and no-renewal timeout are required fixtures.

`credential.renewal_requested` and the live snapshot expose only a non-secret `leaseId`, run/provider scope and deadline. A reconnected Space proves the same stable `clientId`, obtains the replacement secret again from its OS keychain, and replaces the lease for that exact run/provider; it never reads the prior secret. A different stable client ID cannot renew or replace the lease in F121. Space process restart is therefore recoverable, while loss of the Space keychain value ends in the typed wait/timeout path.

#### 8. Generic host-tool reverse RPC

KodaX does not need to adopt the Space Artifact product model. It needs a generic, bounded host-tool transport:

- a client registers versioned tool descriptors and receives opaque binding IDs;
- a run started by that client explicitly selects allowed binding IDs;
- daemon injects trusted session/run/turn/tool-call/client context;
- the model cannot supply or widen that authority;
- requests and results have size, timeout, cancellation and schema limits;
- every call has an idempotency key derived from `runId + toolCallId + bindingId`, and the host may reconcile a known result by that key;
- a reconnected instance with the same registered stable `clientId` may advertise a read-only prior-result lookup by idempotency key; this cannot resume the old binding or execute the tool;
- disconnect fails the call closed, and a possibly executed host tool is never automatically replayed. If reconciliation cannot prove the result, the outcome is `unknown`.

Space binds `create_artifact`, Office artifact delivery, and eligible F120 Space Control tools only to Space-started Coder runs. A CLI-started run never inherits Space tools merely because Space later attaches. Partner keeps direct in-process tool registration.

#### 9. Concurrency and idempotency

Session settings and shared configuration mutations require a revision plus `expectedRevision`. Conflict returns the current revision and sanitized current value; last-writer-wins is not acceptable for multi-client settings.

Every mutating client operation has a bounded idempotency lifetime advertised by capability. During that lifetime, retrying the same token returns the recorded outcome; after expiry it returns a typed expired/known-outcome result and never executes an ambiguous non-idempotent mutation as new work. A daemon-signed request epoch is one acceptable implementation, not a required internal design. F121 requires an advertised lifetime of at least 15 minutes and exercises the boundary with a fake clock.

Daemon and emergency inline Coder must satisfy cross-process mutual exclusion for the Coder profile across their full owner lifetimes. An atomic `coder-profile-owner` lease containing owner kind/runtime identity/heartbeat is one acceptable implementation. Observable requirements are that daemon auto-start refuses while verified inline rollback owns Coder, inline rollback refuses while daemon or unverifiable stale ownership exists, and Partner never contends for the Coder owner domain.

#### 10. Explicit administrative preflight

Operational rollback needs one authenticated, atomic answer to “can this exact daemon stop without abandoning work or another client?” The published boundary must report current runtime/owner identity, active/queued work, pending interactions, live host bindings and other attached clients, then conditionally stop only if that short-lived preflight is still current and all counts remain zero. Normal client close never invokes this operation. API naming and owner-lock mechanics remain upstream choices.

### Space architecture and data flow

#### Surface runtime router

Replace the single mixed adapter role with an explicit trusted router:

```text
SurfaceRuntimeRouter
  ├─ surface=code    -> CoderDaemonAdapter
  └─ surface=partner -> PartnerInlineAdapter
```

The renderer cannot choose a Runtime endpoint, profile, adapter class, client identity, credential lease, host-tool binding or trusted surface. Electron main derives them from the live session record.

`CoderDaemonAdapter` owns connection lifecycle, capability negotiation, observe/replay, command routing and sanitized Runtime-to-Space projection. It does not keep a private active-run map as truth.

`PartnerInlineAdapter` retains the current Partner creation and callbacks. It must reject Coder sessions and must not mutate daemon-owned Coder runs, Coder permission grants or global Runtime configuration.

The base profile has an explicit state-domain map:

| Profile store                                                            | Writer in F121                                                                         |
| ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| Coder session files and Coder session settings                           | Daemon only                                                                            |
| Partner session files and Partner session settings                       | Partner inline owner only                                                              |
| Shared session directory enumeration                                     | Read-only in both; no mutable global index may be written by the Partner owner         |
| Coder Runtime config/provider/model defaults                             | Daemon CAS service only                                                                |
| Partner provider/model/tool-policy effective config                      | Space-owned Partner config snapshot; Partner inline owner only                         |
| Coder permission grants, run journal, live projection and dedupe records | Daemon only                                                                            |
| Partner policy/grants, KB, deliveries and Artifact state                 | Space-owned files under the Space namespace only                                       |
| Partner inline diagnostic journal/cache                                  | A Partner-specific Space runtime namespace, never the daemon profile runtime directory |

This table describes normal shared mode. In emergency rollback, only the Coder rows temporarily change writer from daemon to verified inline Coder after exclusive ownership transfers; Partner rows and ownership do not change.

The shared session directory needs an enforceable surface partition, not only a renderer filter. Existing persisted tags are the migration discriminator: `partner` remains Partner-owned, `code` is Coder-owned, and historical sessions with no surface tag retain the existing deterministic classification as Coder. A persisted session cannot be retagged between `code` and `partner`; the only permitted promotion in F121 is the dedicated Space-ephemeral Coder tag to `code`.

Before default-on, the published Runtime boundary must provide an equivalent server-enforced admission rule so a CLI or other daemon client cannot start, resume, fork, delete, retag or change settings on a Partner-owned session. `PartnerInlineAdapter` applies the inverse guard and rejects every non-Partner session. Read-only enumeration may still discover both record kinds for Space navigation, but neither owner may mutate the other's record. Exact tag/namespace/lease mechanics belong to KodaX; the observable cross-owner rejection and legacy classification are the release requirements.

F121 keeps the existing shared session directory so Partner data does not migrate. Therefore KodaX must publish and test the observable guarantee that concurrent Coder/Partner owners cannot corrupt enumeration, require either owner to mutate a cross-session global record, or write another session domain. Atomic per-session files with read-only enumeration are one acceptable implementation, not a prescribed design. If the guarantee cannot be made, F121 is blocked and a separate reviewed storage-migration design is required; it does not silently choose a second directory. Concurrent fixtures are evidence, not a substitute for ownership.

Before enabling daemon by default, Space seeds a versioned `PartnerEffectiveConfigSnapshot` under its Partner namespace from the current working Partner/provider configuration. Partner reads this snapshot and Space keychain directly; it never needs a live daemon read to start or continue. Partner-specific provider/model/tool-policy changes update that Space-owned snapshot atomically. Coder/global Runtime changes go through daemon CAS. When one Settings gesture intentionally targets both domains, Space performs two named writes and reports partial success instead of pretending they are one transaction. If daemon is unavailable/incompatible, Coder/global controls are disabled, while Partner can still read and update its own snapshot. A stale/corrupt Partner snapshot fails with a Partner-specific recovery flow and never promotes itself to Coder config truth.

#### Join and reconnect flow

```text
1. Space main authenticates and negotiates capabilities with the profile daemon.
2. Space opens observeSession(sessionId, lastCursor?) and immediately buffers events after cursor C.
3. Daemon returns the live snapshot, terminal summary and immutable transcript revision at C.
4. Space loads exactly that transcript revision while continuing to buffer post-C events.
5. Space atomically replaces transcript/live projection, then applies buffered and later events by cursor/event ID.
6. If revision or cursor is unavailable/mismatched, Space discards the partial join and restarts from a fresh observation.
7. Renderer receives bounded zod SessionEvent/projection updates.
```

Space uses `observeProfile` for the low-volume global session/run/interaction lifecycle and `observeSession` for the selected Coder session. Both start from atomic snapshots and cursors. Switching sessions changes the rich observation but does not lose global completion or prompt notifications.

The Space IPC event/projection schema must carry at least `eventId`, `seq`, `occurredAt`, `runId`, optional `turnId`, and sanitized `initiatedBy`. Terminal projection is idempotent by run ID and appears exactly once.

#### Spinner and Todo semantics

Spinner animation frames are not synchronized. All clients receive the same semantic facts:

- run phase and `startedAt`;
- current assistant/thinking phase;
- active tool name and start time;
- managed-task phase/active worker;
- current Todo items and `activeForm`.

Each client renders its own CSS animation and computes elapsed time from the daemon timestamp. Reconnecting in the middle of a run immediately restores the correct semantic label and approximate elapsed duration.

Todo is a full current-state projection in the live snapshot, then replaced or patched by typed Todo events. Space must not depend on replaying the entire run to recover an in-memory Todo store.

### Space-owned implementation design

This section is the normative design for changes in the KodaX Space repository. Upstream contract examples above may change shape; the Space ownership split, renderer behavior, migration safety and release gates below do not.

| --------------------------- | ------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |

| Space tools                 | Artifact and F120 tools are registered directly in the inline SDK process                                     | Partner keeps direct registration; Space-started Coder runs receive explicit host bindings                             |
| Workflow/MCP/External Agent | Space controllers/managers bridge process-local Coder execution                                               | Coder routes use daemon/public host-provider contracts; Partner/local product stores retain only their named ownership |
| Shutdown/rollback           | Closing the inline Runtime stops its owned work                                                               | Normal close detaches Space from daemon; emergency inline rollback uses the shared Coder owner lease before startup    |

#### Main-process component split

Create a dedicated `apps/desktop/electron/kodax/runtime/` boundary:

```text
runtime/

  coder-daemon-adapter.ts
  partner-inline-adapter.ts
  runtime-projection-controller.ts
  runtime-client-identity.ts
  coder-interaction-bridge.ts
  credential-lease-broker.ts
  space-host-tool-provider.ts
  partner-effective-config-store.ts
```

Responsibilities:

- `SurfaceRuntimeRouter` resolves the trusted surface from the main-owned session record. Renderer/model input cannot select an adapter. It exposes product commands to `KodaXHost`/IPC without forcing the Coder and Partner adapters into a false lowest-common-denominator interface.
- `CoderDaemonAdapter` owns attach/auto-start, handshake, capability validation, Coder session/run commands, settings revisions, queue commands and detach. It never stores a local active run as authoritative state.
- `PartnerInlineAdapter` wraps the existing inline session factory, Partner profile/tool/policy bindings and Partner brokers. It rejects `surface='code'` except while the explicit emergency rollback owner is selected before startup.
- `RuntimeProjectionController` owns the daemon profile observation, selected-session rich observation, consistent transcript join, event deduplication, reconnect state machine and bounded main-process projection cache.
- `RuntimeClientIdentity` persists Space's stable client registration in the approved current-user store and creates a new process `instanceId`; neither value is accepted from renderer IPC.
- `CoderInteractionBridge` converts daemon-owned pending AskUser/permission projections into the existing bounded renderer prompt channels and routes replies back to daemon with first-result/conflict handling.
- `CredentialLeaseBroker` is main-only. It reads the existing keychain, supplies or renews the daemon credential capability and exposes only redacted lease state to diagnostics/UI.
- `SpaceHostToolProvider` registers reviewed Space tool descriptors, validates daemon-injected context and dispatches into the existing Artifact/Office/F120 services.
- `PartnerEffectiveConfigStore` owns the versioned Partner snapshot and migration described above; it is not a second Coder Runtime config store.

The existing `runtime-host-adapter.ts` becomes a temporary compatibility facade during the migration. Once all callers use `SurfaceRuntimeRouter`, it either re-exports the router for one stabilization release or is removed. It must not remain a second Runtime owner. `real-session.ts` remains the Partner/explicit rollback implementation and stops being the normal Coder execution path.

`KodaXHost` remains the Space session registry and merged product projection, but delegates every Coder mutation/read to `CoderDaemonAdapter`. Its local `sessions` map may contain Partner live objects and bounded Coder metadata handles; it may not contain the authoritative Coder run, queue, Todo, permission or AskUser state.

#### Space startup, attach and shutdown

Startup order is fixed:

1. Resolve Space home/profile and establish the stable Space client identity.
2. Load/migrate `PartnerEffectiveConfigSnapshot` before any Partner session starts.
3. Create `PartnerInlineAdapter` without acquiring the Coder owner lease.
4. Create `CoderDaemonAdapter` for the fixed local profile and negotiate all F121 capability versions.
5. Start the profile observation and build the first sanitized `SpaceRuntimeProfileProjection`.
6. Register Space host-tool descriptors and credential-provider capability, but do not bind either to an existing/foreign run.
7. Mark Coder ready only after the profile snapshot and no-gap stream are established; create the renderer window with a truthful connecting/ready/incompatible/degraded state.

When daemon is unavailable or incompatible, Space keeps Coder visible but disabled with actionable diagnostics. Partner continues to load and run from its own snapshot and inline owner. Space never starts inline Coder as an automatic fallback.

Normal application shutdown performs:

1. stop accepting new renderer Coder commands;
2. close rich/profile observations and reject pending local IPC waits;
3. detach the daemon client without calling daemon stop or aborting foreign runs;
4. close Partner inline sessions through their current deterministic disposal path;
5. flush only Space-owned caches/config/artifact records.

Emergency rollback is a separate pre-start path governed by the `coder-profile-owner` procedure. It is not reachable from a failed send/reconnect handler.

#### Rollback preflight and Space entry

Rollback is exposed only as an internal diagnostics/startup recovery action, requires explicit confirmation and schedules the owner change for an application restart. Renderer never sends a raw stop/lease request.

Before offering the action, main requests an atomic administrative preflight with at least: current `runtimeId`, owner state, active and queued run counts, pending interaction count, live host-binding count, and attached-client count excluding the requesting Space instance. The result is revisioned/short-lived. The authenticated stop request carries the expected runtime/preflight identity and succeeds only if every work count and other-client count is zero at commit time. Space then verifies that the daemon endpoint and Coder ownership have been released before restart-time inline acquisition. Any changed count, stale runtime, unverifiable owner or failed verification refuses rollback.

These are observable admin semantics; KodaX may choose its public API shape. `space.version` and diagnostics expose the redacted preflight/last refusal reason. Human and automated rollback tests use this Space entry, not direct file deletion or process killing.

#### Main-owned projection and subscription policy

`RuntimeProjectionController` maintains two observation tiers:

- one always-on, low-volume profile projection for connection state, sessions, active/queued runs, terminal summaries, pending interactions and durable notifications;
- one rich selected-session projection for transcript revision, assistant/thinking draft, active tools, Todo, managed-task state and queued inputs.

Changing the selected Coder session closes the prior rich observation only after the new observation has acquired its snapshot/cursor and buffered later events. Background sessions remain visible through the profile projection; reopening one obtains a new consistent transcript/live join rather than relying on an old renderer buffer.

The main cache is bounded and disposable. It may retain the selected session plus a small recent-session LRU for renderer reload speed, but daemon remains the source of truth. No projection cache is written as a competing Runtime journal. On reconnect or cursor reset, a fresh daemon snapshot replaces the affected cache atomically.

The connection state exposed to UI is one of:

```ts
type SpaceCoderConnectionState =
  | 'connecting'
  | 'ready'
  | 'reconnecting'
  | 'degraded'
  | 'incompatible'
  | 'disconnected';
```

Connection state and per-command availability are separate projections:

| Connection state | Observation/UI rule                                                                        | Mutation rule                                                                                 |
| ---------------- | ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| `connecting`     | Show last data as stale, start no join until handshake completes                           | Disabled                                                                                      |
| `ready`          | Snapshot/events are current                                                                | Enabled only for commands whose capability and target state allow them                        |
| `reconnecting`   | Freeze last projection and label it stale                                                  | Disabled until cursor/idempotency reconciliation completes                                    |
| `degraded`       | Connection is alive but one or more subservices are unavailable; show named route failures | Each command uses an explicit `available`/reason fact; unaffected commands may remain enabled |
| `incompatible`   | Do not consume unrecognized projection/protocol                                            | Disabled; upgrade/restart action only                                                         |
| `disconnected`   | No daemon connection and no claim that cached state is current                             | Disabled; retry/diagnostics action only                                                       |

Missing release-critical capabilities at startup make Coder `incompatible`, not partially shipped. `degraded` is reserved for a negotiated route that becomes temporarily unhealthy after attach. A possibly accepted mutation that lost its response remains `reconciling`/unavailable until its idempotent outcome is known.

#### Space IPC schema migration

Renderer continues to communicate only with Electron main. Raw `KodaXRuntime`, subscriptions, credentials, errors and unrestricted event payloads never cross preload.

Add the following Space-owned IPC projections in `packages/space-ipc-schema`:

| Channel                     | Direction      | Purpose                                                                            |
| --------------------------- | -------------- | ---------------------------------------------------------------------------------- |
| `runtime.profileSnapshot`   | invoke         | Current sanitized connection/profile/session/run/interaction projection            |
| `runtime.profileChanged`    | push           | Low-volume replacement/patch with Runtime cursor and projection revision           |
| `runtime.connectionChanged` | push           | Connecting/reconnecting/ready/degraded/incompatible transition and redacted reason |
| `session.liveSnapshot`      | invoke         | Selected Coder session current live projection at a Runtime cursor                 |
| `session.liveChanged`       | push           | Selected-session projection replacement/patch after join/reconnect                 |
| `session.event`             | push, existing | Transcript/display events with normalized source and correlation metadata          |

New DTOs live in a new `packages/space-ipc-schema/src/channels/runtime.ts`; existing `session.ts`, `queue.ts`, `ask-user.ts`, `permission.ts` and `version.ts` import the shared correlation/connection schemas rather than duplicating them.

`runtime.profileChanged` sends a full bounded replacement because it is low-volume. `session.liveChanged` sends typed domain changes (`run`, `draft`, `tools`, `todos`, `managedTask`, `queue`, `terminal`) with `baseProjectionRevision`, `projectionRevision` and Runtime cursor. Renderer applies a change only when its local revision matches the base; otherwise it requests a fresh `session.liveSnapshot`. Transcript text deltas continue through `session.event` and are correlated with the same Runtime event ID/cursor.

Every `session.event` has a Space envelope source:

```ts
type SpaceSessionEventSource = 'coder-runtime' | 'partner-inline' | 'space-local';

interface SpaceEventCorrelation {
  source: SpaceSessionEventSource;
  localEventId: string;
  occurredAt: number;
  runtimeId?: string;
  runtimeEventId?: string;
  runtimeSeq?: number;
  runId?: string;
  turnId?: string;
  initiatedBy?: SpaceRuntimeInitiator;
}
```

For `source='coder-runtime'`, Runtime ID/event ID/sequence/run ID are required by schema refinement. Partner/local events use a main-generated `localEventId` and never fabricate Runtime sequence values. Main drops duplicate Runtime events before push; renderer also performs bounded ID deduplication to tolerate reload/batch overlap.

`session.send` keeps its existing fire-and-accept product behavior but returns the authoritative daemon `runId` or queued input/run ID plus effective delivery mode. Routing is atomic at the daemon boundary:

| Projected state when daemon accepts    | User intent          | Authoritative outcome                                                                                                   |
| -------------------------------------- | -------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| No active run                          | normal send          | Start now and return `runId`                                                                                            |
| Active run                             | `interrupt`          | Create daemon queued input for the next safe interrupt drain; return `inputId`/effective mode                           |
| Active run                             | `after-turn`         | Create daemon after-turn input; return `inputId`/position                                                               |
| Start already queued by another client | normal new start API | Queue the run FIFO and return `runId`/position                                                                          |
| State changed during request           | any                  | Daemon chooses exactly one outcome atomically and returns it; Space never reclassifies or retries as a different intent |

For Coder, `session.cancel` includes main's `expectedRunId` and asks daemon to abort only if that run is still current. `no_active_run`, `run_changed` and an accepted abort are distinct results; renderer does not choose an arbitrary run ID. Partner retains its current cancel shape behind the router. Setting mutations carry the current Space projection revision; main translates it to the upstream CAS contract and returns a structured conflict projection.

Space normalizes daemon states before IPC. Run phase is one of `queued | starting | running | waiting_permission | waiting_user_input | waiting_credential | cancelling | completed | cancelled | failed | interrupted`; queued input is `queued | delivering | delivered | cancelled | failed`; interaction is `pending | resolved | dismissed | expired`. Unknown future values fail schema/capability negotiation rather than being rendered as idle.

The existing AskUser/permission modal channels remain for UI compatibility. Main records the trusted request ID/surface/run mapping. `askUser.reply` and `permission.answer` accept only the bounded answer/decision; main derives daemon vs Partner routing. A stale/conflicting reply closes the local modal from the latest profile projection and does not surface as a generic IPC crash.

Coder queue projections become session-scoped and daemon-derived. Current `kodax.queueGet`/`kodax.queueChanged` payloads add trusted `sessionId`, source, stable queue ID, state, delivery mode, creation time and initiator. Partner keeps its existing queue source. The renderer cannot combine two sources into one executable queue item.

`session.list` remains the full-history query but adds bounded cursor/page semantics for Coder. The profile projection contains only the bounded recent/active working set; renderer search/load requests additional pages instead of widening the always-on push.

`space.version`/capability diagnostics add separate rows for Coder daemon connection, live observe, user input, permission grants, queue, credential provider, host tools, Workflow, MCP and External Agent parity, plus one independent `partner.inline` row. A missing Coder capability must not mark Partner unavailable.

#### Quick Ask, ephemeral sessions and handoff compatibility

Quick Ask is a Coder entry point, so its temporary plan-mode session follows the same daemon route as the main Coder panel. It must not silently re-enter `RealSession` merely because its UI is transient.

- opening Quick Ask creates a daemon-owned hidden/ephemeral Coder session tagged with the stable Space client ID and a Quick Ask purpose marker;
- the session remains `mode=plan`; mutating Space host tools are not bound, and any safe tool exposure follows the existing Quick Ask policy rather than the normal Coder-panel binding;
- closing the popover requests abort when needed and best-effort archival/deletion through the public daemon contract; it never stops the daemon or deletes Runtime files directly;
- **Continue in Coder** atomically promotes/retags the same daemon session and opens it in the main panel. Space does not clone or replay the transcript, so session/run identity and event cursors remain intact;
- after an abnormal Space exit, the next start may clean stale Space-owned Quick Ask sessions only when daemon facts prove that no run is active. A bounded daemon-side expiry is preferred when advertised; cleanup failure is diagnostic, not permission to edit Runtime storage.

Default-on therefore requires public ephemeral create, promote/retag and safe cleanup semantics. Until those capabilities are negotiated, Quick Ask is disabled for the daemon slice with a truthful reason; it is not routed to inline Coder as a hidden fallback.

The existing filesystem handoff inbox remains a compatibility discovery mechanism, not a transfer of Runtime ownership. Opening a handoff resolves and attaches the referenced daemon session, deduplicates it against the current profile projection, and removes the handoff record only after successful attachment. If the same session is already visible through daemon observation, Space opens that canonical session rather than importing a second copy.

#### Credential integration in Space

`CredentialLeaseBroker` reuses `providers/keychain.ts` and provider catalog resolution. Renderer never supplies a credential to a run. For a Space-started Coder run, main:

1. resolves provider/model and verifies a supported credential source;
2. reads the secret inside main;
3. establishes the upstream scoped credential capability before submitting the run;
4. stores only the redacted lease ID/deadline/run/provider mapping in memory;
5. handles renewal requests by re-reading keychain for the same stable Space client;
6. clears local mapping on terminal/cancel/final expiry.

If credential setup fails, `session.send` rejects before a run or queue entry is accepted. If renewal later fails, UI renders the daemon's waiting/failure state; Space does not inject a different provider secret or restart the run.

Existing environment injection may remain for Partner/legacy compatibility during one release, but Coder daemon correctness must not depend on Electron main `process.env`. Diagnostics tests scan both Space logs and exported bundles for credential fixtures.

#### Legacy state removal and compatibility

Remove from the normal Coder path after its replacement passes parity:

- `RuntimeHostAdapter.startingSessions` and `activeRuns` as run truth;
- Coder callback translation as the only event publisher;
- Space-owned Coder after-turn queue and in-process interrupt drain;
- Coder entries in the current AskUser/permission pending callback brokers;
- event-history inference as the source for Coder spinner/Todo/managed-task/running state;
- Coder credential dependence on Electron main environment injection;
- direct in-process registration of Space tools for Coder;
- mid-run or reconnect fallback to legacy/inline Coder.

Retain:

- Partner inline session objects and callback translation;
- Partner AskUser/permission/queue semantics;
- Space-owned Artifact, KB, delivery, policy, diagnostics and UI stores;
- renderer-facing compatibility selectors where they reduce component churn, provided they read the new projection for Coder;
- an internal pre-start rollback selector for one stabilization release, protected by the shared Coder owner lease.

During migration, a Coder Runtime event is published to renderer through exactly one path. Contract tests fail if the callback bridge and daemon observer both publish the same run/turn/tool/terminal fact.

### Interaction and conflict rules

| Situation                                   | Rule                                                                                                                                             |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Two clients start a run on the same session | Daemon serializes starts FIFO and reports queued position/state                                                                                  |
| Two clients answer AskUser                  | First valid atomic response wins; the other receives resolved/conflict and closes stale UI                                                       |
| Two clients answer permission               | Same first-valid-response-wins behavior; persistent grant creation is idempotent                                                                 |
| One client aborts a run                     | Daemon aborts that run; every client observes the same terminal event                                                                            |
| Two clients edit settings                   | Revision mismatch returns conflict; UI reloads and asks the user to retry if needed                                                              |
| Client retries after transport uncertainty  | Same valid request token returns the recorded outcome; expired token returns proven durable outcome or `request_id_expired`, never new execution |
| Space attaches to a CLI-started run         | Observe/control only; no dynamic Space host-tool injection                                                                                       |
| Space closes                                | Coder continues in daemon; Partner inline run follows existing Space shutdown behavior                                                           |

### Artifact boundary

Space Artifact remains Space-owned:

- storage, versions, preview, export and Artifact UI do not move into KodaX Runtime;
- Runtime's current input artifact handles are not treated as the Space output Artifact store;
- only a Space-started Coder run with an explicit host-tool binding can create or revise a Space Artifact;
- a CLI-started Coder run can still be observed in Space but has no Space Artifact tool;
- the Artifact store records `runId + toolCallId + bindingId` with the created version, so an ambiguous host result can be reconciled without creating a duplicate version;
- after Space reconnect, the same stable Space client can answer the daemon's read-only result query from that profile-scoped record; absence returns `unknown`, never a new Artifact write;
- Space disconnect during a host-tool request returns a bounded failure/unknown result and does not replay the call;
- F121 assumes the existing single active Space application instance per Space profile. The profile-scoped Artifact store, not the daemon, publishes Artifact UI updates; support for two concurrent Space Artifact writers is a separate feature;
- Partner artifact behavior is unchanged because Partner stays inline.

### Workflow, MCP and External Agent boundary

These capabilities must have one truthful owner in shared mode:

- Coder Workflow state is daemon-owned. Release parity requires stop reason, terminal uniqueness, durable origin/resume metadata, result/evidence query and Space projection parity. F121 does not claim crash replay of side-effectful workflow work.
- Coder MCP execution/catalog is daemon-owned when shared mode uses MCP tools. Space may keep administration UI and diagnostics only after public lifecycle/log contracts prevent a second process manager.
- Runtime External Agent factories currently cannot be injected into an already-running daemon. Released Reference External Agent actions require a daemon-loadable provider or a separately reviewed bounded host-provider contract; they must not escape to inline Coder.
- Memory and Learning UI consume only daemon-advertised contracts and do not create parallel stores.

Workflow, MCP and every released Coder External Agent action are `v0.1.32` release gates. Already unavailable/experimental Memory and Learning actions stay governed by their existing capability gates. None of these are reasons to migrate Partner.

### Security and permission boundary

- Transport is local-only: Windows named pipe or Unix domain socket, authenticated by daemon state/token restricted to the current OS user.
- No public TCP listener, remote collaboration, account sharing or cross-user access is introduced.
- Renderer accesses Runtime only through existing bounded zod IPC.
- Model output cannot select client identity, session authority, profile, endpoint, credential, permission answer or host-tool binding.
- Host-tool trusted context is injected by daemon and revalidated by Space main.
- Event/draft/tool content forwarded to renderer is schema-validated, bounded and sanitized.
- Capability versions fail closed. Unknown or incompatible protocol versions do not silently fall back to another owner.
- Credential material is redacted before every log/event/diagnostic sink and never persisted by the lease service.
- Permission grants and AskUser answers record safe client attribution without storing secrets or unnecessary prompt/document bodies.

F121's trust principal is the current OS user. It does not claim isolation from another malicious process already running as that user; such a process can access the same local files and daemon token. Within that boundary, the server applies this operation policy rather than trusting `clientInfo.name`:

| Operation                                                                    | Admission rule                                                                                                                                                                                     |
| ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Observe session/profile, start/abort, queue input, answer AskUser/permission | Authenticated same-user daemon connection plus valid target/session capability                                                                                                                     |
| Change session/config settings or persistent grants                          | Same as above, plus revision/CAS and bounded schema/scope policy                                                                                                                                   |
| Provide/renew credential                                                     | Authenticated connection with negotiated credential-provider capability and the lease's stable `clientId`; a new `instanceId` may renew with a replacement secret but can never read the old lease |
| Register/invoke host tool                                                    | Registering connection owns the binding; run explicitly binds it; invocation carries daemon-derived context                                                                                        |
| Stop/restart daemon                                                          | Separate explicit administrative method/CLI flow; never implied by normal client `close()`                                                                                                         |

Wrong token/OS identity, missing capability, cross-profile target, cross-session request, another stable client's lease, another connection's live host binding, renderer-direct request and model-supplied authority all fail before mutation. These negative cases are release tests.

### Compatibility and migration

- Existing Coder and Partner session transcript formats remain KodaX-owned; F121 adds no second transcript database.
- `v0.1.31` remains the historical inline migration record and is not rewritten.
- The app may keep an internal Coder inline rollback selector for one stabilization release, but selection happens before daemon attachment or any Coder mutation and requires an app restart.
- Once shared mode is selected for a profile, Space never opens an inline Coder owner against that same profile, never falls back mid-run, and never replays a failed start/tool on inline.
- Operational rollback first blocks new starts, requires zero active/queued runs and pending interactions, refuses while another client remains attached, performs the explicit authenticated daemon stop, and verifies the owner lock/endpoint is gone. Inline Coder then atomically acquires and holds the shared `coder-profile-owner` lease before opening the profile; later terminal/SDK daemon auto-start attempts receive an owner-conflict result until inline Space exits. If any precondition or lease acquisition cannot be proved, rollback is refused rather than creating two owners.
- Partner always selects inline independently of the Coder rollout switch.
- If daemon protocol/capabilities are incompatible, Space exposes an upgrade/restart/degraded message. It does not pretend the session is idle.
- Closing the Runtime client detaches Space only. Daemon stop remains an explicit authenticated administrative operation.

### Failure and recovery rules

For every accepted durable mutation, a post-crash client must observe one coherent result: the durable object, dedupe outcome, live projection and journal cannot disagree in a way that permits duplicate execution. KodaX may implement this with a transaction, journal reconciliation or another mechanism; F121 tests only the observable atomicity. Credential secrets and live host bindings are deliberately excluded from persistence and are never replay candidates. On startup, the daemon reconciles every nonterminal durable record before accepting clients:

- a previously active run becomes one terminal `interrupted` record with reason `daemon_restart`; it is never resumed automatically;
- a queued-but-not-started run and queued user input become `cancelled` with reason `daemon_restart_before_start`;
- pending AskUser and permission requests become `dismissed`/`cancelled` with reason `daemon_restart`;
- in-memory credential leases and host bindings are lost and cannot be reconstructed from disk;
- durable request IDs remain attached to their run/queue/response/settings records so a retry cannot duplicate an accepted mutation;
- the new daemon has a new `runtimeId`; an old `{ runtimeId, seq }` cursor returns `cursor_reset`, after which clients consume the recovered terminal/profile snapshot from the new runtime namespace.

Recovery terminal materialization completes before the daemon reports ready. If durable evidence cannot determine whether an external provider/host side effect occurred, the run/tool receipt is explicitly `unknown`; KodaX still does not replay it.

| Failure                          | Required behavior                                                                                      |
| -------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Space renderer reload            | Main keeps daemon connection; renderer reloads a sanitized current snapshot                            |
| Space main exits/crashes         | Coder daemon/run continues; reconnect performs snapshot plus cursor reconciliation                     |
| Daemon connection drops          | Freeze controls, show reconnecting/degraded state, reconnect explicitly, then observe from last cursor |
| Replay cursor expired            | Reload transcript and fresh live snapshot; do not replay side effects                                  |
| Daemon process crashes           | Apply the deterministic reconciliation above; never auto-resume or requeue work                        |
| Host-tool client disappears      | Fail pending call closed; do not rebind or replay it on another Space instance                         |
| Credential lease missing/expired | Reject before start or fail the provider operation with a typed credential error; never log the secret |
| Partner run while daemon fails   | Partner continues on its independent inline owner unless Space itself exits                            |
| Protocol/profile mismatch        | Refuse attach with actionable diagnostics; never connect to a different profile opportunistically      |

### Explicit non-goals

- No Partner daemon migration or Partner transport protocol.
- No shared Partner state between Space instances.
- No migration of Space Artifact storage into KodaX.
- No synchronization of spinner frames, React state or window layout.
- No dynamic Space-tool injection into a run started by another client.
- No public remote daemon, cloud relay or multi-user collaboration.
- No automatic replay/resume after daemon, tool-host or transport failure.
- No second Coder session, Todo, permission, workflow, MCP, memory or agent-task truth in Space.
- No user preference that allows arbitrary Runtime endpoints or mixes inline and daemon Coder owners in one profile.

### Limits and measurable convergence

Space clamps daemon data to explicit IPC limits; it never forwards an upstream “unbounded” collection or payload. F121 starts from the existing schema caps and adds the new projection caps below:

| Boundary                                 | Space hard cap / behavior                                                                                                                  |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| User prompt                              | 1 MiB, existing `session.ts` cap                                                                                                           |
| Text/thinking delta or draft field       | 256 KiB per field, existing cap                                                                                                            |
| Tool result content                      | 512 KiB per field, existing cap                                                                                                            |
| Queue projection                         | 500 entries per session/source; overflow is a typed degraded/error state, not silent truncation of actionable entries                      |
| Profile projection                       | 500 most-recent idle/terminal summaries plus all active/queued/pending references up to their caps; full history uses paged `session.list` |
| Pending permission or AskUser projection | 500 each; overflow disables new starts and reports a typed capacity failure                                                                |
| Todo / active tools                      | 1,000 Todo items and 128 active tools per session; upstream overflow fails validation and marks that live projection degraded              |
| Main recent-session cache                | Selected rich session plus at most five completed/recent rich projections; eviction never affects daemon truth                             |

Upstream replay retention, idempotency lifetime, host-call timeout, credential lease windows and page sizes are advertised by capability and shown in diagnostics. Space uses the lower of its hard cap and the advertised limit. Default-on requires at least the 15-minute idempotency lifetime above; 14:59 is an incompatibility fixture, 15:00 is the minimum passing fixture. Replay may instead return a typed cursor reset with a complete replacement snapshot, so replay retention is not conflated with idempotency retention.

“No gap” means contiguous Runtime sequence/event IDs after the snapshot cursor or an explicit cursor-reset replacement—never inferred silence. “Converged” means the main projection is identical after normalization and the renderer applies it within one push/reducer cycle; Electron E2E allows two seconds after the local fixture emits/acknowledges an event. Spinner elapsed time is derived from daemon `startedAt` and must be within two seconds of the fixture clock after attach. “Partner regression” means the frozen Partner `v0.1.31` fixture set remains byte/semantic-equivalent for public IPC outcomes, excluding intentional diagnostic metadata additions.

### Rollout and rollback

- Begin with internal/diagnostic enablement, then observe-only, then shared control, then Space host tools, then default-on.
- Capability negotiation controls each dark-launch slice. A missing required contract disables that internal slice with a redacted reason; it does not qualify as the shipped F121 outcome.
- Rollback is an app-restart decision made before any Coder daemon mutation. It is never a mid-run failover.
- If a shared daemon already owns the selected profile, use the zero-work/zero-client explicit-stop procedure above; otherwise refuse rollback and do not start inline Coder.
- Do not mark F121 Completed or cut `v0.1.32` until shared daemon is the default Coder path and the released-action manifest, process-distinct, packaged and human acceptance gates pass.
- Partner remains inline through rollout and rollback; no Partner data migration is part of F121.

## F121 exit condition

- Shared daemon is the default Space Coder path, and a Coder run has one daemon-owned live truth observed consistently by multiple authenticated local clients.
- Space can join an already-running terminal Coder session and recover spinner semantics, Todo, tool, transcript and interaction state without restarting or duplicating work.
- Shared permission, AskUser, queue, credential and host-tool boundaries pass their conflict and security suites.
- Space Artifact remains Space-owned and Partner remains inline with no behavior regression.
- No same-profile inline Coder fallback, duplicate state owner or automatic side-effect replay remains in the shared path.
