# v0.1.40 - Partner Composer-First Skill Workspace

> Status: Planned
> Features: F130
> Revised: 2026-07-29
> F130 depends on the shipped F095/F109/F114 and F122-F124 Partner foundations, plus the existing KodaX SkillRegistry and `skill` tool contract. F129 later upgrades presentation delivery without changing this entry model.

## Batch decision

Partner will use a composer-first task entry:

- compact scene shortcuts sit directly above the composer in a new, empty session;
- there is no `Choose a work mode`, `What do you want to complete?`, or similar heading;
- there is no welcome-card or prompt-card grid;
- selecting a scene writes a useful, visible, editable prompt into the composer;
- the shortcuts remain until the first user message is accepted, then disappear for that session;
- no persistent scene mode, mode badge, outcome receipt, or mode switch is created;
- installed Skills are real Partner capabilities, available through explicit selection and Auto LLM intent matching;
- loading a Skill never grants additional authority: Partner permissions and tool policy still govern every action.

F130 does not copy WorkBuddy's Ask/Plan/Craft selector. Auto LLM and the existing permission controls remain authoritative.

From v0.1.40 onward, this file is the normative Partner task-workspace UX contract. Earlier F046/F095/F103/F114 documents remain historical implementation and data-contract records; their Partner placement, mode language, and prompt-hiding decisions do not override F130.

## FEATURE_130: Partner Composer-First Skill Workspace

### 1. Requirements

#### User outcome

Partner should feel useful before a non-technical user knows how to write a strong prompt:

> A new task offers recognizable scene shortcuts above the input box. Clicking one writes a complete example task into the input box, where the user can learn from it, replace details, attach materials, and send. Partner may then use installed Skills automatically or as explicitly selected by the user, while preserving the same permission boundary.

Free-form natural language remains a complete first-class path. Selecting a scene or a Skill is never required.

#### Scene shortcuts

The new-session row reuses the eight existing Partner scenes:

| Scene ID | `zh-CN` label | Visible prompt intent |
| --- | --- | --- |
| `document-processing` | 文档处理 | Read, transform, summarize, or create a document for a named audience |
| `finance` | 金融分析 | Analyze financial material with evidence, assumptions, and risks |
| `data-analysis` | 数据分析 | Inspect and transform data, explain findings, and produce useful files |
| `deep-research` | 深度研究 | Define the question, gather evidence, compare sources, and synthesize |
| `product-management` | 产品管理 | Clarify users, problem, scope, tradeoffs, and requested deliverable |
| `presentation` | 幻灯片 | Define audience, narrative, slide structure, and editable output |
| `design` | 设计 | Produce only a truthful supported design brief or design deliverable |
| `email-editing` | 邮件编辑 | Draft or revise an email for audience, tone, and desired action |

Layout rules:

- no heading appears above the shortcuts;
- wide layouts may show all shortcuts or the highest-value shortcuts plus `More`;
- narrow layouts use horizontal scrolling;
- the composer stays focused and usable without making a selection;
- clicking a shortcut never sends automatically or opens a wizard.

Draft replacement rules:

- when the draft is empty, insert the selected scene template;
- when the draft is still the untouched output of a previous scene selection, replace it;
- when the user has edited or independently written the draft, changing scenes must preserve that content or provide immediate undo; it must not silently destroy user text;
- attachments and explicitly selected materials survive every scene change.

#### Prompt visibility

The visible template teaches the business method:

- goal or question;
- material to use;
- intended audience;
- expected deliverable;
- important constraints, evidence needs, and success criteria.

Runtime safety rules remain internal:

- Partner identity and durable behavior;
- tool and permission policy;
- evidence integrity and citation rules;
- connector authorization;
- checkpoint, proposal, rollback, and audit contracts.

F130 removes the current pattern in which most scene-specific business guidance lives only in a hidden `partnerPromptOverlay`. The sent, editable user prompt is the task truth. A bounded internal overlay may still carry runtime context that is unsafe, noisy, or impossible to express as a user request, but it must not secretly replace the user's business request.

#### Executable Partner Skills

Partner must consume real installed KodaX Skills. This is an explicit product requirement, not future parity work.

Required entry paths:

1. **Explicit selection** - the existing Skill picker and slash completion can select an installed Skill for the current Partner task.
2. **Natural-language activation** - Partner receives a surface-scoped Skills addendum so Auto LLM can match and invoke a relevant installed Skill.
3. **Scene-assisted recommendation** - a scene template may make relevant Skills easier to match or recommend, but a scene is not itself a Skill.

Required semantics:

- the SDK `skill` tool is a capability loader that returns expanded Skill instructions;
- admitting `skill` does not admit shell, write, MCP, connector, subagent, workflow, or arbitrary mutation tools;
- every tool requested after Skill loading is independently checked by Partner tool visibility, permission, workspace, connector, checkpoint, and audit policy;
- a task may use multiple Skills in sequence;
- an explicitly selected Skill is visible and removable before send;
- automatically invoked Skills are visible in ordinary execution detail or a concise capability receipt, not as a persistent work mode;
- incompatible Skills remain discoverable with a truthful compatibility reason rather than being advertised as runnable and then failing mysteriously.

#### Skill history correction

The current exclusion is historical, not a valid product invariant:

- v0.1.27 introduced the Partner fail-closed read/research tool policy while the shared Skills prompt was still injected;
- the Partner policy rejected the SDK `skill` tool, so the model was told to invoke a capability it could not call;
- v0.1.30 fixed that contradiction by making `buildSkillsPromptForSurface('partner', ...)` return an empty string;
- v0.1.30 documents then described executable Partner Skills as future work.

That repair chose suppression instead of completing the Partner Skill authority path. F130 supersedes the suppression.

The explicit user-invocation path is already closer to the intended model: `skill.discover` and `skill.invoke` resolve a Skill and send its expanded prompt to the current session without excluding Partner. F130 must unify explicit and automatic behavior instead of maintaining two different capability stories.

#### Workspace layout

The permanent `PartnerWorkbenchPanel` and nested Partner `SourcesPanel` leave the default task layout.

The primary layout is:

1. conversation and composer in the center;
2. on-demand material/context surface;
3. Partner right rail with `Results`, `Process`, and `Files`.

The right rail preserves authoritative ownership:

- `Results` projects Artifacts, Deliveries, and Presentation Projects without merging stores or deduplicating by filename;
- `Process` projects structured run/tool/source/verification facts and never parses assistant prose to manufacture progress;
- `Files` projects proposals, checkpoints, apply/reject, reveal, and rollback without creating a duplicate file store.

### 2. Impact

#### Renderer

- replace the permanent workbench strip with a session-aware scene-shortcut row above `BottomBar`;
- keep the existing Skill picker/slash affordance available on Partner;
- write scene templates into normal composer state;
- distinguish untouched generated template text from user-edited draft state;
- hide the shortcut row after the first accepted user message;
- remove card selection, outcome-mode badges, and persistent outcome receipt UI;
- preserve shared attachment, drag/drop, long-query collapse, localization, accessibility, theme, and Coder behavior.

#### Electron main

- stop suppressing the Skills prompt solely because `surface === 'partner'`;
- admit the SDK `skill` tool through a dedicated Partner capability-loader policy;
- build a Partner-compatible Skill catalog and compatibility result;
- bind Skill dynamic-context handling to the current Partner session and permission policy;
- preserve existing session/surface/project validation on explicit Skill invocation;
- keep actual tool authorization in the existing Partner policy rather than in renderer state.

#### KodaX SDK

No new SDK API is assumed. F130 consumes existing public contracts:

- SkillRegistry discovery and full Skill loading;
- `context.skillsPrompt`;
- the `skill` tool;
- `KodaXOptions.skillDynamicContext`;
- tool visibility metadata and policy;
- AgentProfile and verification contracts.

If implementation proves one of these contracts cannot safely carry a Partner-scoped invocation, that is an explicit SDK gap and release blocker; it does not justify silently reverting to “Partner has no Skills.”

#### Documents and compatibility

- existing sessions, messages, sources, KB pages, artifacts, deliveries, proposals, checkpoints, and citations are not rewritten;
- old scenario state may seed a draft only for a truly empty legacy session and must never alter an existing transcript;
- existing explicit slash Skill invocation remains compatible;
- Coder Skill discovery, invocation, permissions, and UI remain unchanged.

### 3. Technical design

#### Scene presentation state

Scene selection is draft-local UI state, not domain state:

```ts
interface PartnerSceneDraftState {
  sessionId: string;
  sceneId?: PartnerWorkbenchScenarioId;
  generatedTemplate?: string;
  generationRevision: number;
  userEdited: boolean;
}
```

It is reset on session change. It is not persisted after the first accepted user message. The transcript and authoritative run/result stores are sufficient durable truth.

The shortcut row is shown when all are true:

```ts
surface === 'partner'
&& sessionExists
&& acceptedUserMessageCount === 0
```

An in-flight first send hides the row once main accepts the message, not after model completion. Run failure or cancellation does not recreate a “mode chooser.”

#### Partner Skill admission

Partner Skill execution has two separate gates:

1. **Load gate** - whether Partner may discover and load the Skill instructions.
2. **Action gate** - whether Partner may execute each tool requested by those instructions.

The `skill` tool passes the load gate. It does not bypass the action gate.

The Partner tool policy therefore explicitly recognizes `skill` as a capability loader. It must not classify the tool as a generic mutation, shell, workflow, or subagent capability merely because unknown tools currently fail closed to that category.

#### Compatibility projection

Skill metadata is projected for Partner with:

```ts
type PartnerSkillCompatibility =
  | { status: 'compatible' }
  | { status: 'compatible-with-approval'; reasons: readonly string[] }
  | { status: 'incompatible'; reasons: readonly string[] };

interface PartnerSkillProjection {
  name: string;
  description: string;
  source: 'project' | 'user' | 'plugin' | 'builtin' | 'learned';
  argumentHint?: string;
  compatibility: PartnerSkillCompatibility;
}
```

Compatibility is advisory presentation plus a fail-closed load check. It never grants the tools named by a Skill. Missing or inaccurate `allowed-tools` metadata cannot expand authority; the normal action gate remains final.

#### Dynamic context

Skill dynamic-context tokens such as `` !`command` `` are execution and must never use the SDK fallback `execSync` path in Partner.

F130 must provide one of these explicit outcomes per invocation:

- route the command through a Partner-aware `skillDynamicContext.execute` host policy, permission broker, audit trail, timeout, output cap, process-tree cleanup, safe environment, and validated working directory;
- set `skillDynamicContext.disable = true` and report that this Skill requires unsupported dynamic context.

Natural-language and explicit Skill invocation must use the same rule. A Skill cannot become safer or more powerful merely because it was selected through a different UI entry.

#### Skill source trust

Project, plugin, user, builtin, and learned Skills retain their source identity. Source affects trust and compatibility policy but does not replace content inspection or action authorization.

- unsafe or unverifiable Skill content fails closed;
- a disabled model-invocation Skill is not auto-invoked;
- explicit invocation returns the real reason for rejection;
- learned Skills continue to require Runtime-owner admission;
- installation remains a separate explicit user action; scene selection and automatic routing never install or enable a Skill.

#### Context and results

The `+ Add material` surface preserves distinct facts:

- available to the project;
- selected for this task;
- automatically recalled;
- actually used for this turn.

Selection never silently creates project material or curated knowledge. Result, Process, and Files projections preserve existing F109/F113/F114/F122-F124 ownership, citations, proposal, checkpoint, and rollback contracts.

### 4. Interface contracts

#### Scene template registry

```ts
interface PartnerSceneTemplate {
  sceneId: PartnerWorkbenchScenarioId;
  labelKey: MessageKey;
  promptTemplateKey: MessageKey;
  suggestedSkillNames?: readonly string[];
}
```

`suggestedSkillNames` is a hint only. Missing Skills do not break template insertion, and the hint never installs, enables, or grants a Skill.

#### Skill catalog

The existing `skill.discover` response may be extended with optional Partner compatibility, or a surface-aware catalog endpoint may project the same registry:

```ts
interface PartnerSkillCatalogInput {
  sessionId: string;
  projectRoot: string;
  surface: 'partner';
  forceReload?: boolean;
}

interface PartnerSkillCatalogOutput {
  skills: readonly PartnerSkillProjection[];
}
```

Main validates the live/resumable session, expected project root, and Partner surface. Renderer-provided compatibility or permission values are never trusted.

#### Skill invocation

Explicit and automatic invocation converge on one main-owned service:

```ts
interface PartnerSkillInvocation {
  sessionId: string;
  skillName: string;
  args?: readonly string[];
  origin: 'explicit' | 'auto';
}
```

The service:

1. validates session, surface, project root, Skill source, and model-invocation rules;
2. resolves dynamic context under Partner policy;
3. loads and expands the Skill;
4. returns or injects the resolved instructions;
5. records bounded invocation identity/status without logging prompt content, file paths, credentials, or source payloads;
6. leaves every subsequent tool decision to the normal Partner action gate.

### 5. Implementation steps

1. **Correct the Skill boundary**
   - replace the Partner-empty Skills addendum with a Partner-scoped catalog;
   - explicitly admit `skill` as a capability loader;
   - pass Partner-aware `skillDynamicContext` policy on model-side invocation;
   - add compatibility and rejection reasons.
2. **Unify explicit and automatic invocation**
   - route picker/slash and model-side invocation through the same resolver and security policy;
   - preserve the current readable slash echo while preventing expanded hidden Skill prompt text from leaking into telemetry.
3. **Replace the permanent workbench**
   - remove the permanent scenario panel from the GA Partner layout;
   - add the session-aware shortcut row immediately above the composer;
   - insert visible localized templates and track untouched-versus-edited draft state.
4. **Simplify first-send state**
   - hide shortcuts after main accepts the first user message;
   - remove outcome cards, outcome-mode persistence, task-mode badges, and mode-changing actions.
5. **Re-host material and results**
   - move ordinary material selection into the canonical `+ Add material` surface;
   - keep Results/Process/Files projections over existing authoritative owners.
6. **Regression and rollout**
   - retain a one-release Partner-only rollback flag;
   - prove Coder Skill/runtime/composer behavior is unchanged;
   - remove legacy Partner placement after packaged human acceptance.

### 6. Acceptance

#### Automated acceptance

- a new empty Partner session shows localized scene shortcuts directly above the composer with no heading and no welcome-card grid;
- clicking each shortcut writes the expected visible prompt and does not send;
- switching untouched templates replaces them; switching after user edits preserves text or provides immediate undo;
- attachments and selected materials survive every shortcut change;
- direct free-form input works without selecting a scene;
- the shortcut row disappears after the first accepted user send and remains absent after reload, run failure, cancellation, and later turns;
- no scene mode, outcome receipt, permission change, model change, tool-policy change, or connector grant is persisted;
- Partner explicit Skill selection discovers and invokes an installed test Skill;
- natural-language intent causes Partner to invoke a matching installed test Skill through the SDK `skill` tool;
- the same test Skill produces equivalent resolved instructions through explicit and automatic origins;
- loading a Skill does not make a blocked shell, write, workflow, subagent, MCP, or connector tool available;
- a compatible read/delivery Skill completes under Partner policy;
- a Skill requiring approval reports and exercises the permission path;
- an incompatible or disabled Skill remains visible with a deterministic reason and cannot auto-invoke;
- dynamic-context expansion never reaches unbrokered SDK `execSync`;
- unsafe, learned-without-admission, missing, and stale Skills fail closed with truthful errors;
- Skill invocation telemetry contains bounded identity/status only and excludes expanded prompts, source content, file paths, URLs, credentials, and connector payloads;
- Results/Process/Files preserve authoritative IDs, citations, checkpoints, proposals, and rollback;
- light/dark, keyboard, screen-reader, reduced-motion, wide/medium/narrow, and localization coverage passes;
- Coder snapshots and E2E show no deliberate change to Skill, composer, permission, Auto LLM, navigation, or Task Dock behavior.

#### Human acceptance

1. Open a new Partner task and confirm the shortcuts look like lightweight suggestions above the input, not a mode chooser.
2. Click `深度研究`; confirm a complete research prompt appears in the composer and can be freely edited.
3. Switch to `幻灯片` before editing; confirm the template changes without sending.
4. Edit the draft, attach files, then click another shortcut; confirm neither the edited text nor attachments are silently lost.
5. Start a second task by typing directly without selecting anything; confirm normal Auto LLM behavior.
6. Explicitly choose an installed document Skill in Partner and complete a governed document task.
7. Start a comparable task using only natural language; confirm Partner automatically loads the matching Skill.
8. Use a Skill that requests a Partner-blocked action; confirm loading the Skill does not widen permission and the blocked action is explained.
9. Send the first message and confirm the shortcut row disappears with no persistent scene badge or change-mode control.
10. Confirm outputs, execution state, citations, files, proposals, and rollback remain reachable through Results/Process/Files and on-demand context.

### Security and permission invariants

- scene selection changes only the composer draft;
- Skill selection changes only the loaded capability instructions;
- neither path writes `permissionMode`, `autoModeEngine`, model, effort, connector grants, retrieval scope, allowed roots, or tool policy;
- automatic routing may use only installed, discoverable, admitted Skills and already authorized tools;
- F130 never silently installs a Skill, authorizes a connector, expands filesystem scope, sends an external message, publishes content, deletes files, or starts a workflow/expert team;
- actual mutations continue through existing permission, F113 proposal, F114 checkpoint/delivery, connector, and audit owners.

### Explicit non-goals

- no Ask/Plan/Craft clone and no `smart/quick/deep` selector;
- no persistent task mode or outcome-mode database;
- no welcome-card grid or full-screen task wizard;
- no requirement to select a scene or Skill before typing;
- no separate Partner Skill format or duplicate Skill runtime;
- no bypass of Partner policy for a Skill's requested tools;
- no expert center or expert-team orchestration in F130;
- no general editable visual-canvas promise before a bounded authoring contract exists;
- no Coder redesign or deliberate Coder behavior change;
- no rewrite of F109/F113/F114/F122-F124 authoritative stores.

### Rollout and rollback

- ship behind a Partner-only `composer skill workspace` feature flag;
- qualify Partner Skill admission, shortcut entry, material access, and Results/Process/Files together;
- rollback changes the projection and Partner Skill admission only; it does not rewrite sessions or delete Skills, sources, knowledge, results, proposals, checkpoints, or citations;
- keep the old Partner workbench placement for one released rollback window, disabled by default once F130 qualifies;
- remove the legacy placement and rollback flag after packaged human acceptance.

## Release acceptance

F130 is complete only when Partner supports real installed Skills through explicit and automatic invocation under the unchanged Partner authority boundary, and when new tasks use editable composer templates instead of a work-mode selector, card grid, hidden business prompt, or persistent scene mode.
