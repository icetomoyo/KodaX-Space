## FEATURE_141: Customer-Selectable Coder Runtime Mode and Safe Restart

### 1. 需求概述

在 Settings → Runtime 中向客户展示 Coder 执行模式，并允许在以下两种模式之间切换：

- **Daemon（推荐）**：Coder 连接 profile-scoped shared Runtime daemon，保留多客户端共享、
  后台继续运行和 daemon-owned session/run truth。
- **Embedded（兼容模式）**：Coder 在 Space Electron main 内使用受 owner fence 保护的
  inline 执行路径。当 Daemon 启动、连接或能力协商异常时，客户可以用此模式继续工作。

模式切换不是 live failover。Space 必须在无活动任务时完成 owner policy 转换、持久化
Space-only 偏好并重启应用；已经接受的操作绝不在另一 owner 上自动重放。

### 2. 影响范围

- `~/.kodax/space/settings.json` 新增有版本迁移的 `coderRuntimeMode` 标量偏好；
- Settings IPC 新增封闭的 `daemon | embedded` 切换命令与重启结果；
- Electron main 在 Runtime 初始化前把持久化模式映射为现有 `runtime | legacy` host；
- `RuntimeHostAdapter` 增加仅在初始化前选择 host，以及 daemon ↔ inline owner policy
  安全转换；
- Session 读写、Slash discovery/执行、Workflow 读写与控制、Runtime External Agent
  读写与控制、MCP tool discovery/reload，以及会改变 Runtime 默认值或 integration
  配置的 Settings 操作，共用一个 main-process Coder admission gate；
- Settings → Runtime 增加双选模式卡、当前/推荐/兼容说明、安全提示和“切换并重启”操作；
- 中英文 UI、用户手册和源码启动文档同步说明故障回退路径。

Partner 始终保持现有 embedded-inline owner，不随 Coder 设置迁移。Provider、MCP、
Workflow、Artifact、权限规则和 Session 数据格式不因该开关改变。

### 3. 技术方案

Space 把面向客户的 `daemon | embedded` 映射到内部 `runtime | legacy`，但不向 renderer
暴露 daemon endpoint、token、owner revision 或 inline fence。

切换协调器会同步把 admission 从 `idle` 置为 `switching`，拒绝后续可执行 Coder 入口，
等待已进入的 Runtime 操作退出，再在关闭的 gate 下重新检查活动任务。活动范围包括
ManagedSession、running/paused Workflow、非终态 External Agent task、待处理
permission/AskUser 和尚未派发的 Coder queue。成功切换后 gate 保持关闭到自动重启；
失败且 owner 状态已安全恢复时才重新开放。Artifact、Memory、Skill prompt 解析等不接触
Runtime owner 的 Space-only lazy hydration 不需要进入该 gate。

Daemon → Embedded：

1. 拒绝仍有 Space 活动任务的切换；
2. Runtime 可用时通过 `daemon.inspect()` + `stopForInline()` 原子复核其他客户端、
   active/queued work、Workflow、Agent Turn 和 pending interaction；
3. Runtime 初始化失败时只允许通过现有安全 daemon-stop 门和 owner-state 检查继续；
4. daemon owner 释放后获取 `enableRollback` inline fence，写入偏好并安排重启；
5. 偏好写入失败时恢复 daemon owner policy；如果 daemon 恢复和 inline fence 保留都
   失败，则保持 Coder admission 关闭并安排恢复重启。

Embedded → Daemon：

1. 拒绝仍有 Space 活动任务的切换；
2. 先持久化 daemon 偏好，再释放 inline fence 并调用公开
   `enableKodaXDaemonOwner()`；
3. owner policy 转换失败时把偏好恢复为 embedded；
4. owner policy 与偏好补偿均失败时仍安排恢复重启并保持 Coder admission 关闭；
5. 成功后安排 Electron relaunch，下一进程按 daemon 模式初始化。

若进程在“写入 daemon 偏好”和“恢复 daemon owner policy”之间崩溃，下一次启动会在连接
Runtime 之前读取持久化偏好并检查 owner policy。`daemon + unowned inline policy` 会先
恢复 daemon policy；检测到仍活跃或不可读的 inline owner 时 fail closed，不会启动第二
个 owner。客户端版本在首次 initialize 后缓存并用于重连，不能回退成硬编码旧版本。

Settings 文件缺少新字段时默认 `daemon`。旧的
`KODAX_SPACE_RUNTIME_HOST=legacy|runtime` 只作为首次迁移默认来源；一旦用户偏好存在，
持久化设置成为启动真理。全新 profile 也会在第一次读取时以 exclusive create 原子写入
选定的 version 3 模式，避免环境变量在后续启动重新影响选择。

### 4. 接口契约

```ts
type CoderRuntimeMode = 'daemon' | 'embedded';

interface SpaceSettings {
  readonly coderRuntimeMode: CoderRuntimeMode;
}

// settings.setCoderRuntimeMode
interface SetCoderRuntimeModeInput {
  readonly coderRuntimeMode: CoderRuntimeMode;
}

interface SetCoderRuntimeModeOutput {
  readonly settings: SpaceSettings;
  readonly restarting: boolean;
}
```

Renderer 只能提交封闭枚举。Main 负责活动任务检查、owner policy、原子/补偿写入和重启；
失败以有界 IPC error 返回，不能由 renderer 决定是否强停 daemon。

### 5. 实现步骤

1. 扩展 Settings schema/store，覆盖 v1/v2 迁移、无效值回退、并发写入和持久化测试。
2. 扩展 IPC registry 与 schema tests，加入 `settings.setCoderRuntimeMode`。
3. 为 Runtime Host 增加初始化前 mode 配置、失败 daemon 的安全 embedded 准备路径、
   inline → daemon 恢复路径和 focused unit tests。
4. 增加可注入的模式切换协调器，测试两向成功、活动任务阻断、owner 转换失败补偿和
   无变化不重启。
5. Electron startup 在 daemon 初始化前应用偏好；生产 Settings handler 成功后安排
   `app.relaunch()` + 正常清理退出。
6. Settings → Runtime 增加可访问的模式选择、双语客户说明、错误反馈和切换重启按钮。
7. 更新用户手册、USAGE 和 Runtime ownership 文案。
8. 运行 schema/store/Runtime focused tests、typecheck、lint、renderer/main build。
9. 打包时验证根/desktop manifest、两份 lock、已安装 SDK 的精确版本和 Registry
   tarball/integrity 全部一致；自动执行 public facade import、Node ancestor dependency
   closure、解包后的 `better-sqlite3` 原生加载和 Windows packaged application boot。

### 6. 验收标准

- 新安装和旧配置默认显示并启动 Daemon；旧显式 legacy 环境在尚无持久化字段时迁移为
  Embedded。
- Daemon 与 Embedded 均可在重启后创建并运行 Coder Session；Partner 行为不变。
- UI 明确标记 Daemon 为推荐模式，并告诉客户 Daemon 异常时可切换 Embedded 继续使用。
- 模式卡分别显示当前已保存模式与待提交 radio 选择，失败后不会把待选值冒充为当前模式。
- 选择另一模式后必须点击“切换并重启”；成功写入和 owner 转换后应用自动重启并显示
  新模式。
- 任一 ManagedSession、running/paused Workflow、非终态 External Agent task、待处理
  permission/AskUser、尚未派发的 Coder queue、daemon 其他客户端或 active/queued work
  都会阻止不安全切换，不会强停或重放。
- Session、Slash、Workflow、Runtime External Agent、MCP 和 Runtime-affecting Settings
  操作都遵守同一个 admission gate；切换开始后不能从读写/控制旁路触碰正在交接的
  owner。Space-only 诊断仍可用于排障。
- Daemon 初始化失败且 owner 可安全释放/为空时仍能切换 Embedded；owner 状态不明或
  安全停止被拒绝时保持原模式并显示错误。
- 持久化或 owner policy 转换失败会执行补偿；若补偿后仍不能证明 owner 可用，则进入
  恢复重启、保持新 Coder admission 关闭，并用中性错误文案要求重启后确认实际模式。
- 启动时会按持久化模式协调 owner policy；daemon 偏好遇到 unowned inline policy 可
  自动修复，遇到 active/unreadable inline owner 则 fail closed。
- Renderer 永远收不到 daemon endpoint/token、owner revision、fence handle 或内部
  `legacy` 名称。
- focused tests、typecheck、lint、renderer/main build、精确 Registry SDK 检查、完整
  packaged dependency/native load smoke 与真实 packaged application boot 通过。

## FEATURE_142: Conversation File Action Menus

> Status: Completed (2026-07-28)

### 1. 需求概述

会话正文中已识别为文件路径的行内代码和 Markdown 文件链接，左键继续使用既有的
`openFileSmart` 路由；右键打开与 Files、Changes 等文件表面一致的完整
`FileActionMenu`。菜单包含：

- 在文件查看器中打开；
- 打开 diff；
- 插入 `@path`；
- 复制相对路径；
- 在文件管理器中显示。

HTTP(S)、Partner 生成物链接和证据引用继续使用各自现有行为，不显示文件操作菜单。

### 2. 影响范围

- `apps/desktop/renderer/src/features/session/messages/Markdown.tsx`
- 复用 `apps/desktop/renderer/src/shell/FileActionMenu.tsx`
- `tests/e2e/markdown-file-actions.spec.ts`
- 本功能设计和人工回归指南

不新增 Electron IPC、权限、持久化、Runtime 或 KodaX SDK 能力。

### 3. 技术方案

在 Markdown 文件目标外围增加一个轻量状态组件，持有右键菜单坐标并通过 Portal
渲染既有 `FileActionMenu`。鼠标右键阻止系统原生菜单并保留目标路径；键盘触发
context-menu 事件时，以目标元素边界作为坐标回退。

行内代码继续渲染为原有文件路径按钮。非 HTTP、非 Partner URI、非证据引用的 Markdown
链接，会从可识别的标签文本或解码后的 `href` 提取文件路径。两种目标的左键都继续进入
`openFileSmart`，右键只负责显示共享菜单。

### 4. 接口契约

- 左键路由不变：代码文件可进入 diff，预览型文件进入 File Viewer，其他类型按既有规则
  回退到文件管理器。
- “在文件查看器中打开”强制调用 `openFileInViewer`。
- “打开 diff”调用 `openInDiff`，仍受当前项目边界检查约束。
- “插入 @path”复用 composer 的 `requestInsert`。
- “复制相对路径”使用当前项目根目录归一化，不复制未验证的新路径表示。
- “在文件管理器中显示”复用 allowlisted `shell.revealPath` 链路。
- 文件识别仍由 `looksLikeFilePath` 管理；URL、敏感 `.env` 和包含 `..` 的路径不因本功能
  获得新入口。

### 5. 实现步骤

1. 先增加 Electron E2E，用真实项目文件证明当前会话路径右键没有共享菜单。
2. 在 Markdown 文件目标上挂接右键坐标状态，并复用 `FileActionMenu`。
3. 同时覆盖行内路径和 Markdown 文件链接，保持外部链接、Partner 链接和证据引用不变。
4. 验证五个菜单动作可见，并通过菜单实际打开 File Viewer。
5. 运行 focused E2E、renderer build、typecheck、lint 和格式检查。

### 6. 验收标准

- 已识别的会话文件路径右键显示五个现有文件动作，顺序、图标、文案和样式与其他文件表面
  一致。
- 左键行为与改动前一致，不因右键菜单统一而强制改成单一路由。
- 相对路径和允许范围内的绝对路径都把原始目标交给共享菜单，再由既有安全边界解析。
- HTTP(S)、Partner 生成物和证据引用不被误判为本地文件菜单目标。
- 菜单可以通过外部点击和 Escape 关闭，且靠近视口边缘时沿用现有防溢出定位。
- focused E2E 先失败后通过，并验证五个动作及 File Viewer 打开结果。
