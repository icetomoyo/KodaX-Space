# v0.2.0 - Connected Partner

> Status: Planned
> Features: F050, F051, F052
> Depends on: F116 embedded Runtime hosting, F121 authenticated Coder daemon host-tool binding, F114 workspace-first delivery, F122-F124 project material/evidence/recall, F126-F127 governed project knowledge, F129 presentation delivery, F130 Partner Outcome-First Workspace, and the shipped policy/audit foundation

## Batch decision

`v0.2.0` is no longer a reserve for re-enabling Partner; Partner is already released. The next major line makes Partner materially better at connected, evidence-grounded work through one governed browser runtime and two formal capability packs.

The packs are product-authored KodaX Skills/playbooks with deterministic tools and acceptance fixtures. They are hidden routing implementations behind F130's five stable outcome entries and free-form requests, not user-facing work modes or a Skill selector. They are not “learned Skills” and do not wait for KX-F263.

## FEATURE_050: Governed Browser Runtime

### User outcome

Coder and Partner can open modern web pages, navigate, interact, capture screenshots/content, and return source-linked evidence while the user can see and stop the browser session and audit network/browser actions.

### Product boundary

- Space-owned Electron browser capability exposed through bounded KodaX tool contracts.
- Visible or inspectable execution; no hidden general-purpose browsing daemon.
- Session-scoped browser context by default.
- Separate from external-system Connectors, which use scoped APIs and snapshots.
- `web_search`/`web_fetch` remain useful for simple retrieval; F050 handles JS rendering, navigation, interaction, screenshots, and structured extraction.
- Partner registers the bounded browser tool through the F116 embedded-inline host.
- Coder exposes the browser only through an authenticated F121 host-tool binding selected by an explicitly Space-started run. A CLI/IDE-started run does not inherit browser access merely because Space later attaches.
- The binding carries session, run, tool-call, initiating-client, permission, cancellation, and idempotency context. Browser availability is never inferred from an SDK version or renderer state.

### Design

- Main-process `BrowserSessionManager`; renderer receives sanitized state/screenshots, never direct privileged `webContents` control.
- Minimal tool family:
  - open/navigate;
  - inspect current page;
  - click/type/select/scroll;
  - capture screenshot/structured extract;
  - close/reset.
- One browser session has a stable session/run owner, bounded tabs/pages, navigation timeout, download policy, and storage policy.
- A capture keeps one authoritative browser-capture identity with URL, title, captured time, content hash, and screenshot/text provenance. Adopting its exact snapshot version through an F122 `ProjectMaterialRelation` or registering a screenshot Artifact creates an explicit stored relation; the UI never merges those owners by URL, path, or title.
- An accepted browser capture is an immutable task-only external evidence snapshot by default. It implements F123-compatible evidence units and truthful URL/time plus DOM/text/document/screenshot locators, F124-compatible selected/used trace facts, and F127's four-axis access/content state. Explicit F122 adoption creates only a `ProjectMaterialRelation` to the exact browser-capture owner/version without fabricating or merging a project-source identity.
- Permission policy distinguishes read/navigation, form input, file upload/download, authentication, and side-effecting submission.
- Network and navigation audit uses F069 structured logging plus F098 policy/audit semantics without recording secrets or page bodies by default.

### Security

- Browser content is untrusted and isolated from application origin/preload/Node.
- No arbitrary DevTools protocol access from the renderer or model.
- Block dangerous schemes, local file access, loopback/private-network targets by policy unless explicitly approved for a local-development use case.
- Credentials, cookies, and form secrets are never echoed to the model/logs.
- Side-effecting submissions require an explicit policy/permission decision and a visible target/action summary.
- Downloads are quarantined to a bounded staging area before becoming current-task/project material or a governed workspace file.

A quarantined download exposes separate reviewed actions:

- `Use in this task`: attach the quarantined immutable snapshot as task-only material;
- `Accept into workspace`: perform a governed Files/F114 move and create a workspace file;
- `Add to project materials`: explicitly create an F122 `ProjectMaterialRelation` to a supported immutable snapshot/file owner/version;
- `Discard download`: delete only the quarantined copy when no retained evidence relation requires an impact decision.

None implies another. Accepting a workspace file does not automatically make it project material, and unaccepted quarantine entries expire under a bounded retention policy.

### F130 Partner projection

- F050 is an authorized capability behind any relevant outcome entry or free-form request; it does not add a Browser entry, work mode, or right-rail tab.
- Current navigation, extraction, waiting, permission, failure, and recovery facts appear in `Process`. A visible browser inspector opens contextually from that run and does not replace the three-tab Partner rail.
- Browser-owned data uses explicit adoption actions: `Use in this task` creates an exact task-only evidence reference visible in Context; `Add to project materials` creates an F122 `ProjectMaterialRelation` to the exact capture/download version; `Register screenshot as result` creates an Artifact relation visible in Results; `Accept into workspace` creates a governed F114 file mutation visible in Files.
- `Propose as project knowledge` is available only through the F126 draft/evidence/review flow and never follows capture or project adoption automatically. Context distinguishes captures available from the browser catalog, selected for this task, and actually used by the turn. Automatic project recall may use a capture only after explicit F122 project adoption and under the effective F124 scope.
- Source-linked reports and screenshot artifacts appear in `Results` with their evidence relations. A quarantined download enters `Files` only after an explicit governed accept/move action.
- Closing the browser or its inspector does not discard already registered evidence, and closing the Partner rail does not stop the browser run.

Closing/resetting a browser session clears live pages, temporary permissions, cookies, and session storage according to policy; it does not silently delete accepted captures or citations. `Detach from task` removes only task selection; `Remove from project materials` ends only the F122 relation's project eligibility while preserving its target tombstone and current task selections; `Forget capture` is owned by the browser-capture store, requires an impact preview, writes the F127 `forgotten` content state, and leaves typed unavailable references for surviving Results/project knowledge. It never silently rehydrates the exact forgotten version. Deleting an accepted workspace file remains a Files action. Disabling F050 prevents new browsing but does not hide adopted F122 relations, Artifacts, Deliveries, or their evidence relations.

### Non-goals

- No desktop screen automation.
- No CAPTCHA bypass, anti-bot evasion, payment, purchase, or autonomous high-risk transaction.
- No cloud browser service.
- No browser-extension marketplace.

### Acceptance

- Navigation/interaction/capture works on deterministic local fixtures and representative HTTPS pages.
- Application origin and browser content cannot access each other.
- Private-network/file/scheme guards and permission classes have adversarial tests.
- Captures preserve inspectable immutable provenance and can participate as task-only evidence or explicitly related project material without becoming a project source.
- User can stop/reset the browser and clear session storage.
- Partner E2E proves the same browser capability can support an existing outcome entry without adding a launcher card, permanent panel, or fourth right-rail tab.
- Capture-to-project-material, capture-to-artifact, and accepted-download relations preserve authoritative IDs and never deduplicate by URL/title/path.
- Capture fixtures distinguish available, selected, and used states; task-only capture, project adoption, and knowledge proposal remain explicit separate steps.
- Capture citation resolution survives browser close while obeying retained-snapshot access policy.
- Use-in-task, accept-into-workspace, add-to-project, discard, detach, remove, and forget actions have non-cascading tests.

## FEATURE_051: Partner Document Work Pack

### User outcome

Users can give Partner a bounded set of PDF/DOCX/PPTX/XLSX/CSV/Markdown/images and request repeatable document outcomes such as extraction, comparison, summary, transformation, meeting notes, RFC/PRD drafts, presentation briefs, or structured tables.

### Design

- Ship formal versioned Skill/playbook assets behind automatic routing rather than adding scenario-specific conditionals, a visible Skill selector, or another persistent mode strip.
- Register bounded templates/capability adapters under F130's `分析报告`, `表格与数据`, `PPT 演示`, `文档写作`, and `文件整理` entries where their output contract fits. Free-form routing remains complete when no entry is selected.
- Reuse F130 task context, F122/F126 project material and knowledge, Office/PDF writers, F114 delivery/checkpoints, Results preview adapters, and policy/audit.
- Presentation requests delegate to F129's Presentation Project/Studio/verification contract. F051 may prepare sources, briefs, and citations but does not introduce another slide schema, writer, preview, or export route.
- Each workflow defines:
  - accepted sources and limits;
  - evidence/citation expectations;
  - output schema/format options;
  - deterministic validation where possible;
  - unsupported/ambiguous input behavior;
  - human review points.
- Prefer direct deterministic transformations/tools for mechanical work; use the model for judgment, synthesis, and layout decisions.

Inputs and templates are selected through Context; current workflow and validation facts appear in Process; registered documents, spreadsheets, reports, and presentations appear in Results; governed workspace mutations remain in Files. The pack never duplicates a full deliverable in the center conversation.

### Acceptance

- Fixture suite covers mixed Chinese/English sources, scanned/image-heavy documents, tables, citations, malformed files, and size/ZIP limits.
- Outputs are durable deliverables with provenance and render in current previews.
- Claims that depend on evidence cite an immutable evidence owner/version plus the best truthful locator; a local path is only a resolver-time display/open projection when current policy permits it.
- No unrestricted shell/package install or broad workspace mutation is introduced.
- Enabling or disabling the pack changes only its templates/adapters and truthful capability availability. The five F130 entries, `permissionMode`, `autoModeEngine`, effort/provider/model policy, tool policy, F124 source scope, connector grants, allowed workspace, composer draft, and attached material remain unchanged.

## FEATURE_052: Partner Research and Citation Pack

### User outcome

Partner can perform bounded multi-source research, compare claims, retain citations/captures, disclose uncertainty, and deliver an inspectable report rather than a chat-only answer.

### Design

- Trigger from F130's `分析报告` entry or free-form intent; research is not a sixth entry, `deep` mode, or Skill choice.
- The release baseline supports bounded research over task/project material, accepted project knowledge, `web_search`, and `web_fetch` without F050.
- `web_search` is discovery metadata, not page evidence. A search snippet may guide a bounded fetch but is never cited as though it were the underlying page.
- Every accepted `web_fetch` response becomes an immutable task-only `web-fetch-snapshot` with URL, capture time, content hash, bounded evidence units, truthful section/text/fallback locators, F127-compatible access state, and an F123 owner/version identity. It participates only when selected/used under F124 and does not become project material merely because it was fetched.
- `Add to project materials` creates an explicit F122 `ProjectMaterialRelation` to the exact web-fetch snapshot owner/version; only then may project-grounded automatic recall use it in later tasks. `Propose as project knowledge` remains the separate F126 draft/review step.
- F050 adds a `browser-enhanced` route for JS-rendered navigation, interaction, screenshot capture, and structured extraction. It is selected only when F050 is advertised, authorized, and useful for the request.
- Combine explicitly selected task-only captures with task/project material and accepted project knowledge. Automatic recall may include browser captures only after explicit F122 project adoption and under the effective F124 scope.
- Every used capture records its immutable evidence owner/version ID, F123 locator, four-axis access/content decision, and F124 trace relation.
- F050 absence never turns a search snippet into page evidence and never blocks the baseline research route. If the task specifically requires browser interaction, Partner reports that capability as unavailable rather than claiming completion.
- The bounded research plan, source/call/time limits, current stage, permission wait, and partial-failure recovery appear in `Process`, not as a permanent plan in the center.
- Evidence records include immutable owner/version identity, capture time, truthful locator plus quoted/derived claim boundaries, and resolver-time freshness/access/content decisions where available.
- Important claims require citation coverage; disagreements and missing evidence remain visible.
- Results include executive summary, methodology/scope, findings, evidence table, limitations, source list, citation coverage, and partial-result state.
- Use the shipped Partner verification contract for source-faithfulness/citation-completeness; do not create an H1-Partner engine fork.

### Acceptance

- Research fixtures include corroborated, conflicting, stale, inaccessible, and low-authority sources.
- The pack does not cite a search snippet as if it were the underlying page.
- Web-fetch snapshots, browser captures, connector snapshots, and local project sources remain typed distinct owners even when their URLs/titles match.
- Web-fetch citation resolution survives a changed/unavailable live page by resolving the immutable snapshot under its retained-access policy.
- Report regeneration preserves source provenance and creates a new artifact version.
- Bounded failure produces a partial report with explicit gaps, not fabricated completeness.
- Research-plan progress remains in Process, report/evidence review remains in Results, and the launcher contains no Research-specific card or mode.
- The complete baseline research fixture suite passes with F050 absent; browser-interaction fixtures run only when the browser-enhanced capability is enabled.
- Enabling or disabling F050 changes only browser-enhanced route availability. It does not change the selected outcome, `permissionMode`, `autoModeEngine`, effort/provider/model policy, F124 source scope, connector grants, allowed workspace, draft, or attached material.

## Release acceptance

- F050 threat model and permission matrix reviewed before browser implementation lands.
- Partner pack fixtures/evals measure faithfulness and task usefulness, not prose style alone.
- Browser and document workers are disposable/bounded where appropriate.
- Full typecheck, test, E2E, build, packaged smoke, and manual journeys pass.

## Rollout and rollback

- Gate browser registration, document pack, research baseline, and browser-enhanced research independently. Disabling F050 terminates browser sessions and disables only the browser-enhanced branch; F051 and the F052 local/web baseline remain available when their own gates and required capabilities pass.
- Closing or rolling back F050 terminates browser sessions and revokes their temporary permissions; it does not delete already accepted citation artifacts.
- Disabling a pack removes or disables only its pack-specific templates/adapters and reports a truthful unavailable reason. It never removes an F130 top-level entry; prior reports, provenance, and exported deliverables remain readable in Results.
