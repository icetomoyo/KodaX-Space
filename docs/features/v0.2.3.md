## FEATURE_096: Connector Foundation and Read Snapshots

### User outcome

Users can connect a supported external service, understand the granted scopes, select bounded content, create immutable read snapshots with provenance, add selected snapshots to current task or project material, explicitly promote eligible material into project knowledge, revoke access, and inspect what Space retained.

### Scope correction

The earlier F073 connector-snapshot item is absorbed here. Governed GitHub issue/PR writes are **not** part of the connector foundation; they require a separate reviewed feature after read-only authorization, snapshot, revocation, and audit behavior is proven.

### Connector model

Every adapter advertises:

- identity and version;
- supported auth modes;
- read scopes and resource types;
- snapshot/cursor behavior;
- freshness and deletion semantics;
- optional write capabilities, hidden in this release;
- rate limits and degraded states.

Space provides the shared catalog, authorization state, encrypted credential reference, scope review, resource picker, snapshot envelope, provenance, revocation, diagnostics, and audit. Provider-specific API logic stays in the adapter.

Every adapter separates these capabilities:

- authorization and account management;
- create/read/refresh remote snapshots;
- read retained local snapshot manifests and retained content when policy permits.

Revocation or an adapter action flag may disable remote authorization/read/refresh without disabling the retained-local read capability.

### Snapshot envelope

```ts
interface ConnectorSnapshot {
  snapshotId: string;
  snapshotVersionId: string;
  connectorId: string;
  accountIdentity: string;
  resourceType: string;
  resourceIdentity: string;
  title?: string;
  capturedAt: string;
  sourceUpdatedAt?: string;
  contentHash: string;
  contentRef: string;
  provenance: readonly string[];
  permissionScope: readonly string[];
}
```

The final persisted schema must cap all strings/collections and avoid storing credentials or unbounded raw API responses.

Changing access state is stored separately from the immutable envelope:

```ts
interface ConnectorSnapshotAccessState {
  snapshotId: string;
  snapshotVersionId: string;
  liveAvailability: 'current' | 'stale' | 'missing' | 'deleted';
  originAccess: 'authorized' | 'revoked' | 'unknown';
  retainedSnapshotUse: 'permitted' | 'audit-only' | 'restricted';
  retainedContentAvailability: 'present' | 'missing' | 'forgotten' | 'corrupt';
  reasonCode?: string;
  observedAt: string;
}
```

`snapshotId` is an opaque, non-semantic stable connector/resource lineage owner; `snapshotVersionId` is an opaque identity for one immutable capture. Neither ID encodes the connector, account, URL, resource identity, or title. Refresh keeps the lineage owner and creates a new version envelope rather than rewriting the cited capture. The immutable snapshot envelope is never rewritten to carry changing access/content state. Version-addressed observations implement F127's four-axis contract so a citation can resolve the exact captured version while the lineage's current pointer advances. The adapter also supplies F123-compatible bounded evidence units and truthful locators, such as resource field, comment/item identity, page/cursor, or a clearly labeled resource-level fallback.

### Authorization and revocation

- Prefer OAuth/device flows or connector-supported delegated auth; never ask the model for credentials.
- State/PKCE/callback handling is main-process-only, short-lived, origin-bound, and auditable.
- Tokens live in the OS credential store; durable records store references/metadata only.
- Users review scopes before authorization and can disconnect/revoke.
- Revocation blocks new remote-origin reads and refresh immediately. Retained-local reads remain separately governed by `retainedSnapshotUse`, `retainedContentAvailability`, integrity checks, and current owner/project policy; the UI explains retained snapshots, project material, and derived project-knowledge versions separately.

### Partner integration

- Connector catalog, authorization, account switching, scope review, and revocation live in project settings/connection management. They do not become a Partner launcher card, work mode, or right-rail tab.
- `+ Add material > Connected sources` is a picker for authorized advertised adapters. Selecting a resource creates or reuses an account-bound immutable snapshot and attaches only its opaque task reference. It does not make the resource project-available or select an account-wide corpus.
- `Add to project materials` explicitly creates an F122 `ProjectMaterialRelation` to the exact connector snapshot owner/version; it never creates a project-source ID or changes the connector owner. `Propose as project knowledge` is available only after durable project adoption and always enters the F126 draft/evidence/review flow.
- Task-only, project-material, and project-knowledge identities remain separate; no adoption step implies another. Context distinguishes five sets without inferring one from another: resources currently available in the authorized remote picker, exact versions retained locally, active project-adopted relations, exact refs selected for the task, and owner/version refs actually used by the turn.
- Snapshot selection/adoption never writes source IDs, account identity, connector grants, or retrieval scope into `PartnerOutcomeReceipt`. Connection management and Context may show only policy-safe account/authorization state. The F124 trace stores opaque evidence owner/version refs, effective scope, four-axis decisions, and bounded reason codes—never raw account identity, resource identity, credentials, or grant payloads.
- Refresh creates a new snapshot/version; it does not silently rewrite a cited evidence version.
- Authorization, account switching, connector refresh, and outcome selection never change the task's F124 retrieval scope. Only explicit task selection or project-material adoption may expand the user-requested eligible set; current authorization, access, retention, content availability, and freshness policy may always narrow the effective set. Each run records exact selected/used evidence owner versions plus access decisions in the normal F124 trace. Revoked/unknown origin authority fails closed for origin read/refresh and can never widen to an account corpus; a stale or origin-inaccessible exact retained version is evaluated independently and may be used only when the declared freshness policy allows it, retained use is `permitted`, retained content is `present`, integrity passes, and disclosure is truthful.
- F127 maps external deletion, permission loss, revocation, account switching, local forget, missing content, and corruption into the four-axis access/content contract. Before and after project adoption, F123 citations always resolve directly against the immutable connector owner/version; the `ProjectMaterialRelation` controls only project eligibility. Connector snapshot, F122 relation, F126 knowledge, and any generated Result retain separate authoritative IDs and are never merged by title or external URL.

Revocation immediately blocks new origin reads and refreshes. It does not silently delete retained snapshots, project material, project knowledge, or Results. When authorization is absent:

- hide or disable only the new-resource picker;
- keep existing task/project references visible in Context with typed safe state;
- keep Result identity and evidence-state metadata visible;
- allow retained snapshot detail only when `retainedSnapshotUse=permitted`, `retainedContentAvailability=present`, and snapshot integrity passes;
- expose only bounded tombstone/reason/remediation metadata when `audit-only` or `restricted`;
- show current-run revocation failure and recovery in Process;
- keep long-lived retained-snapshot inspection and forget actions in connection/project management.

Connection/project management retains a `Retained snapshots` section whenever local manifests exist. It remains reachable after revocation, account removal, adapter disablement, or framework rollback, subject to retention/access policy. Existing explicit task/project relations remain typed references. A retained version may be newly selected or adopted from this retained-local surface only when `retainedSnapshotUse=permitted`, `retainedContentAvailability=present`, integrity passes, and the retained-local adapter plus current owner/project policy explicitly authorize that action; it cites the exact retained version and never reuses revoked origin authority. `audit-only`, `restricted`, `missing`, `forgotten`, and `corrupt` versions cannot be newly attached or adopted, and the disabled remote picker never treats a local manifest as authorization.

Connector lifecycle commands are distinct:

- `Detach from task`: remove only the task reference.
- `Remove from project materials`: end only the F122 relation's project eligibility and retain its immutable target tombstone; preserve current task selections and the connector snapshot owner.
- `Forget retained snapshot`: delete eligible connector-owned snapshot content after an impact preview, write `retainedContentAvailability=forgotten`, and preserve typed tombstones for surviving references. The exact forgotten version never silently rehydrates; explicit authorized reacquisition creates a new immutable version.
- `Disconnect/Revoke`: remove authorization and block remote operations; do not imply deletion.
- `Delete external resource`: unsupported in this read-only feature.

### Security and non-goals

- Read-only adapter actions only in this release.
- No autonomous email/send/comment/merge/PR mutation.
- No connector credentials in renderer, prompts, logs, artifacts, project material, or project knowledge.
- No generic “OAuth proxy” that accepts arbitrary endpoints/scopes.
- No claim of real-time sync; refresh/cursor behavior is adapter-specific and visible.

### Acceptance

- Catalog/capability negotiation, auth state/PKCE, encrypted credential reference, scope review, snapshot caps, refresh, revoke, and stale behavior have deterministic tests.
- At least two adapter shapes validate that the shared model is not a single-provider abstraction; mock adapters are acceptable before production credentials.
- Partner material and project-knowledge citations resolve to immutable snapshot provenance.
- Revocation and account switching cannot cross-read snapshots or credentials.
- Diagnostics remain useful with all secrets redacted.
- Partner E2E covers authorization in settings, selection through `Connected sources`, explicit task/project/knowledge adoption, and typed revocation in Context/Results without introducing a Connector tab or outcome entry.
- Task-only connector evidence resolves an F123 citation without requiring project promotion; remote-picker-available, retained-local, project-adopted, task-selected, and turn-used connector sets remain distinct.
- The complete four-axis access/content matrix covers revoke, unknown authority, account switch, external deletion, retained permitted/present snapshot, audit-only, restricted, missing, forgotten, corrupt, and explicit reacquisition.
- Retained-local E2E proves a permitted/present/integrity-valid version can be deliberately selected/adopted after origin revocation without a remote read, while audit-only, restricted, missing, forgotten, corrupt, and remote-picker paths fail closed.
- Picker hiding never removes existing Context/Results references.
- Detach, remove-from-project, forget-snapshot, revoke, and unsupported external delete cannot invoke one another implicitly.
- Connector resource selection -> project-material relation -> project-knowledge draft -> accepted knowledge version requires four explicit user-confirmed actions/commits; none implies the next or creates another Partner session/run receipt type.

### Rollout

- Start with read-only GitHub issues/PR metadata or another low-risk adapter plus a deterministic mock.
- Production adapters are independently feature-flagged and capability-advertised.
- Adapter authorization/read/refresh flags are children of the connector-framework flag and current provider capability. A disabled child cannot be re-enabled by renderer state.
- Disabling remote actions preserves the retained-local snapshot reader, manifests, provenance, citations, and audit. It removes new authorization, remote selection, and refresh actions.
- A later governed-write feature must define captured target, diff/action preview, permission, idempotency, reconciliation, and audit before enabling mutations.

### Rollback

- Disable authorization and refresh per adapter without invalidating other connectors.
- Revocation and framework rollback block new origin reads/refreshes without silently deleting retained snapshots or derived objects.
- Retained snapshots are readable, previewable, exportable, or reusable only when the combined four-axis decision, integrity check, and owner/project policy permit it; audit-only/restricted/missing/forgotten/corrupt snapshots expose only their allowed typed state.
- A framework rollback preserves snapshot manifests, access-state records, explicit relations, tombstones, citations, and audit events. It must not silently reauthorize, promote, forget, or purge user data.
- Disabling the retained-local reader is permitted only for an explicit retention/access-policy reason and must render a typed unavailable state rather than silently hiding retained data.
