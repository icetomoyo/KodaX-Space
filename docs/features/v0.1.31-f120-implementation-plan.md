# v0.1.31 Implementation Plan - F120 Natural-Language Space Control

> Planning status: Implemented and verified
> Feature status: Completed
> Release target: `v0.1.31`
> Depends on: completed F116 inline Runtime adapter; final release resolves exact `@kodax-ai/kodax@0.7.68`
> Does not depend on: F055 `app://space` or F069 structured logging
> Prepared: 2026-07-12

## 1. Decision

F120 moves from `v0.1.32` into `v0.1.31` so the Runtime contract and its first user-facing semantic-control capability ship together. The release will deliver one end-to-end governed slice and a complete control-classification manifest. It will not expose every existing mutation to the model merely to meet a numeric coverage target.

Definition of done for `v0.1.31`:

1. every Settings row, top-level Shell control, Command Palette action, and local slash mutation is classified;
2. the semantic action contract, main authority service, and primary-renderer broker are production-ready;
3. the first low-risk action families share executors across deterministic UI and LLM tools;
4. only parity-complete descriptors appear in `space_control_inspect`;
5. all other controls remain deterministic and carry an explicit deferred or user-only classification;
6. F116 regressions remain green and the release is tagged only after the combined gate passes.

## 2. Verified starting point

### 2.1 Existing control paths

The current code confirms four independent control paths that can drift:

- `apps/desktop/renderer/src/shell/commandSources.ts` defines renderer-only Command Palette actions, including new-session and theme cycling.
- `apps/desktop/renderer/src/shell/BottomBar.tsx` owns a large `dispatchSlashAction()` branch tree spanning local notices, renderer state, and typed IPC.
- Settings and shell controls call channels such as `settings.setLanguageMode`, `settings.setRuntimeDefaults`, and `settings.kodaxConfig.setCompaction` directly.
- Shell layout/navigation is divided among `appStore`, `SurfaceStore`, `Shell` component state, and main-owned settings/services.

The migration must extract semantic executors without changing current persistence keys, visible behavior, slash transcript behavior, or owner boundaries.

### 2.2 Existing runtime/tool support

Space already has suitable foundations:

- in-process SDK tools use `registerTool()` and validate again inside their handlers;
- `session-run-context.ts` attributes tools through AsyncLocalStorage and SDK execution context;
- Partner uses a fail-closed tool visibility policy and explicit Space-tool policy registry;
- `push.ts` already targets and identifies the current primary renderer;
- `space-ipc-schema` is the zod-backed invoke/push allowlist used by preload, main, renderer, and tests.

### 2.3 Contract gap to resolve first

The SDK contract introduced by `0.7.67` and retained in the final `0.7.68` dependency exposes optional `toolCallId` and `taskSurface`. Space now preserves both. `taskSurface` is the SDK task-entry surface (`cli`, `repl`, or `plan`), not Space's Coder/Partner product surface or the live session's Permission Plan mode. Product attribution remains bound through `agentProfile.surface`, AsyncLocalStorage, and the authoritative Space session; Plan policy uses the Space session's trusted `permissionMode`. F120 requires `toolCallId` for apply idempotency and does not synthesize a replacement when it is absent.

The existing push helper is fire-and-forget. F120 therefore needs a dedicated bounded request/ack broker rather than treating `pushToRenderer()` as a request-response transport.

## 3. Scope policy

### 3.1 First LLM-visible slice

Subject to the P0 inventory, implement these families first:

- explicit theme and language selection;
- Coder/Partner surface selection when the target is currently available;
- registered panel and Settings-section navigation;
- left sidebar, Task Dock, focus mode, and semantic width/layout presets;
- default reasoning mode and other individually reviewed non-sensitive defaults.

Use desired-state actions (`set dark`, `set open`, `set half`) rather than toggles. A deterministic UI control may keep toggle presentation but must resolve it to an explicit desired-state action before execution.

### 3.2 Classified but not automatically exposed

These families require separate confirmation, undo, or stronger owner work and may remain deferred within `v0.1.31`:

- default Provider and default permission mode;
- session rename/pin/unread and project rename/archive;
- default workspace changes and compaction changes;
- any action whose readback cannot yet distinguish applied from unknown.

Deferred entries remain in the manifest with an owner, effect, reason code, and availability gate. They do not appear in tool inspect results.

### 3.3 User-only and excluded

- credentials, tokens, authorization headers, arbitrary provider URL/header/env values;
- permission request answers, AskUser replies, or confirmation acceptance;
- native picker results and OS credential dialogs;
- destructive deletion, exit/restart, installer/update acceptance, MCP install/config writes;
- arbitrary filesystem paths, URLs, network sends, IPC channels, store keys, DOM selectors, or click coordinates;
- caret, scroll, hover, drag, animation, and other non-semantic mechanics.

## 4. Target architecture

```text
KodaX registered tools
  -> space_control_inspect / space_control_apply
  -> SpaceActionService (Electron main authority)
       -> descriptor catalog + availability + policy
       -> idempotency/precondition/receipt stores
       -> main-owned executor adapters
       -> RendererActionBroker
            -> typed push request to primary renderer
            -> renderer owner validates and executes
            -> typed invoke acknowledgement and readback

Trusted UI entry points
  -> renderer semantic executor or main service adapter
  -> same descriptor schema and canonical readback
  -> no impersonation of LLM origin
```

Ownership rules:

- Descriptor metadata is shared; executable functions stay in the owning process.
- Availability is computed by the owner/service and is not stored as mutable descriptor data.
- Renderer state is not mirrored wholesale into main. Inspect returns only descriptor-approved safe state.
- Main-owned settings continue through existing stores/services; F120 does not create parallel persistence.
- Auxiliary and artifact windows cannot inspect, apply, confirm, acknowledge, or undo actions.

## 5. Contract shape

The canonical shared zod contracts cover:

- versioned action descriptors without executable fields;
- effect, owner, surface, confirmation, plan-mode, revision-key, and exclusion enums;
- bounded per-action argument and safe-state/receipt unions;
- inspect query/result;
- apply request/result;
- renderer inspect/apply request pushes and acknowledgement invokes;
- confirmation and undo receipts where supported.

Required limits:

- one action per apply call;
- bounded query, alias, result count, string length, object depth, and receipt detail;
- `additionalProperties: false` for every LLM-facing object;
- canonical argument serialization and digest fixtures;
- no free-form renderer error text in receipts.

Precondition tokens bind action ID, canonical argument digest, trusted session/surface, owner and renderer instance, revision key/revision, and expiry. Exact apply retries use a process-local 10-minute/1,024-entry LRU keyed by `sessionId + toolCallId + actionId + argument digest`. Reusing the same tool call with different arguments is denied.

## 6. File plan

### 6.1 New modules

| Area              | Planned module                                            | Responsibility                                                       |
| ----------------- | --------------------------------------------------------- | -------------------------------------------------------------------- |
| Shared schema     | `packages/space-ipc-schema/src/channels/space-control.ts` | zod contracts for inspect/apply/broker/receipts                      |
| Main catalog      | `apps/desktop/electron/space-control/catalog.ts`          | stable descriptor metadata and classification manifest               |
| Main authority    | `apps/desktop/electron/space-control/service.ts`          | policy, trusted context, preconditions, idempotency, receipts        |
| Renderer broker   | `apps/desktop/electron/space-control/renderer-broker.ts`  | bounded pending map, timeout, cancellation, primary-target authority |
| Tool registration | `apps/desktop/electron/space-control/tools.ts`            | SDK inspect/apply registration and Partner policy                    |
| Main executors    | `apps/desktop/electron/space-control/main-executors.ts`   | adapters over current settings/provider/session/project owners       |
| Renderer registry | `apps/desktop/renderer/src/space-control/registry.ts`     | renderer descriptor/executor/readback mapping                        |
| Renderer listener | `apps/desktop/renderer/src/space-control/broker.ts`       | primary renderer request validation, execution, ack                  |
| Receipt UI        | `apps/desktop/renderer/src/space-control/receipts.ts`     | compact local receipt projection and optional user-only undo         |

Names may be adjusted to repository conventions, but ownership must remain explicit and modules must not become a generic IPC or store mutation layer.

### 6.2 Existing modules to change

- `packages/space-ipc-schema/src/channels/index.ts`: register the new invoke/push contracts.
- `apps/desktop/electron/ipc/register.ts` and the main IPC registration composition: register acknowledgement handlers with sender identity checks.
- `apps/desktop/electron/kodax/session-run-context.ts`: include and validate `toolCallId` and `taskSurface`; reject tool-context/ALS/authoritative-session identity mismatches.
- `apps/desktop/electron/kodax/real-session.ts`: register F120 tools before managed execution and expose them only when the capability gate passes.
- `apps/desktop/electron/kodax/partner-tools.ts`: add a bounded `space-control` policy scope and keep per-action Partner enforcement in the F120 service.
- `apps/desktop/renderer/src/shell/commandSources.ts`: call semantic actions rather than owning duplicate mutations.
- `apps/desktop/renderer/src/shell/BottomBar.tsx`: route only compatible slash mutations through semantic executors while preserving notices and read-only diagnostic commands.
- Settings, `Shell`, layout stores, and selector components: migrate family by family to owner executors.
- localization and manual topics: add action/receipt/denial strings without exposing raw model or renderer errors.

## 7. Implementation sequence

### P0 - Contract probes and inventory (1-2 engineering days)

1. Add a published-SDK probe proving registered tool handlers receive `sessionId`, `toolCallId`, `taskSurface`, execution root, and agent profile through F116 inline Runtime.
2. Add negative probes for missing/mismatched context and retained legacy behavior.
3. Generate or hand-author the initial complete control manifest, then add a coverage test that detects new unclassified controls.
4. Freeze current theme/language/navigation/layout/Settings/Command Palette/slash behavior and persistence fixtures.
5. Approve the initial LLM-visible slice before implementation proceeds.

Exit gate: trusted tool attribution is proven and every manifest entry has a reviewed classification.

### P1 - Shared contract and pure registry (2-3 engineering days)

1. Add zod schemas, bounded discriminated unions, canonical argument serialization, and schema tests.
2. Implement descriptor uniqueness, surface/effect/confirmation consistency, exclusion-code, and safe-field tests.
3. Implement pure availability/policy functions and per-key revision semantics.
4. Define the first-slice descriptors and readback shapes.

Exit gate: all contract and registry tests pass without Electron or renderer state.

### P2 - Main authority and renderer broker (3-4 engineering days)

1. Implement `SpaceActionService` with trusted-context derivation, precondition tokens, idempotency, plan/surface checks, and canonical receipts.
2. Implement the primary-renderer request/ack broker with bounded pending state, timeout, abort, reload/shutdown cleanup, and sender identity validation.
3. Add unknown-result/readback reconciliation; never automatically reapply after an ambiguous timeout.
4. Add receipt-local user-only undo infrastructure only for actions with reliable before-state and revision conflict detection.

Exit gate: race, replay, timeout, stale renderer, auxiliary sender, and shutdown tests pass.

### P3 - Deterministic executor convergence (3-5 engineering days)

1. Migrate theme/language and registered navigation first.
2. Migrate layout presets and panel/Settings opening.
3. Migrate reviewed non-sensitive defaults through current main owners.
4. Route Command Palette and compatible slash mutations through the same executors.
5. Keep read-only slash diagnostics in their current domain unless a semantic observe action adds clear value.

Exit gate: each migrated family has state, persistence, UI, Command Palette/slash where applicable, direct-service, and readback parity fixtures.

### P4 - KodaX tools and Partner policy (2-3 engineering days)

1. Register `space_control_inspect` as readonly and `space_control_apply` as state-mutating with strict schemas and progressive disclosure.
2. Pass the actual SDK tool context to the service; do not rely only on AsyncLocalStorage when both sources are available.
3. Filter Partner descriptors during inspect and enforce the same surface matrix during apply.
4. Enforce per-action plan-mode rules inside the service even though the multiplexed tool has coarse SDK metadata.
5. Project canonical receipts as local client notices, not assistant-authored claims.

Exit gate: mock-provider tests prove correct calls and prove guessed/hidden action IDs remain denied.

### P5 - Hardening, docs, and release gate (2-4 engineering days)

1. Run malformed-output, replay, surface/session/project mismatch, renderer reload, ack-loss, and confirmation/undo conflict coverage.
2. Verify no secrets, prompts, arbitrary paths, or raw errors reach receipts or existing diagnostics.
3. Test Provider-unavailable and broker-unavailable degradation with deterministic controls still working.
4. Add bilingual human acceptance guidance and update current docs/manual topics.
5. Run the full F116 regression set, Desktop unit/E2E, typecheck, lint, production build, and packaged smoke on the existing packaged origin.

Exit gate: combined F116 + F120 acceptance passes before creating the `v0.1.31` tag.

Estimated implementation size: 13-21 engineering days for one experienced engineer, mainly driven by inventory size and the number of deterministic paths migrated in P3. P0 must re-estimate P3 after the manifest is frozen.

## 9. Human acceptance

With a configured mock or real Provider, verify in Coder and Partner where allowed:

1. explicitly set dark theme and receive one truthful receipt;
2. open the exact MCP Settings section without exposing MCP configuration writes;
3. select the Task Dock half-width preset across restored and maximized windows;
4. switch surface and open a registered panel without rebinding the originating run;
5. set the default reasoning mode and confirm persistence after restart;
6. ask an ambiguous request and confirm Space does not guess an action;
7. attempt credential, permission-answer, arbitrary-path, destructive, and hidden Coder-only actions and confirm denial/navigation-only behavior;
8. reload the primary renderer during apply and confirm a truthful unknown/failed receipt without duplicate mutation;
9. disable the F120 tool gate and confirm all deterministic controls still work;
10. start from no active Session and no active Project and confirm the documented deterministic fallback behavior.

## 10. Risks and mitigations

| Risk                                           | Mitigation                                                                                                                   |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Scope expands into every UI gesture            | Complete classification, but expose only parity-complete semantic actions; defer mechanics and sensitive families explicitly |
| Tool call retries duplicate mutations          | Desired-state executors, trusted `toolCallId`, argument digest, bounded idempotency cache, no retry after unknown            |
| Main/renderer state races                      | Per-owner instance and revision keys, short-lived preconditions, owner-side revalidation and readback                        |
| Multiplexed tool widens Partner or plan mode   | Filter at inspect and enforce per action at apply from trusted descriptor/session state                                      |
| Refactor breaks existing UI/slash behavior     | Freeze fixtures in P0 and migrate family by family behind the semantic executor                                              |
| F120 becomes coupled to sibling infrastructure | Keep semantic control independent from the F055 origin and F069 sink even though all ship in `v0.1.31`                       |
| Release metadata is finalized too early        | Treat `v0.1.31` as development until implementation, combined verification, tag, and package publication complete            |

## 11. Rollout and rollback

- Keep semantic executors usable by deterministic UI even when LLM tool exposure is off.
- Gate inspect/apply exposure by runtime context and renderer-broker readiness; do not use SDK version comparison alone.
- Enable action families only after their parity fixtures pass.
- If LLM policy fails, stop new applies, cancel uncommitted broker requests, reconcile ambiguous requests, and hide/unregister the tools. Do not revert already persisted preferences automatically.
- Preserve existing persistence formats so the last stable build can reopen the profile.
- Retain F116's restart-only legacy Runtime rollback for its existing scope; never replay an F120 mutation through legacy mid-turn fallback.

## 12. Approved decisions

Implementation proceeded under these two approved decisions:

1. `v0.1.31` ships the first safe vertical slice plus 100% classification, rather than requiring executor migration for every eligible control.
2. permission default, Provider default, workspace/compaction, and session/project organization remain deferred unless P0 proves their confirmation, undo, and readback contracts fit the release window.

This checkpoint keeps the version-consolidation goal while preventing the release from turning into an unbounded UI-platform rewrite.
