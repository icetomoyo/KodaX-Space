# v0.1.42 - Partner Knowledge Quality and Curation

> Status: Planned
> Features: F125, F126
> Position: first quality/governance enhancement after the usable `v0.1.32` baseline
> Depends on: F122-F124 and F130; optional retrieval providers are not release blockers. F117 remains Coder-only and no Partner Memory integration is part of this release.

## Batch decision

The `v0.1.32` offline FTS5/citation loop remains the required product baseline. This release adds optional internal retrieval routes only when measurement justifies them and turns the existing Partner KB into a reviewed, versioned project-knowledge layer reached through F130's project-material management path.

Embedding, reranking, and automatic drafting are independently gated. Failure or disablement always returns to the already-usable FTS5 and explicit project-knowledge path. Retrieval routes are engine decisions and advanced diagnostics, not Partner work modes or outcome entries.

## FEATURE_125: Hybrid Retrieval and Evidence Ranking

### User outcome

Partner finds relevant evidence for exact identifiers, Chinese/English terminology, paraphrased concepts, and multi-source questions while preserving a fast offline route. Users can inspect why cited evidence matched while retrieval routing remains automatic.

### Retrieval plan

- FTS5 BM25 remains the required offline baseline and fallback.
- A bounded full-context path may be used for a small, explicitly selected corpus that fits the evidence budget and access policy.
- Optional dense retrieval uses a pluggable local or remote embedding capability and stores only versioned, rebuildable derived vectors.
- A hybrid route fuses lexical and dense candidates deterministically before optional reranking.
- Optional reranking is bounded by candidate count, latency, cost, privacy, provider health, and data-locality policy.
- Project, selected material/evidence owner, exact version, type, time, language, state, access, and freshness filters apply across every route.
- F130 outcome-entry selection never selects a retrieval route, changes source scope, or changes Core Project Context eligibility.

### Provider and locality policy

- No embedding or rerank provider is required to use Partner knowledge.
- Remote providers require explicit opt-in describing what text leaves the device and how to disable/delete/rebuild derived state.
- Local models are optional downloads with version, size, health, and removal controls.
- Provider changes create a new derived-index generation and never mutate source text, citations, or accepted knowledge.
- Provider failure degrades to FTS5 with a visible retrieval-route explanation in the F124 trace and technical details; it does not create a separate run-routing object.

### Ranking and explainability

Each result retains the retrieval route, applied filters, component ranks, fusion/rerank generation, freshness, authority class, and selection/truncation status. A concise `why matched` explanation appears with F123 evidence details and F124 recall trace, not as a work-mode selector or permanent task control. Detailed scores and provider diagnostics remain under technical details.

Pinned sources and preferred accepted synthesis pages influence eligible candidate selection through explicit bounded policy; they do not force irrelevant text into every answer.

### Acceptance

- The FTS5-only route passes the complete suite with optional providers absent, disabled, failing, or timing out.
- Identical source/index/config generations produce deterministic candidate fusion and trace output.
- Access/status filters cannot be bypassed by vector results, caches, query rewrite, or reranking.
- Provider opt-in, removal, rebuild, timeout, budget, fallback, and data-locality disclosure have deterministic tests.
- A versioned benchmark demonstrates whether hybrid/rerank materially improves the target queries before either route becomes default.
- Selecting or switching any F130 outcome entry leaves the eligible material/evidence set, Core Project Context blocks, and route policy unchanged.

## FEATURE_126: Curated Knowledge Lifecycle and Core Project Context

### User outcome

Partner can propose a reusable decision, concept, synthesis, timeline, or note. Users inspect its evidence, edit or reject it, and explicitly promote it into versioned project knowledge. A small Core Project Context keeps accepted goals and constraints available in new sessions.

### Knowledge lifecycle

Pages use explicit states:

- `draft`: proposed and excluded from normal factual recall;
- `active`: accepted and eligible for normal Context Broker retrieval;
- `stale`: accepted but affected by changed or unavailable evidence;
- `superseded`: retained history with an explicit replacement;
- `archived`: excluded from normal recall but retained under policy;
- `restricted`: provenance/access does not permit normal use.

Transitions are explicit, audited, concurrency-checked, and reversible where safe.

### Versioned page model

- Preserve and extend F070 page types: source, entity, concept, synthesis, decision, timeline, and note.
- Every accepted edit creates an immutable version with user/agent origin, timestamp, change summary, status, and F123 citations.
- Diff covers body, metadata, state, evidence coverage, evidence additions/removals, and provenance.
- Merge and supersede preserve backlinks and history rather than silently deleting cited knowledge.
- Existing `partner-kb.json` content receives an exportable, hash-checked, rollbackable migration into the versioned canonical model.

### Draft proposal flow

- Partner may create a draft on explicit request or propose one after a grounded run.
- Proposals include type, title, content, evidence, confidence rationale, assumptions, and affected current pages.
- A grounded result exposes `Propose as project knowledge` in F130 `Results` only after the exact Result version/export has an explicit F122 `ProjectMaterialRelation`; project-wide pending proposals also appear in the management surface's draft inbox. An explicit user request may still create a clearly labeled uncited/assumption draft, but it cannot carry or imply task-only evidence that has not been adopted.
- Users can accept, edit then accept, merge, defer, or reject.
- Rejected drafts do not reappear unchanged without new evidence or an explicit request.
- Bulk promotion has a bounded preview and explicit confirmation; chat history is never auto-accepted as project truth.
- Creating a result, selecting an outcome card, attaching material, or completing a run never promotes content automatically.

Task-only evidence, project material, and project knowledge remain separate owners:

1. `Attach to this task` creates only a task selection.
2. `Add to project materials` creates an explicit F122 `ProjectMaterialRelation` to the exact source/evidence/Result owner version.
3. `Propose as project knowledge` creates an F126 draft with evidence.
4. User acceptance creates an active knowledge version.

No step implies, batches, or silently performs the next step.

### Core Project Context

- Store a bounded ordered set of accepted blocks for goals, current phase, constraints, terminology, and critical decisions.
- Each block has a strict budget, evidence coverage, state, owner, and last-reviewed time.
- Users explicitly pin/unpin or approve Partner suggestions.
- Core Project Context obeys the F124 retrieval-scope matrix:
  - `project-grounded` may inject eligible active blocks;
  - `selected-only` excludes Core Project Context; a future explicit block-selection contract may pass a selected block only as ordinary task input;
  - `general` excludes Core Project Context.
- Every included block ID, version, and inclusion reason is recorded in the turn trace.
- Outcome entry, result kind, prompt template, and retrieval route never alter this matrix.
- F130 outcome entry, preferred result kind, and prompt template do not add, remove, reorder, or bypass Core Project Context blocks.
- Over-budget content requires user-visible consolidation; it is not silently truncated into a different meaning.
- Coder/F117 Memory and transient session notes cannot enter Core Project Context. F117 exposes no Partner adapter; any future Partner memory feature requires a separately reviewed promotion contract.

### Project materials and knowledge management surface

- Open from F130 `+ Add material` -> `Manage project materials and knowledge`, with a typed unavailable/legacy fallback when F126 is gated off.
- Present Materials, Knowledge, and Updates as project-level management sections; local project sources are one typed material-owner class rather than a separate permanent Partner rail.
- Draft inbox with evidence preview and diff.
- Filters for type, state, owner, freshness, confidence, and evidence coverage.
- Core Project Context editor and budget meter.
- Version history, compare, restore, merge, supersede, archive, and backlinks.
- This surface is not a permanent Partner left rail, a sixth outcome entry, a new task-level top tab, or a replacement for the F130 `Context` drawer.
- F130 `Context` remains the task-scoped place to select eligible input material; F130 `Results` remains the task-scoped place to inspect a generated result and explicitly propose it for promotion.

### Acceptance

- Draft, accept, edit, concurrent edit, reject, merge, supersede, stale, restrict, archive, restore, migrate, and rollback cases have deterministic tests.
- Draft/stale/restricted pages are excluded from normal factual recall unless an explicit review action/filter requests them.
- Every active page version retains resolvable evidence or a visible uncited/assumption state.
- Core Project Context is bounded, ordered, inspectable, and stable across sessions.
- Scope fixtures prove that only project-grounded auto-injects Core Project Context and that each included block ID/version/reason appears in the F124 trace.
- Migration and corruption recovery preserve user-authored content and legacy source links.
- The management surface is reachable from F130 without recreating the removed permanent Sources/KB rail or changing the active outcome entry.

## Release acceptance

- FTS5 remains a complete offline path while optional retrieval routes prove measurable value or stay disabled.
- Partner can propose a cited decision draft, the user can compare/edit/accept it, and a fresh session can retrieve the active result.
- Core Project Context supplies accepted project orientation without importing Coder/F117 Memory or transient session notes.
- Disabling hybrid retrieval or drafting does not reduce the `v0.1.32` local material/evidence-grounded baseline.
- No retrieval route, knowledge state, or Core Project Context action becomes a Partner work mode or outcome entry.

## Rollout and rollback

- Gate full-context selection, dense retrieval, rerank, draft proposals, versioned canonical storage, and Core Project Context independently.
- Introduce retrieval enhancements in trace-only/shadow mode before automatic selection.
- Migrate legacy KB with preflight, export, counts/hashes, and readback before switching the canonical pointer.
- Rollback restores FTS5 retrieval and accepted KB read/export while stopping new versioned writes or Core Project Context injection.
