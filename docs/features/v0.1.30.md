## Batch Intent

`v0.1.30` is the Partner foundation consolidation lane and the new Partner working-agent design home. It pulls the implemented Partner workbench, knowledge base, generated deliverable, reviewed workspace-file, and local policy/audit sessions into one release-management bucket, then supersedes the overly rigid "finite artifact formats + proposal-only writes" model with F114.

Partner's target model is now workspace-first: the safety boundary is where Partner may write, how writes are checkpointed, and how the user can inspect/accept/rollback the result. The deliverable boundary is no longer a fixed list of file extensions. `F109` remains a convenience writer for common Office/PDF files, and `F113` remains a strict/review-required fallback, but neither defines the ceiling of what Partner can deliver.

Historical source docs remain useful design records:

- F049 historical design: [v0.1.12.md](v0.1.12.md)
- F070-F074 historical KB design: [v0.1.17.md](v0.1.17.md)

External design references (directional references, not parity claims):

- WorkBuddy pattern: workspace/project folder as the core task boundary, expert/skill/connector composition, and Ask -> Plan -> Craft -> Accept as the user-facing loop.
- Hermes-agent pattern: narrow core tool surface, composable toolsets/skills, real file/tool paths, checkpoint-style safety, sensitive-path guards, approvals at risk boundaries, and post-write verification.

## FEATURE_114: Partner Workspace-First Delivery and Checkpointed Writes

> Status: Completed (2026-07-09)

### Problem

The previous Partner write model solved safety by restricting delivery to a few Space-owned artifact kinds or reviewed text-file proposals. That is too rigid. A working agent's output can be a folder, archive, dataset, notebook, webpage, image set, generated config sample, transformed source bundle, spreadsheet, deck, audio, video, or a change performed in an external system. A fixed format list becomes the product ceiling.

Partner should be a highly efficient working agent: lighter than Coder, but able to borrow coding capabilities when they make office/research/data work faster. It should not become a heavyweight coding agent that autonomously refactors repositories, manages branches, installs dependencies, or performs broad shell mutation by default.

### Design Principles

- Workspace, not extension, is the primary safety boundary.
- Any bounded file inside an allowed Partner output root can be a deliverable. Direct folder-level registration remains follow-up work; helper-created directories act as containers for registered file outputs.
- Preview support is best-effort and extensible; unknown formats still appear as files with metadata, reveal, and copy-path actions.
- User friction should happen at risk boundaries, not on every generated file.
- Writes must be inspectable, hashable, and reversible.
- Coding capability is a boost layer: use it to inspect, transform, validate, render, and package work; escalate to Coder for true codebase mutation.

### Partner Write Zones

| Zone                   | Default         | Intended use                                                                                       | Gate                                                        |
| ---------------------- | --------------- | -------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| Run output workspace   | Allowed         | Task outputs under `.kodax/partner-runs/<session>/` or a user-chosen output folder                 | Direct write, registry event, optional checkpoint           |
| Workspace session root | Opt-in          | Write into a selected project/folder as part of the task                                           | Checkpoint before mutation, changed-files summary, rollback |
| Review-required paths  | Conditional     | Source code, config, existing important files, overwrites, deletes, moves                          | F113 proposal or explicit approval                          |
| External systems       | Not implemented | Email, PR creation, connector writes, publishing, uploads                                          | Future scoped connector confirmation and audit              |
| Blocked paths          | Always blocked  | Secrets, credentials, system paths, outside allowed roots, destructive git/package-manager actions | Deny                                                        |

### Delivery Model

F114 adds a filesystem-backed delivery registry instead of a format whitelist:

- Partner may create arbitrary bounded files inside the run output workspace; nested directories are created as file containers.
- Every created/modified path is recorded with absolute path, display name, size, MIME/type sniff, extension, content hash, source refs, producer tool, and session id.
- ArtifactPanel is a delivery browser over this registry: text, PDF, DOCX, XLSX, PPTX, image, audio, and video outputs use the existing bounded rich-preview pipeline; unknown formats get metadata, reveal, and copy-path actions without requiring a fixed extension list.
- `create_office_artifact` remains the preferred writer for common Office/PDF outputs when a structured writer is useful.
- Existing `create_artifact` remains useful for inline markdown/code/html/svg/chart/image content, but it no longer constrains deliverable shape.

### Checkpoint and Rollback Model

Borrow the Hermes-style safety net while keeping Partner lightweight:

- Store checkpoint metadata in `~/.kodax/space/partner-checkpoints.json` and before-snapshots under `~/.kodax/space/partner-checkpoints/<checkpoint-id>/before.bin`.
- Never touch the user's real `.git`.
- `write_partner_workspace_file` snapshots the target file before a checkpointed create/update and records before/after hashes, byte sizes, diff preview, producer, session id, and delivery id.
- Rollback is hash-guarded: if the target changed after the Partner write, rollback refuses and requires review instead of clobbering user work.
- Create rollback deletes the created file; update rollback restores the captured previous bytes.
- Current MVP is file-level checkpointing for lightweight Partner writes; multi-file/root snapshots, move/delete checkpoints, restore-single-file UI polish, and pruning policy remain follow-up hardening.

### Lightweight Coding Boost

Partner can borrow coding capability without becoming Coder:

- Default posture: most Partner work should stay non-code: read, synthesize, compare, plan, draft, transform, review, and deliver. Coding is a boost, not the task default.
- Allowed by default: repo read/search, code intelligence summaries, small task-local helper tools, generated mini apps, transformation scripts in the run workspace, validators, format sniffers, renderers, file packagers, data converters, and bounded smoke checks for generated outputs through `run_partner_helper`.
- Toolmaking rule: Partner may write code to help itself or the user when that code is a bounded task artifact. Keep that code in the run output workspace and execute JavaScript helpers only through `run_partner_helper`; project-visible helper code must be checkpointed and easy to roll back when local policy explicitly allows it.
- Approval required: writing source/config in the user workspace, running package managers, installing dependencies, executing long-lived services, changing git state, or modifying many code files.
- Escalate to Coder: implementation tasks, refactors, dependency migrations, debugging production code, branch/commit/PR workflows, or anything where codebase mutation is the primary goal.

### User Flow

The long-term Partner flow uses the following design target; v0.1.30 currently exposes scenario playbooks plus the global Plan/Accept-edits/Auto permission modes, not a complete Ask/Plan/Craft state machine:

1. Ask: inspect sources and list what Partner can see.
2. Plan: show output root, intended deliverables, risky writes, coding boosts, and external actions.
3. Craft: execute without per-file interruption for low-risk output-workspace files.
4. Accept: show real files/folders, previews, changed paths, validation evidence, and rollback controls.
5. Iterate: let the user ask for local modifications without rerunning the whole task.

### Migration From F109/F113

- F095 output target selector becomes an output-mode selector with `Run workspace` as the default, plus Office/PDF convenience outputs and checkpointed/reviewed workspace text modes; connector actions remain a future extension.
- F109 stays as the Office/PDF convenience writer.
- F113 stays as strict/review mode and sensitive-path fallback.
- Partner steering should stop saying "do not write files"; it should say "write only inside the declared Partner output workspace unless a checked policy mode allows more."
- Policy/audit should classify action type, root, path risk, checkpoint id, and external side effect independently.

### Implemented Slices

1. **Output workspace service**: per-session run output roots live under `~/.kodax/space/partner-runs/<session>/` and are exposed through `partner.deliveries.outputRoot`.
2. **Delivery registry**: `partner-deliveries.json` records arbitrary file/folder outputs with path, hash, size, MIME, extension, source refs, producer, checkpoint id, and session id.
3. **Partner run-output write tool**: `write_partner_deliverable` writes arbitrary bytes into the Partner run-output workspace with path normalization, size caps, sensitive-name guards, symlink escape checks, audit, and registry updates.
4. **Checkpointed workspace write tool**: `write_partner_workspace_file` performs lightweight create/update inside the project workspace through file-level checkpointing and registers the result as a `workspace-session` delivery.
5. **Rollback tool and IPC**: `rollback_partner_checkpoint` plus `partner.checkpoints.rollback` restore checkpointed writes when the target hash still matches the Partner write and synchronize or remove the associated delivery registry entry after rollback.
6. **Bounded helper runner**: `run_partner_helper` executes each small `.js` helper in a one-shot Worker containing a capability-free VM snapshot. Inputs, file APIs, logs, and write operations are created inside the VM realm; no host constructors/callbacks are injected. The parent enforces wall-clock termination and V8/resource/payload caps, then independently validates and conflict-safely applies the serialized journal. Shell, package managers, `require`, dynamic import, `process/env`, subagents, and unrestricted filesystem APIs are not exposed.
7. **Isolated source extraction**: PDF, DOCX, XLSX, and PPTX source parsing runs in a one-shot packaged Worker rather than Electron main. The parent performs a stable 5 MiB read and enforces a 15-second hard deadline; the Worker has V8 heap/stack bounds, Office ZIP expansion/ratio guards, a 200-page PDF limit, XLSX sheet/row/cell preflight, linear PPTX text scanning, and a 180k-character result cap.
8. **Policy bridge**: `workspaceDeliveries` policy gates run-output writes, workspace registration, workspace writes, and extension allowlists independently; direct project workspace writes and workspace delivery registration are opt-in, not default-open.
9. **UI**: the Partner artifact rail now has an `Outputs` tab backed by `DeliveriesPanel`, with bounded rich preview for known formats, delivery metadata, reveal/copy-path actions, checkpoint detail, diff preview, and rollback. XLSX, DOCX, and PPTX parsing uses disposable Web Workers with deadlines and validated output DTOs; PDF page shells are lazy and page-count bounded.
10. **Steering and prompts**: Partner profile now describes workspace-first delivery, checkpointed lightweight writes, and bounded helper-code/toolmaking boosts while still escalating heavy codebase mutation to Coder.
11. **Verification**: schema tests, real-handler VM escape regressions, Unicode PDF parsing, Office/PDF source extraction and ZIP-bomb rejection, source/preview Worker timeout and output-limit tests, CJK search, queue watcher races, session-runtime rollback, concurrent-write and hard-link alias tests, corrupt-store preservation, third-party Office reopen checks, typecheck, lint, smoke build, and Playwright coverage.

### Runtime Ownership and KodaX 0.7.67 Migration Gate

Space v0.1.30 resolves the exact published `@kodax-ai/kodax@0.7.67` package. The Partner tranche first validated the Runtime and Worker isolation primitives introduced in 0.7.66; the final release extends that baseline through the 0.7.67 external-agent plane. Packaging requires all Runtime/semantic/constructed-handler sidecars, packaged smoke executes the Runtime and constructed-handler Workers directly from `app.asar`, and isolated compatibility coverage imports the published subpath, creates an `embedded + worker` Runtime with `requirements.hardDispose`, round-trips a session, confirms inline downgrade is rejected, and exercises Reference Agent registration, discovery, task start, events, and terminal results.

KodaX 0.7.66 materially improves the boundary: a private Runtime can live in a disposable V8 Worker with resource limits and hard close, and SDK constructed handlers now run in dedicated Workers with reverse tool RPC and hard timeout termination. These are real capabilities and replace the earlier assumption that 0.7.66 had only inline/cooperative execution.

They still do not directly replace `run_partner_helper`. Runtime Worker isolation moves the whole private session/runtime owner, not one Partner helper invocation. Daemon/Worker run options are DTO-only and reject Space process-local callbacks, while `KodaXRuntime` exposes no general `execution.create/start/abort/terminate` service for arbitrary helper programs. For v0.1.30, the Space-owned one-shot Worker therefore remains the effective per-helper boundary and continues to own the cloned input/file snapshot and serialized write journal. Space also retains Partner workspace snapshots, path/credential policy, approvals, and final journal application.

The remaining generic execution-plane gap is tracked as Known Issue 022. It is a future migration/duplication-reduction item, not a release blocker and not an unresolved form of the v0.1.30 VM escape. A Worker provides fault/resource isolation, but its V8 heap limits do not form a hard bound for every native/external allocation. Genuinely hostile third-party code or documents still require a process/OS sandbox backend; no Runtime contract may silently downgrade such a request to a shared Worker or host execution.

### Acceptance

- Partner can produce at least one arbitrary, non-whitelisted deliverable path in its run output workspace and have it appear in the delivery browser.
- Unknown file extensions are treated as valid deliverables with metadata, location details, reveal, and copy-path actions in the Outputs browser; richer preview/export/attach actions can build on the registry.
- Existing `docx/pdf/xlsx/pptx` writer flows still work.
- A workspace-session write creates a checkpoint before mutation and supports diff plus rollback.
- Source/config edits remain guarded by policy and should route to F113 proposal for strict/sensitive paths unless a local policy explicitly allows checkpointed direct edits.
- Partner can create small helper-code/toolmaking outputs that generate, transform, package, or validate a deliverable inside the run workspace via bounded `run_partner_helper` execution without exposing full Coder mutation tools.
- Playwright Electron E2E covers Partner Outputs visibility for arbitrary file output, checkpoint rollback, and post-rollback delivery registry refresh; Office writer and reviewed proposal fallback remain covered by targeted Electron tests with broader scripted E2E as follow-up.
