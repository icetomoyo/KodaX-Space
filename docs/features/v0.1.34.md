# KodaX Space v0.1.34 — Runtime Safety and Desktop Lifecycle Hardening

> Status: Released 2026-07-30
>
> Space package baseline: `0.1.34`
>
> KodaX baseline: exact npm Registry `@kodax-ai/kodax@0.7.78`
>
> Release owner: KodaX Space

## Version outcome

`v0.1.34` is a safety and stabilization release over the published `v0.1.33`.
It does not ship the previously scheduled native document Skill suite. That
independently authored F137/F139 lane is now scheduled for
[v0.1.61](v0.1.61.md) so this release can describe only code that exists.

The release closes five concrete gaps:

1. optional MCP, A2A, or Extension configuration can degrade without taking
   down the core Coder Runtime;
2. a real application exit either stops the Space-owned daemon or restores a
   visible Space control surface;
3. Space-started daemons have an explicit orphan-idle recovery contract;
4. packaged command-sandbox helpers resolve from physical resources rather
   than from `app.asar`; and
5. startup/shutdown and restored-history projection no longer produce
   misleading transient UI.

## Runtime capability contract

Space connects Coder through the public Runtime facade and negotiates behavior
from capabilities, not from a minimum daemon SemVer. The current release probe
requires the existing shared-session, interrupt, Actor, compaction, transcript,
permission, daemon-management, and external-agent contracts plus:

- `daemonOrphanExit:1`;
- `integrationConfigResilience:1`;
- `runtimeAutoModeGuardrail:4`; and
- `skillLearningLoop:1`.

The exact 0.7.78 dependency is still a release-integrity requirement. It proves
which bytes were packaged; it is not a substitute for live capability
negotiation. A compatible lower identity version with every required contract
may attach, while any daemon missing a required contract is rejected.

Runtime health projection remains bounded. Space exposes identity, connection
state, capability versions, counts, revisions, timestamps, and named diagnostic
codes. It does not expose prompts, responses, integration secrets, file
contents, or sandboxed command output through `space.version` or diagnostics.

## Resilient integration configuration

KodaX owns the canonical user integration documents:

- `~/.kodax/integrations/mcp.json`;
- `~/.kodax/integrations/extensions.json`; and
- `~/.kodax/integrations/a2a.json`.

An invalid optional update retains the Runtime's last-known-good state and
returns a bounded domain diagnostic. Space polls management health every two
seconds while connected because 0.7.78 does not yet publish a management-change
event. A poll failure retains the previous projection and emits one bounded
warning; it does not disconnect Coder.

Settings shows each integration domain's source, revision, watcher state, last
valid reload time, and diagnostic. Mutations report whether the live Runtime
applied the saved file (`applied`, `not-required`, or `failed`). A concurrent
revision conflict asks the user to reload and retry instead of overwriting newer
data.

The Space MCP Manager validates and constructs a complete candidate manager set
before swapping its cache. Invalid global or project configuration leaves the
previous managers live. Local and daemon reload results are reported
independently so a partial failure cannot be presented as success.

## Auto guardrail and sandbox truth

Auto guardrail v4 keeps manually or persistently selected Rules mode sticky.
When the LLM classifier times out, returns a Provider error, or violates its
output contract, Runtime retries once. If that retry also fails, only the
current tool call uses an Accept-edits-compatible permission fallback;
`engine=llm` remains unchanged.

Space projects only bounded side-query facts such as Provider/model, stage,
duration, byte sizes, retry count, and failure category. The classifier prompt
and response are never projected.

KodaX 0.7.78 also publishes a fail-closed command-sandbox facade and structured
tool sandbox observations. Space displays:

- `Sandboxed` when the command ran through the available containment backend;
- `Sandbox fallback` when the backend was unavailable and the ordinary
  permission policy governed execution; and
- `No sandbox` when no sandbox attempt applied.

These facts are activity metadata, not transcript content. F138 remains planned
because command containment does not by itself provide document staging,
credential isolation, native-resource limits, packaging, and platform
qualification.

Packaged builds place ASRT and its runtime dependency chain under physical
`resources/node_modules` paths. Package smoke imports the public sandbox
facade, runs the doctor, rejects `app.asar`/`ENOENT` helper paths, and verifies
the Windows executable or Linux seccomp helper required by the platform.

## Cross-platform complete exit

All ordinary Windows, macOS, and Linux exits enter one coordinator:

1. close Coder admission synchronously and drain already admitted operations;
2. inspect Space-local Partner, Workflow, permission, AskUser, queue, and
   External Agent work;
3. inspect daemon work and other clients;
4. keep the visible control surface alive while performing a revision-fenced
   safe stop; and
5. exit Electron only after `stopped:true` or an independently verified
   unowned Runtime profile.

A blocker, timeout, malformed stop response, late ownership race, or command
failure reopens admission and restores/relaunches Space with a bounded warning.
The Windows tray no longer exposes “Quit Space, keep Runtime”, which could
intentionally remove the only product-visible control surface.

When Space auto-starts the Coder daemon it supplies a 30-second orphan grace.
After the last logical client disconnects, the daemon waits until governed work
is idle and then stops. Another client cancels the reaper. CLI-started
persistent daemons keep their prior behavior.

Issue 133 remains visible until packaged macOS/Linux process-level acceptance
and the upstream asynchronous orphan-cleanup retry/verification gap are closed.
The current release must not claim that `daemonOrphanExit:1` alone proves
eventual process exit after every host cleanup failure.

## Startup, shutdown, and history UX

Electron main owns a single startup overlay from the first visible frame until
the renderer application is ready. The old renderer loading screen was removed,
so there is no flash between a randomized boot splash and the real shell.
Shutdown uses the same main-owned visual boundary while the complete-exit
coordinator is still able to restore the application.

Renderer load scheduling, boot readiness, reveal, recovery, and shutdown are
generation-fenced. A stale window or navigation cannot satisfy the current
startup gate.

History replay now uses canonical positional transcript projection. When a
completed interrupt response precedes a newly sent query, the earlier assistant
reply remains above that query after switching Sessions or restarting Space.
The fix does not infer new transcript identity or rewrite Runtime history.

## `kodax_manual` requirements

The injected Space self manual must answer the following accurately:

- which Coder Runtime mode is recommended and how safe switching works;
- which 0.7.78 capabilities are required and why SemVer is not the live gate;
- how integration last-known-good, revision, watcher, reload, and recovery work;
- what `Sandboxed`, `Sandbox fallback`, and `No sandbox` mean;
- how Windows tray close differs from a real cross-platform exit;
- how orphan recovery is scoped and how to stop a legacy invisible daemon; and
- which limitations remain open under Issue 133 and F138.

Every SDK-recommended underlying topic remains present. Same-id Space overlays
must include the exact installed `MANUAL_REGISTRY` body, aliases, and sources.

  exact Registry `0.7.78`;

  Runtime compatibility, manual, and history replay suites pass;

  contains the exact local and GitHub evidence.
