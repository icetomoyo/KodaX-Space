## FEATURE_274: 结算认证身份化（turnId presence + 源静止放行）

### 1. 需求概述

**问题**：Run 结束后 Space 决定 canonical 历史页能否接管该轮显示的认证机制，此前基于时序/代数证据（generation 计数、读次序）。用户可见后果即 Issue 204：第二轮回答 agent 实际已产出，但 raced 的认证把已画内容交给缺 assistant 行的 canonical 壳，Ctrl+R 才能找回。202/204/205 的反复修补同根：认证靠猜时序，每种竞态都是一种新的猜错方式。

**方案**（决策记录见 [ADR-009](ADR/ADR-009-settlement-certification-identity.md)）：把认证锚在身份证据上——

1. terminal-scoped newest 页包含 `kind !== 'user'` 且 `turnId` 匹配该 terminal Run 的条目，该读才认证该 Run（身份确认）；
2. 身份未确认时，连续两次 `page.revision` 相同（持久化已收敛）仍无该 turn 的行 → 结构性放行（出错轮次本无可持久化内容），至多多 1 次重读；
3. `decideTurnProjectionAuthority` 的空 durable 内容守卫（Issue 204 修复）永久保留为独立兜底不变式；
4. 其余情况保持现有重试梯与 fail-open，不新增错误态。

### 2. 影响范围

- `apps/desktop/renderer/src/store/runtimeProjectionState.ts` — `RuntimeTerminalEvidence` 增加可选 `turnId`；live/profile 两个构造点补齐；新增纯函数 `terminalEventEvidence`（把 App.tsx 直连 terminal 事件的证据构造提为可单测纯函数，含从 fresh live `lastTerminalRun`（runId 匹配）补 turnId）
- `apps/desktop/renderer/src/shell/sessionHistoryPaging.ts` — 证据组与 request scope 每 run 携带 `turnId` + `lastSeenRevision`；`completeTerminalHistoryRequestScope` 身份感知完成判定
- `apps/desktop/renderer/src/App.tsx` — 直连事件证据改用 `terminalEventEvidence`
- 测试：`apps/desktop/electron/test/session-history-paging.test.ts` 新增决策分支用例；`runtimeProjectionState` 证据构造用例
- 文档：`docs/ADR/ADR-009`、`docs/KNOWN_ISSUES.md`（204/205 交叉引用）、`CHANGELOG.md`

### 3. 技术方案

- 纯 renderer 行为，零 SDK/IPC/主进程语义改动；`spaceRuntimeRunProjectionSchema.turnId`、`SessionHistoryItem.turnId` 均为既有字段，无 schema 变更。
- 失败方向全部 fail-open：turnId 缺失 → presence 检查跳过（现状行为）；源静止两次后仍无行 → 放行；重试梯上限（30 次 → phase error → 回 pending）不变。
- mock 路径（`KODAX_FORCE_MOCK`）无 runtime 证据，不进认证链，e2e 行为不变。

### 4. 接口契约

```ts
// runtimeProjectionState.ts
interface RuntimeTerminalEvidence {
  readonly sessionId: string;
  readonly runtimeId: string;
  readonly runId: string;
  readonly phase: string;
  readonly cursorSeq: number;
  readonly startedAt?: number;
  readonly completedAt?: number;
  readonly transcriptRevision?: string;
  /** 该 terminal Run 产出 turn 的身份；缺失 = presence 检查跳过（fail-open）。 */
  readonly turnId?: string;
}

/** App.tsx 直连 terminal 事件的证据构造：runtimeEvent origin 无 turnId，
 *  从 fresh live 投影的 lastTerminalRun（runId 匹配）补齐；补不到为 undefined。
 *  runtimeEvent 缺失 / 连接非 fresh / origin runtime 不匹配 → undefined，
 *  调用方回退 authoritative 候选路径。 */
function terminalEventEvidence(input: {
  readonly kind: 'session_complete' | 'session_error';
  readonly sessionId: string;
  readonly runtimeEvent:
    | { readonly runtimeId: string; readonly runId: string; readonly seq: number }
    | undefined;
  readonly connection: SpaceCoderConnectionProjectionT;
  readonly liveBySession: Readonly<Record<string, SpaceSessionLiveProjectionT | undefined>>;
}): RuntimeTerminalEvidence | undefined;
```

```ts
// sessionHistoryPaging.ts（模块内部状态）
interface TerminalHistoryWorkflowGroup {
  readonly runtimeId: string;
  readonly nextGeneration: number;
  readonly runs: readonly {
    readonly runId: string;
    readonly generation: number;
    readonly status: 'pending' | 'in-flight' | 'completed';
    readonly turnId?: string;
    /** 上次身份未确认尝试时的 page.revision；两次相同 = 源静止 → 结构性放行。 */
    readonly lastSeenRevision?: string;
  }[];
}

// run 完成条件（completeTerminalHistoryRequestScope，在既有 generation/runtimeId 棚栏之上）：
//   无 turnId            → 本次读即完成（现状）
//   turnId 身份在页内     → 完成（存在 kind !== 'user' 且 item.turnId === run.turnId 的条目）
//   page.revision === run.lastSeenRevision → 结构性放行完成
//   其余                  → 记录 lastSeenRevision，保持 pending → 现有重试梯
```

### 6. 验收标准

- 用户故事：一轮回答完成后立即追问，已显示的回答不消失、无需 Ctrl+R 找回；Runtime 结算与渲染竞速时最终内容与 canonical 一致（不重复、不丢行、不空壳）；出错轮次（无 assistant 输出）结束时 UI 立即恢复，不卡加载；加固不引入可感知的结算/切换延迟（至多 1-2 次有界重读）。
- 单测决策分支（session-history-paging.test.ts，TDD 先红后绿）：turnId 身份在页内 → 该读 settle；页内无匹配 → 保持 pending 重读；连续两次同 revision 仍无 → 结构性放行 settle；revision 前进 → 继续 pending；无 turnId 证据 → 一次读 settle（现状）。第 6 分支（turnId/lastSeenRevision 穿越 scope 重捕保留）由结构性放行用例隐式覆盖——其第 3 次读依赖第 2 次记录的 lastSeenRevision 穿过 scope 重捕。

- e2e：mock Playwright 套件全绿；r6 真机 Issue 204 复现场景在 provider 恢复后补跑（已知环境阻塞，不阻塞合入）。

## FEATURE_275: 身份锚定转录模型（重写 workstream，P0-P4 分期）

### 1. 需求概述

转录管线是产品缺陷最密集的子系统：6 月以来 103 个 commit 触及 appStore.ts，一周内 Issue 202/204/206 三个 High 连续入场，同族 136/142/184/193 四个 In Progress，加上 Issue 207（fold 顺序不稳定被 alpha.5 收敛 tick 放大）。根因（两轮独立调查交叉确认）：

1. **双职责缓冲**：`userMessagesBySession`/`eventsBySession` 既当瞬时流式缓冲，又当已入档内容的本地缓存（影子副本永不回收），靠约 1900 行 fail-closed fold 闸门条件性隐藏，任何门失守即重复/乱序气泡（Issue 207 实证：投递边界铸造 ord=max+1 的幽灵气泡，sentAt=墙钟，落到最终回答之下）。
2. **排序双尺子**：composeMessages 的 user 槽按 sentAt 排序（SDK admission/本地 Date.now/restore 服务端三种时钟混排），assistant 事件按 buffer 位置消费。

目标架构：**身份锚定转录模型**——canonical 页（分页读回）是持久层显示投影；live 流只有一个瞬态尾部（未入档的开放轮次），获得结算认证后即退役；fold 闸门体系退化为"live 尾部入档"单一动作；compose 的 user 槽按显式 sortKey（canonicalIndex/turn 序）渲染，sentAt 仅用于 notice 交织与 footer 显示。决策记录：[ADR-009](ADR/ADR-009-settlement-certification-identity.md)（含前景收敛补充）。

### 2. 影响面（实测）

- 重写核心区：appStore.ts（9,570 行，其中对账机器 ≈1,900 行**零外部符号消费者**，可在 store 边界内整体换心）、composeMessages.ts（838 行）、sessionHistoryPaging.ts（1,188 行）、runtimeSnapshotHydration.ts（893 行）
- 消费者环：ConversationStreamV2（3,023 行，四级 useMemo + prepend 锚点）、turnIndex 选择器与 fork/rewind（historyBoundary 跨 IPC 冻结）、transcript 搜索、ask-user 卡锚定、queued inputs/中断/取消（originOperationId 认领）、notices、F144 虚拟化（规划的 canonical 页契约恰为本架构产物）
- 行为契约爆炸半径：≈860 处测试断言编码现语义；安全网 2,853+48+317 单测 + 93 e2e + 1,320 行对抗性复现套件

### 3. 技术方案（expand-contract 五阶段，每步独立合入全绿）

- **P0 验收资产前置（S）**：落地"刷新等价性"属性测试（渐增路径终态 == 冷 reload 投影，先以 allowlist 记录已知偏差）；从 lineage-repro 提炼 golden fixture；202/204/206/207 回归用例挂常驻门
- **P1 排序单一化（M）**：composeMessages user 槽改显式 sortKey（canonicalIndex ?? historyTurnIndex ?? buffer 序，sentAt 兜底）；sentAt 退为 notice 交织 + footer。验收：restore-only 会话等价偏差清零；fork/rewind e2e 不动
- **P2 结算即退役（L）**：既有认证链上把"打标隐藏"升级为"直接删除已认证重复行"；先双写 A/B 等价再删隐藏路径。验收：稳态 buffer 无 hiddenProjectionDuplicate 残留；**认证即回收 shadow**（rememberCanonicalizedHistoryLiveOwners 时从 baseline 删除已收编 live 行，改记墓碑）
- **P3 双职责拆分（L）**：store 拆为 canonicalPageBySession（可替换投影）+ liveTailBySession（仅开放轮次）；prependSessionHistory 语义变为"安装页"；composeMessages = render(page, tail)；公共 action 签名不变（消费者零改动）。验收：内存有界（超长会话 buffer 不随时长线性增长）；等价 allowlist 清零
- **P4 fold 退役 + F144 使能（M）**：删除 stabilize*/foldStrongIdentity*/historyLiveBaselines 死路径；发布 canonical 页契约（revision/sourceRevision/cursor/data_changed）供 F144 窗式虚拟化开工
- **alpha.6 热修（本版本内，已落地）**：幂等守卫（同 revision newest 读跳过 fold 重跑）+ 投递边界铸造改"绑定优先"（边界事件缺显式 `turnUserOrdinal` 即为自解析回放信号；同 turnId 且同内容的 owner 已存在（live 或 canonical）时绑定而非铸新。带显式序号的合法同文本打断仍铸新 owner）

#### 机制基线（2026-09-07 客户 session 20260816_110200_432759c1554ee5 实证 + 代码钉死）

alpha.6 后乱序仍在（assistant 侧变体，两例），持久层逐条验证健康、Ctrl+R 恒正确。已钉死的机制：

1. **不变量**：渲染配对是"位置序"、user 槽顺序是"sentAt 序"，两者仅在特定写入点人工一致。破坏点：B1 `reconcileRuntimeDeliveredInputs`（boundary 按 deliverySeq 定位但 owner 行 append 到 users 末尾且 sentAt 改写服务器时钟）、B2 canonical 页安装接缝（canonical/live 两平面各自有序、跨接缝无全局序）、帮凶 `stabilizeCanonicalPageHeadBeforeEarlierLiveTurns` 的 `turn.sentAt < canonical.sentAt` 时间比较（服务钟超前时误搬 live 轮）。
2. **内容清洗**：certified canonical 合并（`decideTurnProjectionAuthority` → `mergeIdentityProvenTurnProjections`）清零错位槽的 live 文本/工具，唯一护栏只查"durable 段为空"、不查"非空但 foreign"；`hiddenProjectionDuplicate`/`historyNoAssistantSegment` 可整轮隐藏。
3. **快照重水合**：终态快照下 `filterEffectiveOutputSegmentEvents` 对带 providerRequestId 且无 segment-start 标记的 delta 无条件判 stale 删除；合成补发被 `activeRun !== undefined` 门跳过（纯 lastTerminalRun 快照只删不补）；fold 不清孤儿 live 残件 → 芯片翻倍/正文丢失/尾句 ghost（携带 canonical 时间戳）。
4. **alpha.6 两守卫与上述机制作用域不相交**（只覆盖 user 铸造与同 revision 重装），故对 assistant 侧变体无效——热修定位本就是止血，根除靠本 feature。
5. **失败门已入库**：`transcript-order-real-lineage-repro.test.ts` 用例 L（变体 B 精确复现"canonical a1/a2 骑到 q1 之上"；主配方暴露 closed live 残件重复渲染；变体 C/D 复现尾句丢失/ghost 复制）与用例 M（芯片 8≠4 + 正文丢失，三点叠加机制），当前 skip，P1/P2 落地后转绿为验收。
