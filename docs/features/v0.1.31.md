# v0.1.31 - Runtime, Platform Trust, and Semantic Control

> Status: Released 2026-07-12
> Features: F116, F055, F069, F120
> Baseline: Space `v0.1.30`; final SDK dependency exact published KodaX `0.7.68`
> Implementation plans: [F116 Runtime plan](v0.1.31-implementation-plan.md), [F055/F069 platform-trust plan](v0.1.31-platform-trust-implementation-plan.md), and [F120 semantic-control plan](v0.1.31-f120-implementation-plan.md)

## Batch decision

Space will adopt the public `@kodax-ai/kodax/runtime` facade as its long-term host boundary. The first migration is **inline-first**: it replaces duplicated host/session/event/catalog plumbing without claiming Worker or daemon isolation for Space-owned callbacks, Partner tools, profiles, and permission behavior that are not transport-safe yet.

The release combines the Runtime contract migration, a standard packaged application origin, bounded redacted diagnostics, and the governed semantic-control plane. Space keeps its zod IPC boundary and renderer stores; KodaX remains the runtime truth and natural-language interpreter, while Space remains the authority for application resources, diagnostics policy, action definitions, confirmation, execution, undo, and receipts.

### KodaX 0.7.68 integration

The exact npm `@kodax-ai/kodax@0.7.68` package and matching source tag add FEATURE_260 Memory Agent and the `/experimental-memory` export. Space 0.1.31 probes that public shape, reports it separately in `space.version` and diagnostic exports, attaches metadata-only memory lifecycle callbacks, and updates the white-label `kodax_manual`. Top-level managed runs still let KodaX own zero-wait scoped recall, the read-only `memory_recall` tool, Outcome Digests, and bounded review over the existing F228 control plane.

This is not the full F117 desktop host. The exact 0.7.68 release treats a missing or malformed Memory Agent contract as a startup failure. Full Episodes/Activity/correction/forget/purge UX remains planned. Because the 0.7.68 coding path currently auto-activates memory work without a dedicated host disable option, in-process Memory Agent rollback is still an upstream contract gap rather than a Space toggle.

## FEATURE_116: Runtime Host Adapter and Capability Negotiation

### User outcome

- Coder and Partner sessions continue to behave as they did in `v0.1.30`.
- Managed runs and Runtime-backed transcript/compact/fork/rewind operations are reached through one explicit adapter; Workflow and other product-specific capabilities remain named Space bridges.
- Diagnostics explain which Runtime capabilities are active or missing instead of inferring support from an SDK version string.

### Current evidence and gap

Space now initializes one inline Runtime host during Electron startup and routes new `RealKodaXSession` managed turns through `runtime.runs.start()`. `KodaXHost` remains the Space session registry and compatibility projection: it keeps titles, in-flight state, resume/list filtering, Space-only settings, local notices, and cleanup semantics while selected durable operations use the adapter.

The published Runtime facade already exposes sessions, runs, events, permissions, workflows, config, catalog, MCP, artifacts, status, diagnostics, administration, dispatchable agents, and agent tasks. However, Space also injects process-local Partner tools, an `agentProfile`, callbacks, and permission policy. Those functions must not be assumed to cross Worker or daemon DTO boundaries.

Implementation discovery also confirmed that the public facade does not yet replace every Space owner: inline capability discovery is structural rather than a first-class service; per-session `agentMode`/`autoModeEngine` are not Runtime settings; Runtime MCP lacks Space start/stop/log lifecycle; and Runtime External Agents cannot reuse Space's existing durable store/reconcile wrapper. These remain explicit `space-bridge` capabilities in this release rather than parallel Runtime stores.

### SDK and capability contract

Minimum Runtime contract verified during F116 was 0.7.67; the final release resolves exact `@kodax-ai/kodax@0.7.68` and additionally requires FEATURE_260 policy `f260-v0.7.68.2`.

Required services:

- `runtime.sessions`
- `runtime.runs`
- `runtime.events`
- `runtime.permissions`
- `runtime.workflows`
- `runtime.config`
- `runtime.catalog`
- `runtime.mcp`
- `runtime.artifacts`
- `runtime.status` / `runtime.diagnostics`
- `runtime.admin.agentRegistrations`
- `runtime.agents` / `runtime.agentTasks`

Required capability probes:

- create/load/list/paginate/fork/rewind/archive/delete session parity;
- per-session provider/model/effort/thinking/permission/execution-cwd settings;
- ordered rich events and bounded replay;
- client-brokered permission request/response;
- workflow snapshot/lifecycle parity;
- catalog/MCP/extension discovery and reload;
- Reference External Agent administration, preflight, task lifecycle, input, cancellation, and reconciliation.

### Architecture

Add a Space-owned `RuntimeHostAdapter` behind the existing IPC handlers.

```text
renderer
  -> zod IPC
  -> RuntimeHostAdapter
      -> KodaX Runtime facade (inline first)
      -> Space Partner capability binder
      -> Space policy/audit/artifact services
```

Migration rules:

1. The renderer does not receive Runtime objects or raw errors.
2. Existing IPC channel shapes remain stable unless a separate schema migration is documented.
3. Runtime event sequence/correlation becomes the source for new run projections; old callback mapping remains only as a compatibility bridge during migration.
4. Space-owned Partner tools and profiles are bound in the owner process. Worker/daemon mode is enabled only after a public registration/transport contract proves parity.
5. `KODAX_TEST_ONBOARDING`, profile/home redirection, and real-user session isolation remain release gates.

### Migration slices

1. Initialize one `RuntimeHostAdapter` after profile/home setup and close it through the existing shutdown watchdog.
2. Keep renderer IPC stable and expose one redacted Runtime host capability row through `space.version`.
3. Route transcript, compact, fork, and rewind through Runtime while retaining Space list/resume/title/delete compatibility projections.
4. Route managed run start and abort through Runtime; reuse the existing Partner, permission, AskUser, artifact, workflow, extension, queue, and event callbacks.
5. Normalize Runtime result failures/cancellation into exactly one Space terminal event; never replay a started run on legacy.
6. Keep Workflow pause/resume/stop on `WorkflowController`: the raw Runtime manager does not preserve Space's stop reason, immediate cancellation projection, and durable lifecycle semantics.
7. Keep MCP processes and External Agent durable storage on their existing Space owners, and keep Worker/daemon unavailable for this release.

### Security boundary

- Capability negotiation is fail-closed; unsupported actions are hidden or return an explicit capability error.
- Renderer input remains zod-validated and cannot select arbitrary Runtime endpoints, profile directories, callbacks, factories, or credential brokers.
- Daemon connection remains off by default in this release.
- Worker isolation is not described as an OS security sandbox.
- External Agent actor/session/project context remains host-derived.

### Explicit non-goals

- No default daemon ownership.
- No forced Worker migration.
- No new session database or transcript format.
- No duplicate MCP, Skill, workflow, memory, or External Agent store.
- No renderer-visible Runtime administration escape hatch.
- No behavior change justified only by deleting old code.

### Automated acceptance

- Contract tests run the same session/settings/event/workflow/catalog assertions against the legacy adapter and new Runtime adapter.
- Coder and Partner tool visibility/profile metadata remain equivalent.
- Permission, ask-user, artifact, workflow, session-history, and External Agent regression suites remain green.
- Runtime capability snapshot is deterministic and safe to expose through diagnostics.
- Packaged smoke uses the published SDK, not a source link.
- Typecheck, unit tests, Electron E2E, build, and packaged smoke pass.

### Rollout and rollback

- Remove the legacy path only in a later reviewed cleanup after `v0.1.31` stabilizes.

## FEATURE_055: Packaged Renderer `app://space` Origin

### User outcome

Packaged Space loads its renderer and application resources from the privileged standard origin `app://space/`, rather than treating the application as arbitrary local `file://` content. Development continues to use the explicit Vite origin.

### Design

- Register `app` as a privileged standard, secure, CORS-enabled scheme before Electron ready.
- Serve only files below the packaged renderer root for the exact `space` host.
- Canonicalize and decode request paths once, reject malformed encoding, traversal, encoded separators, NUL/control characters, directory requests, unknown hosts, and paths that escape through symlinks or aliases.
- Return bounded HTTP-style responses with explicit MIME types, `nosniff`, and no directory listing.
- Load main and artifact windows from `app://space/index.html`; artifact identity stays in the hash and its document sandbox/CSP remains unchanged.
- Update navigation guards, CSP assumptions, boot/recovery diagnostics, packaging smoke, and tests to recognize the application origin without allowing `app://` to proxy user files.

### Security boundary

- `app://space` serves immutable packaged renderer assets only.
- User files remain data references handled by existing validated file/artifact services.
- Unknown hosts, non-canonical paths, and renderer-root escapes fail closed.
- HTTPS links continue to open in the system browser; auxiliary windows cannot navigate to arbitrary application or local paths.

### Acceptance

- Production main and artifact windows boot from `app://space/index.html` on Windows, macOS, and Linux packaging layouts.
- Traversal, alternate host, encoded separator, malformed encoding, symlink escape, directory, and missing-file fixtures fail closed.
- CSP and navigation tests pin the production application origin.
- Existing interactive HTML artifact sandbox behavior remains unchanged.

## FEATURE_069: Structured Main-Process Logging and Diagnostic Export

### User outcome

Space keeps a bounded, structured, locally stored diagnostic record for startup, Runtime capability state, workflows, providers, permissions, Partner, external agents, updater state, and recoverable failures. A user can explicitly export a redacted diagnostic bundle without exposing prompts, keys, credentials, or private document content.

### Design

- Add one main-process logger with `debug`, `info`, `warn`, and `error`, structured component/event fields, safe correlation IDs, release/SDK/platform metadata, and deterministic serialization.
- Redact before serialization and disk write. Cover provider keys, authorization/cookie headers, URL userinfo and secret query keys, configured secret environment values, bearer/token-shaped values, home/profile paths, and fields classified as prompt/tool/document content.
- Use size-bounded append logs with atomic rotation and bounded retention. Logging failure must never block application startup.
- Install a console bridge early so existing production `console.*` calls reach the structured sink during incremental migration; migrate high-value paths to direct logger calls and enforce a scoped `no-console` rule for new production code.
- Accept renderer diagnostics only through a capped zod envelope with an allowlisted component/event/level shape; the renderer cannot select paths or arbitrary structured keys.
- Export a user-selected ZIP containing a manifest, redacted recent logs, version/capability snapshot, updater/channel state, and known degradations. No remote upload is added.
- KodaX tracing remains separately owned; Space records correlation and capability state, not duplicate prompts or tool payloads.

### Security boundary

- Metadata is the default; task content is excluded.
- Redaction precedes every sink and export path.
- Diagnostic export requires an explicit user gesture and reports included categories.
- File count, individual file size, total export size, and retention are bounded.
- Corrupt or unavailable logs degrade to an explicit manifest diagnostic rather than breaking startup or export.

### Acceptance

- Secret fixtures never appear in log files or exported bundles.
- Rotation/retention survives restart and concurrent writes without unbounded disk growth.
- Renderer envelopes reject unknown keys, oversized strings, and untrusted component names.
- Runtime/workflow/provider/external-agent failures can be correlated without raw task content.
- Exported ZIP contents and size are deterministic and bounded.
- Typecheck, lint, unit/E2E, production build, packaging, and packaged boot pass with logging enabled.

## FEATURE_120: Natural-Language Space Control

### User outcome

After a Provider is configured, a user can explicitly ask Coder or Partner to perform a supported Space control such as setting the theme, opening a registered Settings section, selecting a shell layout preset, or changing a non-sensitive default. KodaX selects one typed Space action; Space validates and executes it through the same semantic executor used by deterministic UI entry points and returns a local, inspectable receipt.

This is not generic UI automation. F120 exposes no DOM selector, click coordinate, arbitrary IPC channel, arbitrary Zustand key, filesystem path, URL, shell command, credential value, or permission answer.

### Release scope

`v0.1.31` delivers a bounded vertical slice, not immediate model control over every existing control:

- build and freeze a complete classification manifest for Settings rows, top-level Shell controls, Command Palette actions, and local slash mutations;
- implement the shared schema, registry, main authority service, and primary-renderer broker;
- converge appearance, registered navigation, panel/Settings opening, semantic layout presets, and explicitly reviewed non-sensitive defaults;
- register `space_control_inspect` and `space_control_apply` only for action families whose deterministic parity tests pass;
- keep sensitive, destructive, native-picker, permission-answer, provider-secret, network-send, installer/update, and arbitrary project mutation controls user-only.

The complete inventory must be classified in `v0.1.31`, but executor migration may be staged. An action is LLM-visible only after its descriptor, owner executor, readback, surface policy, and parity fixture are complete.

### Contract and ownership

- Action IDs are stable product API and use desired-state semantics such as `ui.theme.set`; blind toggles are not LLM-visible.
- Shared zod schemas define bounded requests, availability, receipts, and IPC push/ack payloads. Tool JSON schemas are derived or mirrored with contract tests.
- Inspect returns only allowlisted safe state plus a short-lived precondition token bound to action, canonical arguments, trusted session/surface, owner instance, revision key, revision, and expiry.
- Apply revalidates schema, availability, trusted run context, surface policy, plan-mode policy, revision, token, and confirmation policy at the state owner.
- Main-owned state executes in existing main services. Renderer-owned state executes in the primary renderer through a bounded request/ack broker with timeout and stale-instance rejection.
- Exact retries are idempotent by `sessionId + toolCallId + actionId + canonical argument digest`; ambiguous or conflicting retries fail closed.
- Confirmation and undo are Space-owned UI operations. The model and AskUser output cannot confirm or invoke undo in this release.

### Capability gate

```text
F116 inline Runtime ready
AND SDK registerTool is available
AND tool execution context includes sessionId + toolCallId + surface
AND primary renderer broker is ready
=> F120 LLM tools may be exposed
```

Worker/daemon transport is not required for `v0.1.31`. If a gate fails, deterministic buttons, Settings, Command Palette, and slash paths remain available; Space does not fall back to regex intent parsing or replay a control request through another runtime path.

### Initial action families

| Family                                                                                                                              | `v0.1.31` policy                                                                      |
| ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Theme, language, surface, registered panel/Settings navigation                                                                      | First migration slice; desired-state actions; Coder and Partner where applicable      |
| Sidebar/Task Dock/focus layout presets                                                                                              | First migration slice after owner/readback fixtures exist                             |
| Reasoning default and other reviewed non-sensitive defaults                                                                         | Coder-only unless explicitly surface-compatible; no security widening in plan mode    |
| Permission default, Provider default, project/session organization                                                                  | Classified now; exposed only with reviewed confirmation/undo and parity coverage      |
| Credentials, permission/AskUser decisions, native picker results, destructive deletion, update/install, arbitrary paths/network/IPC | User-only or not-semantic; navigation to a safe Settings section may still be exposed |

### Security and failure rules

- The natural-language prompt and model-produced tool arguments are untrusted.
- Main derives the authoritative session, project, surface, primary renderer, and current availability; model-supplied identity is never authority.
- Partner visibility is filtered at inspect and enforced again at apply. Registering the multiplexed tool name does not grant every action to Partner.
- Plan mode admits only descriptor-marked UI-ephemeral actions and an explicit allowlist of non-security preference writes.
- A renderer timeout after a possible apply returns `unknown`; it is not automatically retried. One bounded readback may reconcile the receipt.
- Receipts and existing diagnostics contain only action IDs, safe localized fields, result class, timing, and correlation IDs; F120 does not depend on F069 structured logging.
- Packaged validation runs from the exact `app://space` origin. F120 remains architecturally independent of the renderer transport even though both ship in this consolidated release.

### Acceptance

- 100% of inventory entries have a reviewed classification and exclusion code where applicable.
- Every LLM-visible action has descriptor/executor/readback/parity coverage across deterministic UI and tool entry points.
- Missing `toolCallId`, wrong surface/session/project, stale revision, expired token, auxiliary renderer, reload, timeout, replay, and malformed arguments fail closed or return a truthful `unknown` result.
- Partner does not gain Coder shell/edit/write/workflow/subagent capabilities.
- Existing buttons, keyboard shortcuts, Settings, Command Palette, and slash behavior remain usable when LLM tool exposure is disabled.
- Typecheck, lint, unit/integration tests, Electron E2E, production build, and packaged smoke pass before the `v0.1.31` tag is created.

Detailed sequencing, file ownership, risks, and release gates are in the [F120 implementation plan](v0.1.31-f120-implementation-plan.md).
