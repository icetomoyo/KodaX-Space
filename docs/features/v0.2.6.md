# v0.2.6 - Durable Artifacts and Automations

> Status: Planned
> Features: F097, F110
> Depends on: F116 embedded Partner Runtime adapter, F121 Coder daemon/task ownership and host binding, F114 delivery/checkpoints, and F130 Partner Composer-First Skill Workspace; F110 also depends on F055 application origin and the existing ArtifactVersion store, while connected refresh additionally requires F096

## Batch decision

Space adds two local-first durable workflows: scheduled/manual Runtime dispatch and explicitly refreshable Partner artifacts. Both remain visible, permission-scoped, auditable, and tied to durable Runtime/task/result identities. They plug into the owning Coder or Partner surface rather than creating a new mode, dashboard entry, or generic workflow shell.

## FEATURE_097: Local Automations Scheduler

### User outcome

Users can create a local automation, run it manually, schedule it, inspect last/next run and task evidence, receive completion/failure notification, pause it, and understand the permissions it will use.

### Ownership

- Space owns schedule definitions and OS wake integration.
- KodaX Runtime owns sessions/runs/events/permissions/workflows/agent tasks.
- Every automation execution has a Runtime session/run/task identity and appears in global automation history. Coder executions retain their Task Dock projection; opening a Partner execution projects the live run into `Process`, registered outputs into `Results`, and governed workspace mutations into `Files`.
- Completion/failure notifications deep-link to the exact owning session/run and, when present, the authoritative result owner/ID. They do not open a generic activity panel detached from the task.
- Do not spawn an untracked `kodax --once` process as the primary architecture.
- `SurfaceRuntimeRouter` selects the execution owner before dispatch. Coder automations use the F121 daemon/task owner. Partner automations use the F116 embedded-inline owner launched and supervised by Space. An automation cannot migrate a session between owners, and a missing Coder daemon capability cannot fall back to an inline Coder process.
- `Settings > Automations` is the single definition-list/editor/history destination, with an explicit project filter. Eligible tasks/results may expose a contextual `Schedule this` action that opens the same editor; it does not add a Partner launcher card, work mode, top-level rail tab, or second dashboard. Run/history rows deep-link to the exact Coder Task Dock or Partner Results/Process/Files projection. Empty, disabled, adapter-unavailable, and read-only states remain reachable there.

### Definitions, runs, and material/evidence policy

Space owns two versioned automation records; neither is a Partner receipt:

- `AutomationDefinitionRevision` is immutable and discriminated by `surface`. Both variants contain the human name, enabled/trigger policy, project plus an opaque `taskInputRef`, provider/model/effort or inherit-default policy, requested permission-profile revision, explicit surface-owned context policy, concurrency/missed-run policy, and notification policy. The Partner variant may add an optional `expectedOutcome` and typed Partner result/refresh target `(owner, ownerId, ownerSubresourceId?, recipeVersionId?)`. The Coder variant carries only daemon/workspace/task target references and rejects Partner expected-outcome, F110 recipe, and Partner result-target fields.
- `AutomationRunRecord` identifies one attempted dispatch and records the definition revision, trigger instance, idempotency key, effective context-policy reference, surface-owned trace reference, bounded route/playbook builder-version reference, effective permission-policy reference, Runtime session/run/task correlation, status, timestamps, and links to resulting owner IDs plus surface-owned receipts when that surface defines them. A Coder run never creates an F130 Outcome receipt.

Editing, pausing, or resuming creates a new immutable definition revision and atomically advances the active revision pointer; every queued/run record pins the revision it evaluated. Last/next-run state is derived from the active trigger plus run records rather than rewriting historical revisions.

Secrets, prompt text, raw material/evidence paths/content, and provider/connector credentials are stored in neither record. The bounded task text/template and any path-bearing local task-attachment payload live behind `taskInputRef` in a separately access-controlled payload owner with explicit retention/deletion. `AutomationContextPolicy.materialBindings` stores only bounded opaque owner/version references to already governed material/evidence owners; it never embeds a raw path, title, content, excerpt, credential, or connector payload. Run records keep only references and effective non-secret facts.

For a Partner definition, context policy is independent from its optional expected outcome. Coder has context policy but no expected-outcome field:

```ts
type AutomationMaterialBinding = {
  materialRelationId: string;
  version:
    | { policy: 'pinned'; versionId: string }
    | { policy: 'current-at-run' };
};

type AutomationContextPolicy =
  | {
      surface: 'partner';
      retrievalScope: 'project-grounded' | 'selected-only' | 'general';
      materialBindings: readonly AutomationMaterialBinding[];
    }
  | {
      surface: 'coder';
      daemonContextPolicyRef: string;
      contextRefs: readonly string[];
    };
```

The policy discriminant must match the definition surface. For Partner, `project-grounded` is the default and `selected-only` never widens when material becomes stale or unavailable. A binding references an active F122 `ProjectMaterialRelation`, never a raw Artifact/Result owner or path. `current-at-run` is valid only when the target adapter advertises a current-pointer capability; immutable evidence snapshots and exact Result targets require `pinned` with a concrete version matching the relation target, and creation plus dispatch preflight reject every impossible combination. Each accepted Partner dispatch intersects bindings with current project, connector, retention, access/content, and workspace policy; it freezes the revalidated bindings into that new session's separate `selectedMaterialRelationIds` and exact/selector-backed selected evidence refs. Project availability does not imply task selection, and selection does not imply use. The execution resolves every used selector to an exact owner/version and records only actual use plus the access decision in the normal F124 trace. Removing a relation after admission blocks it for future trigger preflight but does not detach or implicitly cancel the admitted run; that run continues only under its frozen task selection, current access/content policy, and the normal owning-Runtime cancellation path.

Coder has no F124 retrieval scope. Its F121 daemon validates `daemonContextPolicyRef`, opaque context references, and the current allowed workspace under the admitted task owner, then records its own daemon/task context trace. Neither surface may fall back to the other policy or trace when validation fails.

Partner dispatch preparation is idempotent. For each distinct trigger instance, before enqueueing that run, main resolves the outcome exactly once: an explicit expected entry becomes `automation-declared`; otherwise the ordinary bounded pre-dispatch route may produce `inferred`; if it cannot, the receipt is permanently `unspecified`.

Main then writes the F130 session-presentation receipt exactly once and creates the `AutomationRunRecord` under the same client-request/idempotency boundary used to request Runtime dispatch. An accepted dispatch never lacks both records; a prepared record without an accepted dispatch is reconciled as not-started and never executes on retry. Every distinct accepted trigger instance—manual, one-shot, recurring, or an admitted missed-run execution—creates a new Partner session/run/task and exactly one Outcome receipt for that session; it never reuses or mutates a prior trigger's session receipt. Only redelivery or transport retry of the same trigger-instance/idempotency tuple resolves to the original run/session/receipt. The Outcome receipt contains no schedule, prompt, material/evidence selection, policy, reference, permission profile, provider/model/effort policy, credentials, or tool policy. Later results never mutate it.

Foreground composer dispatch and headless automation dispatch call the same versioned, main-owned pure F095/F130 route/playbook builder. The headless adapter accepts only bounded task/context/expected-outcome references, persists the builder/route/playbook versions in the run record, and never derives execution from renderer state, `BottomBar`, or the Outcome receipt.

### Safety

- Creation previews the effective permission profile and task target.
- Choosing, inferring, switching, or clearing a Partner expected outcome has the same bounded effect as an interactive F130 entry: it may select the registered prompt playbook and preferred result contract. It cannot change `permissionMode`, `autoModeEngine`, provider/model/effort policy, tool policy, retrieval/material scope, connector grants, allowed workspace, concurrency policy, or review policy, and the receipt itself is never execution authority.
- Every dispatch revalidates the definition revision against current capability, permission, connector, material/evidence access, retained-content integrity, and workspace policy. A historical grant or successful prior run is never reusable authority.
- High-risk/write/network behavior cannot be silently upgraded after creation.
- Credentials remain Runtime/connector/provider-owned.
- Concurrent and missed runs follow deterministic policy; default is skip/serialize, not unbounded catch-up.
- Disable/delete prevents future dispatch but preserves bounded audit/history.
- OS wake/scheduler failures are visible and do not create duplicate runs.

### Acceptance

- Manual, one-shot, recurring, missed, disabled, overlapping, failed, cancelled, and app-restart cases have deterministic tests.
- Every execution is traceable to one Runtime run/task and permission profile.
- User can stop a live run through the normal Runtime control path.
- No hidden background LLM work occurs when the automation is disabled.
- Partner automation E2E restores its bounded outcome receipt and Results/Process/Files projection after restart; Coder retains its Task Dock behavior.
- Missing or unsupported expected outcome metadata degrades to an unspecified/free-form Partner task and never blocks dispatch or broadens capability.
- Idempotent dispatch tests prove that retries create at most one Runtime execution, one `AutomationRunRecord`, and one immutable Outcome receipt.
- Recurrence tests prove distinct accepted trigger instances create distinct Partner sessions and receipts, while duplicate delivery of one trigger/idempotency key reuses its original run/session/receipt.
- Declared, inferred, and unspecified automation outcomes are fixed before dispatch and never mutate after later results.
- Definition revisions and run records restore after restart without being rendered as Outcome, Completion, or Route receipts.
- Definition-schema tests reject `expectedOutcome` on Coder, admit it only on Partner, and prove Coder automation never writes an F130 Outcome receipt.
- Definition-schema tests reject Partner result/F110 targets on Coder, reject invalid pinned/current material bindings, and require a supported current-pointer capability for `current-at-run`.
- Foreground/headless parity tests feed the same bounded request and assert identical route/playbook versions and preferred-result contract without starting a renderer.
- Partner context-policy tests prove selected-only never widens; active project relations, selected refs, and actually used refs remain distinct; selected-but-unused material never enters the used projection; and pinned/current-at-run bindings resolve deterministically. Revoked/unknown origin authority fails closed for origin/current-pointer reads, while an exact pinned retained version may run only when use is `permitted`, content is `present`, integrity passes, and owner/project policy allows it. Actually used IDs come only from the F124 trace. Coder fixtures prove F121 daemon validation/trace ownership and no F124 or embedded-inline fallback.
- Settings/Automations and contextual `Schedule this` E2E cover keyboard navigation, project filtering, empty/disabled/unavailable/read-only states, restart, and exact surface deep-links without creating another Partner navigation mode.

## FEATURE_110: Refreshable Partner Artifacts

### User outcome

Partner can deliver an interactive HTML/dashboard artifact with declared data bindings, a visible manual refresh action, immutable versions, last-refresh evidence, and `Restore version` for a previous good ArtifactVersion. Files keeps the separate term `Rollback workspace changes`.

### Current foundation

Space already has persisted artifacts, F114 delivery identity, versioned previews, sandboxed opaque-origin `interactive-html`, F130 Results projection, and bounded document preview workers. F110 adds refresh semantics; it does not reintroduce LiveCanvas.

### Design

- The Artifact manifest declares renderer entry, immutable data-binding specifications, refresh recipe identity/version, bounded `renderPermissions`, and `refreshRequirements`. Each binding spec names a stable governed owner/relation plus either `pinned(versionId)` or `current-at-refresh`; it stores no resolved mutable content, Runtime permission grant, connector authorization, `permissionMode`, `autoModeEngine`, provider/model/effort state, or workspace-write authority.
- Refresh is explicit/manual in v1 and dispatches through Runtime/Partner tooling with the original immutable recipe/binding specs. Each run resolves them to exact immutable evidence owner/version refs, records those refs in refresh audit and the F124 trace, and never rewrites the manifest. Main derives current effective execution policy from the active Partner session/project and intersects it with current grants and owner policy; scheduled refresh derives its requested policy from its `AutomationDefinitionRevision` and performs the same intersection.
- Every successful refresh creates a new immutable ArtifactVersion; the previous version remains readable and restorable.
- The rendered iframe receives only serialized bounded data, never filesystem/IPC/credential access.
- Material/evidence freshness, missing origins or retained content, partial refresh, and schema mismatch are visible.
- External Connector refresh requires F096 and the connector's current authorization; old snapshots remain cited evidence.

F110 uses the owning Artifact store's built-in version model:

- `artifactId` is stable for the durable result.
- Every refresh creates a new immutable `artifactVersionId`; `currentVersion` and `versions` remain Artifact-owned.
- Results contains one `PartnerResultRef { owner: 'artifact', ownerId: artifactId }`.
- Version history, lineage, selected version, evidence, and refresh status remain owned by the Artifact store/adapter.
- Internal Artifact versions do not create duplicate result rows or common `PartnerResultRef` relation rows.
- Restoring an earlier version creates a new immutable head derived from that prior version; it never mutates or deletes the prior version.

### F130 Partner projection

- An interactive report/dashboard is a result that may originate from `分析报告`, `表格与数据`, or a free-form request. F110 does not add a sixth launcher entry, Dashboard mode, or top-level Artifact tab.
- `Results` owns preview, data-binding summary, manual refresh, ArtifactVersion history, evidence, failure state, and `Restore version`. The row keeps one authoritative Artifact owner/ID; adapter-local selected-version state never becomes a second result identity.
- Invoking refresh from the selected Result creates a correlated run shown in `Process`. The action binds that exact result without relying on filename or ambiguous natural-language selection.
- Input snapshots/material are selected through Context. `Files` shows only governed workspace locations and mutations; it does not duplicate result identity or refresh history.
- F110 has no implicit or background periodic loop. A user may schedule refresh only by explicitly creating a separate F097 `AutomationDefinitionRevision` with a permission/material-evidence preview. Each dispatch uses the normal session/run status and evidence projections; it does not create an additional generic automation or cross-object review receipt. F110 v1 remains manual by default.

### Security

- Keep opaque-origin iframe, strict CSP, no Node, no same-origin, and permission-checked HTTPS/SRI external resource policy.
- No arbitrary code execution in Electron main.
- No silent periodic refresh in v1.
- Refresh recipes cannot broaden material/evidence owners, connector scopes, or workspace-write authority without review.
- Every refresh recomputes current permission, provider, connector, material/evidence access-retention-content, and workspace policy and intersects it with the recipe's maximum requirements. The result can narrow or fail, but can never restore historical permissions or Auto LLM/model state.
- Generated dashboards are deliverables, not application plugins.

### Acceptance

- Manual refresh with unchanged, changed, missing, stale, and malformed data produces deterministic version/history behavior.
- Previous version remains available after refresh failure.
- Iframe cannot access app origin, preload bridge, filesystem, network beyond declared policy, or credentials.
- Refresh audit links inputs, recipe, Runtime run, outputs, and resulting artifact version.
- Partner E2E proves an interactive result and a failed/successful refresh remain navigable through Results/Process/Files without a Dashboard card, Artifact tab, or duplicate filename-based row.
- A refresh cannot mutate or restore `permissionMode`, `autoModeEngine`, provider/model/effort policy, context scope, connector grants, or workspace-write authority. Revoked or narrowed authority produces a typed wait/denial/failure and leaves the prior good version readable.
- ArtifactVersion tests prove one Results row, immutable internal versions, deterministic restore, and no duplicate relation-backed `PartnerResultRef` rows.
- Binding tests distinguish immutable binding specs from per-run resolved versions and prove pinned, current-at-refresh, changed-input, revoked, and restart behavior is reproducible.

## Release acceptance

- Scheduler and artifact refresh share Runtime/task correlation but not a general workflow engine.
- Background execution, notifications, audit, retention, and deletion semantics are documented.
- E2E covers a scheduled local read-only task and a manually refreshed dashboard artifact.
- The scheduled Partner task and refreshed result use the same F130 receipt/result/process/file contracts as foreground Partner work while remaining separately permissioned operations.
- The complete feature-flag matrix passes for manual/scheduled dispatch, local/connected refresh, active-run cancellation, restart, and read-only recovery; historical Artifact or Automation records cannot restore revoked permission, connector, model, Auto LLM, material/evidence, or workspace authority.

## Rollout and rollback

- Gate F097 definition creation/editing plus manual dispatch, scheduled triggers, and F110 artifact refresh independently. Read-only definitions, run history, receipts, Results, and ArtifactVersions remain available when creation/execution gates are off, subject to owner retention/access policy.
- Disabling F097 prevents new dispatch but never implicitly cancels an admitted run. Explicit cancellation remains available only through the owning Runtime control path; definitions and run history remain visible.
- Disabling F110 blocks new refresh/bind admission but never implicitly cancels an admitted refresh. Any late accepted result is still registered/versioned under normal owner rules; prior ArtifactVersions, provenance, and exports remain visible.

### Feature-flag precedence

| Effective gate                       | Create/edit definition                                      | Manual automation dispatch | Scheduled dispatch                          | Manual artifact refresh                                  | Read-only definitions/history/results         |
| ------------------------------------ | ----------------------------------------------------------- | -------------------------- | ------------------------------------------- | -------------------------------------------------------- | --------------------------------------------- |
| F097 core off                        | blocked, including new revisions, enable, pause, and resume | blocked                    | blocked                                     | unaffected by F097 alone                                 | available                                     |
| F097 core on, scheduled triggers off | allowed; saved schedules remain visibly dormant             | allowed                    | blocked and no OS wake                      | unaffected                                               | available                                     |
| F110 refresh off                     | unaffected                                                  | ordinary automation allowed; refresh-target run blocked | ordinary schedules allowed; scheduled refresh blocked | blocked                                                  | prior versions available                      |
| F096 connected refresh unavailable   | allowed with connected-binding preflight warning            | eligible local runs remain | connected-source run fails preflight        | local refresh allowed; connected refresh blocked         | old snapshots/versions policy-readable        |
| F130 Partner adapter unavailable     | allowed with Partner adapter warning                        | blocked for Partner        | Partner run fails preflight before dispatch | blocked for Partner                                      | owner-backed read-only projection required    |

Authoritative owner capability and current policy outrank every feature flag. A child route/action flag never re-enables a disabled parent. F097 core off blocks definition creation/editing/new revisions and both new manual and scheduled dispatch; neither F097 nor F110 flag transitions erase records or implicitly cancel admitted runs, and explicit cancellation remains an owning-Runtime action. Disabling only scheduled triggers leaves definition editing and manual run available, but saved schedules are visibly dormant and register no OS wake. Existing history, receipts, results, and ArtifactVersions remain readable unless their owning retention/access policy explicitly restricts them.
