# v0.1.35 - Partner Outcomes, Workflow Evidence, and Review

> Status: Planned
> Features: F087, F119, F130
> Rebase note: the former F113 Partner write-path placement is historical. F113 shipped in `v0.1.30`. This file also replaces the old `v0.1.36` Workflow v2 draft/replay plan.
> F130 depends on the shipped F095/F109/F114 Partner foundation and the planned F122-F124 `v0.1.32` project-source loop. F129 later upgrades presentation delivery without changing F130's entry or workspace model.

## Batch decision

Space will improve the Workflow and review experience using contracts KodaX actually ships: pipeline process snapshots, same-session cached replay provenance, immutable review packets, Sidecar/verifier evidence, and governed External Agent tasks.

For Partner, Space will replace the permanent scenario strip and nested Sources rail with an outcome-first empty state, on-demand project context, a conversation-focused center, and a results-first right rail. This is a Space-owned information-architecture change over the existing Partner route/playbook projection and unchanged Auto LLM engine; it does not add another execution-mode system.

Space will not promise cross-process Workflow crash replay, a separate never-run draft lifecycle, or a new Advisor/Council runtime primitive.

## FEATURE_087: Workflow Timeline, Replay Provenance, and Evidence Navigation

### User outcome

Users can understand what a Workflow ran, what was replayed from a prior same-session run, which stages fanned out or joined, what evidence each child produced, and where the final artifacts/results came from.

### Current evidence and gap

Space already renders Workflow process snapshots as a phase/agent tree and supports lifecycle actions, saved workflows, preflight, results, artifacts, and child activity. KodaX KX-F246 now supplies:

- `WorkflowProcessItem.origin` (`ran` or `replayed-from-cache`);
- `WorkflowProcessProgress.replayedAgents`;
- `WorkflowProcessSnapshot.resumedFromRunId`;
- pipeline phase/agent/step/artifact items and correlations.

Space's current IPC schema does not mirror the replay fields, and the UI remains primarily tree/status-oriented.

### Design

- Extend the schema as additive optional fields; older SDK snapshots remain valid.
- Add a timeline mode beside the existing detail tree rather than replacing the compact Task Dock summary.
- Show stage order, active phase, elapsed time, fan-out/fan-in grouping, status, tokens, child counts, artifacts, and result summary.
- Show replay provenance only when the SDK reports it:
  - run-level `resumed from <run>`;
  - replayed-agent count;
  - per-item `replayed from cache` badge;
  - separate newly executed items.
- Cross-navigation targets:
  - child activity/digest;
  - immutable evidence reference or review packet;
  - artifact/delivery;
  - correlated transcript location;
  - source/saved workflow provenance.
- Do not infer replay, stage relationships, or evidence from assistant prose.

### Recovery semantics

- Same-session content-addressed resume is supported and explained.
- A terminal run can be rerun/resumed only through SDK-supported controls.
- Missing artifacts or source runs produce a precise degraded-state explanation.
- App/process crash replay is not claimed; the UI must not show `resumable` unless a future public contract advertises it.

### Security and privacy

- Evidence previews are bounded and respect artifact/session/project ownership.
- Review packets are read-only captured evidence.
- File paths shown to the renderer pass existing path/capability policy.
- External Agent evidence uses task IDs and redacted task DTOs, not executor credentials.

### Acceptance

- A fresh pipeline and a same-session resumed pipeline render distinct truthful provenance.
- Cached replay cannot be mistaken for new execution.
- Fan-out/fan-in and skipped/failed stages remain understandable without raw logs.
- Every displayed evidence link resolves or shows an explicit unavailable reason.
- Older snapshots without replay fields render unchanged.

## FEATURE_119: Evidence Review Surface

### User outcome

Plans, diffs, Workflow runs, Partner deliverables, and release artifacts can carry a durable review record: scope, evidence, findings, verdicts, limitations, reviewer identity/type, and the user's disposition.

### Current evidence and gap

KodaX KX-F259 introduced immutable/content-addressed review packets and consolidated review topology. Space already has diff/review popouts, Workflow activity/results, Partner artifacts/proposals, Sidecar messages, and an External Agent task ledger. The missing layer is a shared reviewed-object model, not another agent abstraction.

### Reviewed object model

```ts
type ReviewedObjectKind = 'plan' | 'diff' | 'workflow-run' | 'artifact' | 'delivery' | 'release';

interface ReviewReceipt {
  id: string;
  objectKind: ReviewedObjectKind;
  objectId: string;
  capturedFingerprint?: string;
  scopeSummary: string;
  evidenceRefs: readonly string[];
  verdicts: readonly ReviewVerdict[];
  reviewer: { kind: 'sidecar' | 'workflow' | 'external-agent' | 'main-session'; id?: string };
  limitations: readonly string[];
  createdAt: string;
  disposition?: 'open' | 'accepted' | 'dismissed' | 'revision-requested';
}
```

The persisted schema must be designed during implementation and remain bounded. The shape above defines product semantics, not a commitment to a new database.

### Design

- Add `Review` actions only where a concrete captured object exists.
- Prefer existing KodaX scoped-review/review packet paths for code diffs.
- Allow a configured governed External Agent to review only after dispatchability/preflight and policy checks.
- Attach results to the object, not the normal conversation stream.
- Present disagreements and limitations rather than collapsing multiple verdicts into fake certainty.
- `Ask main session to revise` sends a bounded receipt/evidence reference, not a transcript dump.
- Stale fingerprints block applying a review to changed content.

### Explicit non-goals

- No `Advisor` service, Council mode, provider matrix, or always-on second model.
- No review call when there is no captured scope or actionable claim.
- No auto-apply of reviewer suggestions.
- No claim that model confidence is evidence.
- No duplicate review packet generator in Space.

### Acceptance

- Review results remain attached to the exact plan/diff/run/artifact fingerprint.
- Changed objects show the previous review as stale.
- Findings link to evidence and distinguish actionable issues from positive/style observations.
- Users can accept, dismiss, or request revision without granting new execution authority.
- No review path bypasses permission, Partner write, artifact ownership, or External Agent policy boundaries.

## FEATURE_130: Partner Outcome-First Workspace

### Decision and user outcome

Partner becomes an outcome-first AI workbench for non-technical knowledge workers:

> The user names or selects the result they want, provides material, and explains the audience or goal. KodaX automatically routes prompts, capabilities, tools, evidence, and output handling, then presents a reviewable deliverable beside the conversation.

The first screen asks `What do you want to complete?` rather than asking the user to understand a work mode, Skill, model, knowledge-base configuration, or execution depth. The user may always ignore the entries and type a natural-language request directly.

F130 does **not** copy WorkBuddy's Ask/Plan/Craft execution selector. KodaX's existing permission modes and Auto LLM engine remain authoritative and unchanged. An outcome entry may affect the prompt playbook and preferred deliverable, but it never changes `permissionMode`, `autoModeEngine`, tool authorization, file scope, connector grants, model effort, or review policy.

### Current evidence and gap

The necessary execution foundations already exist, but their current presentation creates four competing regions and several overlapping concepts:

- `PartnerWorkbenchPanel` permanently occupies the top of the conversation, can grow to `34vh`, and exposes eight scenario buttons plus route, source, output, and advanced details.
- `PARTNER_WORKBENCH_SCENARIOS` already maps scenario to task, prompt capability playbook, and default output. `BottomBar` sends a Partner-only `partnerPromptOverlay` while preserving the user's visible message. These are sufficient automatic-routing foundations; they are not installable SDK Skills.
- `PartnerWorkspace` can render the global navigation, a nested 240 px `SourcesPanel`, the conversation, and the right artifact dock at the same time.
- `SourcesPanel` combines project scope, the legacy knowledge base, administrator audit, attached sources, a file tree, and the add-source action. The controls exist, but the user must understand several storage and policy concepts before the panel creates a useful task loop.
- `ArtifactPanel` separately exposes Artifacts, Files, and Outputs; `DeliveriesPanel` then adds Deliveries and Checkpoints. The persisted objects are useful, but the navigation reflects storage implementation rather than the user's result.
- The shared composer already has working multi-file/image selection and drag/drop parity. User-query bubbles already have a four-line measured collapse/expand interaction. F130 treats both as required baselines and does not reimplement them.
- `styles.css` already defines separate light and dark semantic surface/accent tokens. F130 changes hierarchy and content density, not the established visual identity.

### Research decision

The design borrows WorkBuddy's concrete office outcomes and right-side result review, while deliberately not copying all of its controls:

- WorkBuddy describes document generation, spreadsheet handling, file organization, PPT generation, and automated reporting as concrete work users can recognize: <https://www.workbuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Task-Bar>.
- Its Skills are executable capability packages, while the visible result remains a report, spreadsheet, presentation, poster, or file operation: <https://www.workbuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Skills-Market>.
- Its right-side result area groups generated documents, spreadsheets, presentations, reports, files, changes, and previews beside the task: <https://www.workbuddy.cn/docs/workbuddy/Results>.
- Its separate creative-design mode is backed by a real Ardot canvas and editable design object. KodaX must not expose a comparable general visual-creative entry until an equivalent bounded authoring/review contract exists: <https://www.workbuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Design-Idea>.

The resulting rule is: **the user chooses a primary deliverable when that helps; Partner infers the route when they do not; Auto LLM and permissions remain independent**.

### Product invariants

1. A new Partner task presents at most one optional **top-level result-type decision**: the desired primary result. Templates, material selection, and advanced retrieval scope remain ordinary task inputs rather than additional work modes.
2. Free-form natural language remains a complete first-class entry path.
3. Outcome entries are start shortcuts and output contracts, not persistent runtime modes or mutually exclusive capability buckets.
4. One task may produce multiple result types. Turning a report into a presentation creates another result in the same task; it does not require a mode switch or new session.
5. The center is for conversation, clarification, decisions, and concise receipts. Non-conversational progress belongs to the right rail.
6. Project material and knowledge appear on demand. Partner has no permanent nested left rail.
7. Results are the primary Partner object. Process and files support the result rather than competing with it.
8. Automatic routing is transparent but not configurational: the UI may say `Prepared for: research · spreadsheet analysis · document generation`, while Skills, models, and tool parameters remain behind details.

### Outcome entry model

The GA empty state exposes five localized entries. Labels below are product labels, not new SDK/runtime enums.

| Entry ID            | `zh-CN` label | Primary contract                                                                       | Example templates                                                                                    | Default result family                                                 |
| ------------------- | ------------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| `analysis-report`   | 分析报告      | Evidence, findings, implications, conclusion, and citation coverage when sources exist | competitor analysis, industry research, operating analysis, interview insight, project retrospective | DOCX/PDF or inspectable report artifact                               |
| `spreadsheet-data`  | 表格与数据    | A spreadsheet or dataset remains the primary working object                            | cleanup, aggregation, budget, chart analysis, tracker                                                | XLSX/CSV plus charts when requested                                   |
| `presentation`      | PPT 演示      | Audience, storyline, slide structure, speaker intent, and editable deck delivery       | status review, proposal, pitch, training, document-to-PPT                                            | current F109 PPTX path, then F129 Presentation Project when available |
| `document-writing`  | 文档写作      | Author, edit, transform, or format known content                                       | PRD, proposal, SOP, weekly report, meeting notes, email                                              | DOCX/Markdown/PDF as requested                                        |
| `file-organization` | 文件整理      | A bounded set of reviewed filesystem changes                                           | classify, rename, convert, deduplicate, summarize, add output as project material                    | F113/F114 proposal, delivery, checkpoint, and rollback paths          |

`Visual creative` is not a disabled teaser card in GA. The existing `design` scenario may remain available to automatic routing with truthful design-brief limits, but it cannot claim posters, UI canvases, or editable visual production. A future feature may register a visible entry only after its real editor, preview, persistence, export, security, and rollback gates pass. F129's presentation-specific creative route does not by itself satisfy a general visual-creative contract.

Templates remain bounded prompt starters under an entry; finance, product management, email, meetings, and similar domain/role concepts are templates rather than top-level modes.

The product semantics may be represented as:

```ts
type PartnerOutcomeEntryId =
  | 'analysis-report'
  | 'spreadsheet-data'
  | 'presentation'
  | 'document-writing'
  | 'file-organization';

interface PartnerOutcomeReceipt {
  schemaVersion: 1;
  entryId?: PartnerOutcomeEntryId;
  templateId?: string;
  origin: 'user-selected' | 'inferred' | 'unspecified';
  initialPrimaryResultKinds: readonly string[];
  createdAt: string;
}
```

This receipt is task presentation metadata. It is not a permission, effort, Skill, or Runtime routing authority, and it must not become a second task database.

On the first accepted user send, main validates and atomically writes the bounded receipt into a versioned Space-owned Partner session-presentation sidecar keyed by the immutable session ID. It contains no prompt text, source IDs/paths, permission state, model state, or tool policy; session deletion deletes it. The initial entry/target remains stable when later results are added. Current material count and actual result inventory are always derived from their authoritative stores. Legacy sessions derive a transient receipt from the old scenario and registered results and are not rewritten merely by opening them.

### UX and state flow

#### 1. Empty Partner task

- Show the five entry cards inside the conversation empty state, not in a permanent panel above it.
- No entry is preselected. The composer remains immediately focusable and fully usable.
- Each card shows one icon, one outcome label, and at most one short example line. It does not expose Skill, model, task ID, output ID, source health, or advanced routing data.
- Selecting a card changes the composer guidance and may expose two or three lightweight prompt hints. It never sends automatically or opens a wizard.
- The `+` attachment control remains the single local file/image/folder entry, with file-picker and drag/drop parity.

#### 2. Draft with optional outcome and material

- Selected material is visible as removable chips near the composer.
- A compact `Add material` action opens the context drawer described below.
- The user may switch or clear the selected entry before sending without losing the draft or attachments.
- If no entry is selected, the existing automatic route infers a task/playbook/output from the user's text and material. Ambiguous requests remain unspecified rather than forcing a fake category.

#### 3. First send and active work

- Once the first user turn is accepted, the card grid disappears and does not consume conversation height on reload.
- A compact task receipt may show `Competitor analysis · Word + PDF · 6 materials`. It summarizes the routed goal; it is not a mode selector.
- The center renders user/assistant conversation, necessary clarifications, user decisions, and short semantic receipts only. It does not render a permanent progress bar, tool log, Skill list, or duplicate full result.
- Long user queries preserve the shared measured four-line collapse/expand behavior.
- When work starts, the open right rail follows the deterministic tab state machine below. A closed right rail never auto-opens; the Partner header shows a small status affordance that opens `Process`, without recreating progress in the center.

#### 4. First result and review

- When an artifact/delivery is registered, the right rail shows a result badge. While the producing run is active, automatic follow stays on `Process`; when that run becomes terminal it switches to `Results` only when there is no manual hold for that run.
- The assistant adds a concise completion receipt in the center rather than pasting the full result there.
- `Results` selects the new result and exposes preview, version/provenance, citations or source references, validation state, export/reveal, and follow-up editing actions supported by that result kind.
- F119 review receipts attach only to a supported immutable reviewed object behind the selected result. Today a presentation review therefore targets its exact artifact/delivery export; project-level authoring and verification state remains F129-owned until the reviewed-object contract explicitly adds `presentation-project`. Reviews do not become another conversation or another top-level rail.

#### 5. Refinement and cross-format work

- Selecting a result is navigation only. A follow-up is bound to one result only after the user invokes `Refine this result` (or an equivalent contextual action), which adds a visible removable result-target chip to the composer. Natural-language references without that chip use normal conversation resolution; if multiple plausible results remain, Partner asks rather than mutating one silently.
- Editing creates a new artifact/delivery version or the existing subsystem's update record. F130 does not introduce a parallel version store.
- Requests such as `turn this report into a 12-slide executive presentation` create another result in the same task. The original result remains available.

### On-demand context drawer

F130 supersedes only the permanent placement of the current Sources/KB/Audit UI. F122-F124 source, version, index, citation, scope, retrieval, and trace contracts remain unchanged.

The composer/header `Add material` action opens one Partner context surface with progressive sections:

1. **This task** - explicitly attached files, images, folders, and selected project sources.
2. **Project materials** - F122 durable project sources, their health/freshness, and selection state.
3. **Project knowledge** - accepted legacy KB/F126 curated knowledge when the capability exists; configuration and maintenance do not occupy the ordinary task flow.
4. **Connected sources** - browser or connector sources only when F050/F096 advertises an authorized capability. Hidden otherwise.

The drawer distinguishes three facts:

- available to the project;
- explicitly selected for this task;
- automatically recalled and actually used for this turn.

Selection and scope rules are deterministic:

- direct attachments and explicitly selected project-source IDs persist for the current Partner task/session until the user removes them;
- choosing an outcome entry never changes the retrieval scope;
- default `project-grounded` follows F124: use explicitly selected ready project sources when present, otherwise the permitted pinned/ready project set, plus accepted KB according to its policy;
- `selected-only` and `general` remain on-demand/advanced scope overrides and are never implied by an outcome card;
- each turn records the actual used-source IDs in its F124 trace; the task header derives its current selected-material count instead of storing it in `PartnerOutcomeReceipt`.

After execution, the task receipt may show `Used 6 project materials`; opening it reveals F123 citations and F124 recall trace summaries. The UI never calls all project content `attached` when only a bounded recalled subset was used.

The current `AdminAuditPanel` moves to project settings/diagnostics. Existing knowledge maintenance/configuration moves to a project-level management surface. Neither remains in the default task workspace.

A supported output may be added as an F122 project material through an explicit action. Promotion of an inferred conclusion into curated project knowledge remains owned by F126 and is not silently performed by F130.

Context and Files have different verbs even when they can refer to the same path:

| Surface | Owns                                                                          | Safe removal meaning                                                                  |
| ------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Context | whether a source/attachment is eligible input for this task                   | unselect/detach; never delete the underlying file                                     |
| Results | generated result identity, preview, versions, evidence, export, and review    | remove from the result projection only through the owning subsystem's explicit action |
| Files   | workspace location, mutation proposal, diff, checkpoint, reveal, and rollback | governed filesystem action under F113/F114 policy                                     |

A generated result appears in Context only after `Add to project materials`; that action creates an explicit source-to-result origin reference. It is never inferred from matching paths or filenames.

The context drawer exposes `Manage project materials and knowledge`, which opens the project-level management surface (legacy KB/settings first, F126 when available). `Settings > Diagnostics > Partner policy and activity` hosts the current audit/policy view, subject to its existing role/policy boundary. Both destinations require reachable empty, unavailable, and legacy-session states before the permanent rail is removed.

For Partner sessions, the shipped F103 Environment Hub `Sources` row routes to this same context surface and focuses the relevant section. Coder keeps its existing Task Dock Sources/Context route. F130 does not create a second source picker or change F103 behavior outside Partner.

### Partner right rail

The Partner-specific projection reuses the existing `RightSidebarFrame`/F103 shell and presents three stable top-level tabs in this order:

1. **Results** - generated artifacts, registered deliveries, presentation projects, previews, versions, citations, verification, export, and object-attached review.
2. **Process** - current run state, semantic stages, Workflow projection, active agents when relevant, evidence navigation, warnings, and completion receipt.
3. **Files** - task workspace files, reviewed proposals/diffs, checkpoints, apply/reject, reveal, and rollback.

F130 does not merge the Artifact and Delivery stores. It builds a session-scoped result projection whose rows preserve the authoritative owner and ID. Two records may be visually grouped only through an explicit stored reference; filename equality alone never deduplicates or merges results.

The adapter projection uses a bounded common reference rather than a new result store:

```ts
type PartnerResultOwner = 'artifact' | 'delivery' | 'presentation-project';

interface PartnerResultRef {
  owner: PartnerResultOwner;
  ownerId: string;
  sessionId: string;
  createdAt: string;
  updatedAt: string;
  relation?: {
    kind: 'version-of' | 'derived-from' | 'materialized-as';
    owner: PartnerResultOwner;
    ownerId: string;
    ownerSubresourceId?: string;
  };
}
```

Rows sort by `updatedAt`, then `createdAt`, then `(owner, ownerId)` for stable ties. Explicit `version-of` relations form version groups; `derived-from` retains cross-format lineage without hiding either result; `ownerSubresourceId` identifies an export/version inside an owning project when that subsystem has no separate top-level owner kind. Legacy unlinked records remain separate and display their owner/type rather than being guessed into a group.

`Process` uses the facts already emitted by the current session/run/Workflow projections. It shows user language such as `Reading 6 materials`, `Extracting findings`, `Building 12 slides`, and `Checking citations and file format`. Model names, tool parameters, raw logs, and route diagnostics remain under technical details. F087 enriches this tab with truthful Workflow provenance; F089 may later add its task-plan/completion receipt without F130 inventing plan truth.

Process copy is produced only from a reviewed mapping over structured facts: managed-run phase/state, categorized tool lifecycle, Workflow snapshots, source-ingestion/retrieval events, delivery registration, and verifier results. Missing facts show neutral `Working` or the last verified stage. Failure, cancellation, waiting-for-user, unavailable capability, and partial-result states have explicit projections. Assistant prose is never parsed to manufacture progress.

`Files` preserves F113/F114 policy, checkpoint, proposal, and rollback semantics. A generated output file is primarily discoverable in `Results`; its workspace location and mutations may also be reachable from `Files` without duplicating identity.

#### Deterministic right-rail follow state

- `railOpen` remains user-owned. F130 never opens a rail the user closed.
- `activeTab` is stored as bounded per-session UI preference. A user tab click creates a `manualHoldRunId` for the currently active run; both survive renderer reload while that run remains current, but carry no domain authority.
- At a new run start, stale manual hold is cleared. If the rail is open, automatic follow selects `Process` without moving keyboard focus.
- Results arriving during an active run increment the Results badge but do not interrupt `Process`.
- When the run becomes terminal, automatic follow selects `Results` if at least one new result exists and no manual hold exists for that run. Otherwise the badge remains.
- Visiting Results clears only result notifications at or before the newest result the user has observed. Process warnings use an independent badge and acknowledgement cursor.
- Session switch/reload restores the stored active tab; stale run IDs are discarded. Multiple concurrent result events are reduced by monotonic event/order cursors before applying these rules.

### Responsive, theme, motion, and accessibility contract

- Wide layout: global navigation + conversation + Partner right rail. There is no nested Partner left rail.
- Medium layout: global navigation remains collapsible and the right rail keeps the existing resizable/overlay behavior; the conversation never gives up width to a permanent context rail.
- Narrow layout: conversation is primary and the right rail/context drawer opens as a full-height sheet. No four-column or horizontally squeezed state is permitted.
- New UI uses existing semantic `surface`, foreground, border, accent, status, motion-quality, and reduced-motion tokens. Light and dark themes are designed and tested independently; F130 is not a dark-only or black-gold redesign.
- Entry cards are semantic buttons with visible focus, an announced selected state, and no color-only meaning.
- Results/Process/Files use proper tab semantics and keyboard navigation. Automatic tab selection never steals keyboard focus or overrides the per-run manual hold.
- Process updates use bounded live-region announcements; raw streaming events do not flood assistive technology.
- The existing query-collapse control retains `aria-expanded`, keyboard access, and resize-aware measurement.

### SDK and capability contract

F130 has no new KodaX SDK gate. It is a Space-owned UI and routing projection over:

- F095 scenario/task/playbook/output inference and `partnerPromptOverlay`;
- the current Space permission modes and Auto LLM engine;
- F103 right-sidebar/floating-surface host;
- F109 Office/PDF baseline writers;
- F113 reviewed file proposals;
- F114 workspace delivery, checkpoints, and delivery registry;
- F122-F124 project sources, stable citations, and automatic grounded recall.

Later capabilities plug into this contract instead of adding new permanent UI layers:

- F125/F126 add ranking explanation and curated project knowledge inside the context surface.
- F129 replaces only the `presentation` creation/review backend with the Presentation Project/Studio.
- F050/F051/F052 add governed browser, document, and research capabilities behind the same entries.
- F096 adds authorized connected-source adapters to the same context surface.
- F110 adds refreshable results to the Results projection.

F122-F124 are a GA dependency for F130's project-material claims. Internal/dark development may render the launcher and local-attachment-only flow when one of them is unavailable, but F130 cannot be marked Completed or enabled by default until project source selection, used-source truth, stable citations, and automatic recall pass their `v0.1.32` release gates. Partial capability never produces a misleading `Project materials` success state.

F129 registers one qualified Presentation Project/Studio adapter. When advertised, new `presentation` requests route to F129 and Results opens Studio through that adapter. An F129 generation failure is shown as an F129 failure and never silently relabeled as a verified F109 result; a labeled legacy-simple-deck action may appear only under F129's explicit rollback gate. Existing and in-flight F109 results remain F109 objects and are never migrated implicitly.

Missing future capabilities hide or truthfully degrade their actions. Version numbers, model names, installed packages, or prompt text never enable a product entry by themselves.

### Security and permission boundary

- Selecting or inferring an outcome never writes `permissionMode`, `autoModeEngine`, effort, model, connector authorization, allowed directory, or tool policy.
- F130 never silently installs or enables a Skill, authorizes a connector, expands a file scope, sends external messages, publishes content, deletes files, or starts a high-cost external expert/team.
- Automatic routing may use only capabilities already installed, enabled, advertised, and authorized for the session/project.
- File organization continues through existing permission checks and F113/F114 proposal/checkpoint/rollback paths. Auto LLM may make the same decisions it makes today; F130 neither broadens nor bypasses those rules.
- Project-source selection uses F122 stable IDs and F123 locators where available. Renderer previews remain bounded and follow current path/content policy.
- Result actions retain their owning Artifact/Delivery/Presentation policy. A UI projection cannot grant a cross-store or cross-project action.
- Audit and technical details stay accessible to advanced users and support, but removing the permanent audit panel does not remove audit recording.

### Compatibility and migration

- Existing Partner sessions, artifacts, deliveries, proposals, checkpoints, KB pages, and source records are not rewritten.
- An old persisted scenario may be projected through the compatibility table above. If it cannot be mapped, the task receipt remains unspecified and the original route data stays available in technical details.
- `PartnerWorkbenchPanel` and the permanent `SourcesPanel` may remain behind a short-lived rollback flag for one release. They are not two simultaneous GA surfaces.
- F122-F124's `Project grounded`, `Selected only`, and `General` retrieval scopes remain valid internal/user-advanced scope facts. F130 supersedes only their default placement: ordinary users see material used and can adjust scope on demand rather than maintaining a permanent mode strip.
- The current F109 presentation result remains usable until F129 passes its migration and rollback gates. The `PPT 演示` entry stays stable while the backend changes.
- Shared components may be extracted, but Coder information architecture, tabs, default widths, composer controls, and snapshots remain unchanged.

### Explicit non-goals

- No Ask/Plan/Craft clone and no `smart/quick/deep` selector.
- No new task engine, planner, permission mode, model router, Skill runtime, expert center, or persistent outcome-mode database.
- No Coder redesign or deliberate Coder behavior change.
- No general visual-creative promise before a real bounded canvas/editor/output contract exists.
- No rewrite of F122-F124 retrieval/index/citation contracts, F109/F114 result stores, or F103 shell ownership.
- No full-screen task wizard and no requirement to choose a card before typing.
- No black-gold-only restyle, typography replacement, new icon family, or theme regression.
- No duplicate implementation of the resolved attachment picker or query-collapse behavior; both are non-regression gates.
