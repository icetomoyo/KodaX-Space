# v0.1.35 - Learned Skill and Command-Sandbox Safety Surfaces

> Status: Completed
> Features: F118, F143
> Runtime contracts: published `learningCenter:1`, `skillLearningLoop:1`, and
> `@kodax-ai/kodax/sandbox` facade v1

## Scope decision

F118 was previously specified as a five-view, searchable Learning Center for
Memory, Skill, Extension, and Workflow carriers. That design exceeded the
published KodaX 0.7.78 contract:

- `runtime.learning` is already published, so F118 is no longer SDK-gated.
- The 0.7.78 learning loop produces governed learned **Skills**. Memory is not a
  Learning Center carrier, Extension self-learning was removed from the KodaX
  roadmap, and Workflow is not a learned carrier.
- The public Runtime service exposes list/get/snapshot/events/subscription plus
  acknowledge, snooze, review, trust, reject, disable, rollback, and promote.
  It does not expose archive/restore.
- Current Space commands cover list/detail/ledger and the separate
  review/trust/reject/disable/rollback operations. They still do not supply
  event subscription/cursor recovery, attention UX, or the desktop read model,
  so they do not make F118 complete.

F118 is therefore reduced to the smallest product surface needed to make the
published learned-Skill safety loop understandable and controllable. Space
continues to use Runtime as the only authority and does not create a second
learning database.

## FEATURE_118: Learned Skill Safety Surface

### User outcome

The user can answer four questions without reading Runtime files:

1. Which learned Skill needs attention?
2. What evidence, immutable revision, fingerprint, scope, and canary result
   produced it?
3. Is the revision trusted, disabled, quarantined, or rolled back to a known
   good revision?
4. Which explicit action will review, trust, reject, disable, or roll it back?

### Minimum surface

- Reuse an existing Task Dock/Settings lightweight panel before considering a
  dedicated popout.
- Show an attention badge only for actionable ready, review-required, or
  quarantined records. Opportunity and invocation counts do not create badges.
- Provide bounded list and detail views with a human name/slug, while binding
  every mutation to the exact Runtime capability ID. An ambiguous slug must
  require the ID rather than selecting a candidate heuristically.
- Show scope, immutable revision, fingerprint, evidence/provenance, progress
  across at most three exact-revision canary invocations, the validation result
  reported by Runtime, and previous-good revision when returned by Runtime.
  This is not "run three ordinary tests and auto-promote."
- Expose only actions present in the public service and current record:
  review, trust, reject, disable, and rollback. Promotion remains an explicit,
  separately confirmed action and may ship after the core safety actions.
- Subscribe from a durable Runtime event cursor and recover by snapshot after a
  cursor gap. Reading or acknowledging a notice never trusts code.
- Keep `/learn` as the command path. Any command advertised by Space must call
  the matching Runtime operation; aliases such as `approve` must not silently
  collapse review and trust into one action.

### Carrier boundary

F118 is learned-Skill-first. If a future Runtime returns another carrier, Space
may render its common identity and lifecycle read-only, but it must not invent
carrier-specific actions.

| Domain        | F118 treatment                           | Authority                                 |
| ------------- | ---------------------------------------- | ----------------------------------------- |
| Learned Skill | Full minimum safety surface              | KodaX `runtime.learning`                  |
| Memory        | Link to F117/F228 governance only        | Memory control plane, not Learning Center |
| Extension     | No self-learning UI or execution promise | Reopen only with a new published contract |
| Workflow      | No learned-carrier UI                    | Existing Workflow execution/governance    |

### Deferred until evidence justifies them

- dedicated five-tab popout and global search;
- Opportunity and History product views;
- multi-client unread management beyond the Runtime cursor required for safe
  reconnect;
- archive/restore, because they are not public Runtime operations;
- bulk actions, rich filtering, snooze management, and promotion collision UX;
- Memory/Extension/Workflow union models.

These are not hidden acceptance criteria for F118. They require observed record
volume, a user journey that cannot fit the minimum panel, and a published
Runtime method where applicable.

### Runtime ownership and safety

- Runtime owns evidence collection, draft generation, immutable revisions,
  fingerprinting, canary runs, validation, activation, quarantine, audit, and
  rollback.
- Space owns presentation, stable client identity, cursor persistence, explicit
  confirmation, and truthful error/reconnect states.
- Formal/global promotion always requires a distinct user confirmation and
  collision check. F118 never silently promotes or mutates formal Skills.
- Candidate self-report, invocation count, or confidence is not proof.
- A failed candidate cannot replace the previous-good active revision.
- Unsupported or failed actions remain visible as unsupported/failed; Space
  never infers success from lifecycle text or package version.

### Acceptance

- List/detail and the five core safety actions pass against a real daemon-owned
  learned Skill.
- Detail shows exact revision/fingerprint/scope/evidence/canary/validation facts
  supplied by Runtime, without manufacturing absent fields.
- Review and trust are separate operations and reading cannot activate code.
- Reconnect from an event cursor neither duplicates actions nor loses an
  actionable record; a gap recovers from snapshot.
- Disable and rollback preserve the Runtime audit trail and previous-good state.
- A second client observes the shared lifecycle result without Space creating a
  parallel store.
- Unknown carriers and actions degrade read-only and never execute.

### Rollout and rollback

- Gate the surface on negotiated `learningCenter:1` and
  `skillLearningLoop:1`, not on a semantic version.
- Ship the read model before mutations; enable each mutation only after its
  integration test passes.
- Product rollback disables Space mutation controls while retaining read-only
  Runtime state and normal formal Skill catalogs.

### Implemented architecture

- `packages/space-ipc-schema/src/channels/learning.ts` defines strict bounded
  list/detail/action/acknowledge/event contracts. Only the five F118 actions are
  accepted; schema-v1 and unknown-carrier projections are structurally
  read-only, and Runtime absolute artifact paths never cross IPC.
- `apps/desktop/electron/ipc/learning.ts` owns the Space safety adapter. It
  re-reads the exact capability ID, checks the user-confirmed revision and
  fingerprint, delegates one exact-ID Runtime action, then verifies exactly the
  next revision and the action-specific lifecycle. Runtime `lastAction` is
  display-only because lifecycle transitions such as disable/reject do not
  guarantee that it is rewritten.
- The published daemon facade does not accept a caller-supplied CAS authority
  token. Space therefore does not claim an atomic client-side compare-and-swap:
  Runtime remains the serialized transition authority, while Space fails
  truthfully if its preflight or postflight facts do not match.
- Space persists only `{ runtimeId, revision }` in
  `runtime-learning-cursor.json`. Contiguous events are persisted before push;
  duplicate events are ignored, and identity changes, gaps, or cursor-ahead
  states recover from an authoritative Runtime snapshot.
- The Task Dock panel is gated on both negotiated contracts and shows bounded
  Runtime projections, actionable attention, exact evidence/canary/previous-good
  facts, explicit confirmations, reconnect errors, and read-only compatibility
  states. Acknowledge remains separate from every lifecycle mutation.
- `/learn` resolves names/slugs through Runtime first and binds each Runtime
  mutation to the returned exact capability ID, then reuses the same
  Skill/source/lifecycle/revision/fingerprint safety service as GUI actions.
  `review` and `trust` remain distinct operations.
- `SPACE_DISABLE_LEARNING_MUTATIONS=1` removes all Space mutation controls and
  blocks `/learn` Runtime mutations while preserving the read model.

### Verification evidence

- Strict schema, mutation allowlist, path bounds, and legacy read-only tests:
  `packages/space-ipc-schema/test/learning.test.ts`.
- Exact identity/revision/fingerprint checks, cursor persistence, replay

  `apps/desktop/electron/test/learning-ipc.test.ts`.
- Capability gating and actionable-only attention:
  `apps/desktop/electron/test/learning-model.test.ts`.
- Process-distinct shared-daemon acceptance for review, trust, reject, disable,

- Real-daemon list/detail and all five actions through the actual

  `apps/desktop/electron/test/learning-safety-daemon.test.ts`.

## FEATURE_143: Explicit ASRT Setup and Readiness

### 1. 需求概述

KodaX 0.7.78 publishes a fail-closed command-sandbox facade, but Space v0.1.34
only packages its ASRT helpers, probes doctor once at startup, buries readiness
inside the generic runtime capability ledger, and shows per-tool execution
facts. Users cannot refresh doctor, read bounded setup guidance, or explicitly
complete one-time setup from the desktop.

F143 completes that product loop without treating command containment as F138:
Settings shows the current ASRT/backend state and exposes an explicit,
user-confirmed setup action only where the SDK contract says setup may elevate.
Startup and ordinary tool calls continue to never trigger setup.

### 2. 影响范围

- Add a strict, bounded sandbox status/refresh/setup IPC contract.
- Keep all SDK calls in Electron main; the renderer receives no executable
  path, command output, environment, credential, or unrestricted diagnostic.
- Add a Settings safety surface for status, version/backend, diagnostics,
  guidance, refresh, and eligible setup.
- Keep `Sandboxed`, `Sandbox fallback`, and `No sandbox` as per-execution facts;
  they do not replace machine readiness.
- Refresh the generic `space.version` sandbox row from the same authoritative
  doctor projection instead of introducing a second readiness database.
- Update product/manual/capability wording to distinguish package presence,
  doctor-confirmed readiness, setup-required state, and F138.

### 3. 技术方案

- Use `doctorKodaXSandbox({ refresh })` as the readiness authority and
  `getKodaXSandboxSetupGuidance(doctor)` for bounded user guidance.
- Use `activateKodaXSandbox({ allowElevation: true })` only after a dedicated
  renderer action passes an explicit confirmation. Do not call the lower-level
  setup helper directly.
- Serialize refresh/setup in main so repeated clicks cannot start concurrent
  installers. Setup outcome is followed by a fresh doctor projection before it
  is returned.
- Model `checking`, `ready`, `setup-required`, and `unavailable` separately
  from transient operation state and from the SDK facade's presence.
- Windows may show one UAC prompt. macOS/Linux receive guidance and refresh;
  Space never invokes a package manager or widens permissions.
- Bound arrays and strings at the schema and adapter boundaries, sanitize
  thrown errors, and keep setup cancellation distinct from failure.

### 4. 接口契约

- `sandbox.status`: returns facade version, ASRT version, platform/backend,
  readiness, setup eligibility/elevation metadata, bounded diagnostics and
  guidance, plus the latest operation outcome.
- `sandbox.refresh`: performs a serialized `doctor({ refresh: true })` and
  returns the same status schema.
- `sandbox.setup`: accepts an explicit confirmation literal and invokes
  activation only when doctor still reports setup-required and the capability
  advertises setup elevation. Stale/duplicate/ineligible calls fail closed.
- Setup never runs through `space.version`, app startup, ordinary tool
  execution, or diagnostic export.

### 5. 实现步骤

1. Define schema and tests for bounded status, refresh, and explicit setup.
2. Add a main-process controller that owns SDK import, serialization,
   projection, error sanitation, and doctor cache synchronization.
3. Register IPC and update `space.version` to read the controller's shared
   readiness projection.
4. Add Settings UI, localized copy, confirmation, operation feedback, refresh,
   and disabled/loading states.
5. Add unit/integration tests for ready, setup-required, cancellation,
   unavailable, stale eligibility, concurrent clicks, and post-setup refresh.
6. Run focused suites, typecheck, lint, build, package-sensitive tests, and
   independent review.

### 6. 验收标准

- A ready machine displays backend and exact ASRT version without offering an
  unnecessary setup action.
- A setup-required Windows machine displays bounded guidance and an explicit
  setup action; no elevation occurs before the user confirms.
- Successful setup re-runs doctor and changes the visible state to ready in the
  same app session. Cancellation and failure remain visible and retryable.
- macOS/Linux never run a package manager; unsupported or unavailable systems
  remain truthful and non-executing.
- Repeated setup clicks cannot launch concurrent installers, and a stale setup
  request cannot bypass a new doctor result.
- Startup, `space.version`, diagnostics export, and ordinary tool execution
  never invoke setup.
- No raw path, environment, command output, or credential crosses IPC.
- Existing tool-level sandbox observations and non-sandbox Settings behavior
  pass regression tests.
