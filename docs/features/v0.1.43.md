# v0.1.43 - Beta Completion

> Status: Planned
> Features: F076, F094, F101, F128
> Position: final feature-bearing 0.1.x release; `v0.1.44` is the patch/RC reserve

## Batch decision

The 0.1.x line ends with a measurable product-completion gate: localization coverage, truthful release diagnostics, updater/distribution trust, downstream SDK/package compatibility, and evidence that the pulled-forward Partner knowledge path is accurate, current, access-safe, diagnosable, and rollbackable. Execution sandbox feasibility is removed from this feature batch and remains an ADR/watchlist concern.

## FEATURE_076: Localization Completion Gate

### User outcome

Users can independently choose Space display language and assistant response preference. Supported English and Simplified Chinese UI is complete across normal, empty, error, permission, workflow, Partner, Memory/Learning, diagnostics, and release states.

### Design

- Preserve `system`, `en-US`, and `zh-CN` display modes.
- Add a separate assistant-response preference (`auto`, English, Simplified Chinese) that influences the supported model instruction path without changing UI locale.
- Make message keys typed and require every supported locale to provide the same key set.
- Move remaining menu, main-process dialog, renderer chrome, modal, toast, empty/error, accessibility label, and packaged-only strings into the locale catalog.
- Add a dev-only pseudo-locale that expands text, marks boundaries, preserves interpolation, and exposes clipping/wrapping issues.
- Add a required CI scanner for newly introduced user-visible hard-coded strings with explicit reviewed exceptions.
- Third-party/model/tool/file content is not translated.

### Acceptance

- Locale key parity is a type/test failure.
- The scanner blocks new unapproved high-frequency UI literals.
- Pseudo-locale E2E covers sidebar, Task Dock, settings, permission/ask-user, Workflow, Memory/Learning, diagnostics, and F130's five outcome entries, single `+ Add material` context control, and `Results / Process / Files` rail.
- Partner localization fixtures cover result/process badges, permission and capability degradation, unavailable evidence, retry/recovery actions, and empty/loading/error states without clipping or untranslated fallbacks.
- The F130 context and right rail pass at the true minimum supported width as full-height sheets, and the complete Partner journey is checked independently in light and dark themes.
- Outcome cards, material controls, rail tabs, badges, result actions, and degraded-state disclosures have localized accessible names; live-region announcements are bounded and do not repeat progress or badge updates noisily.
- Localization distinguishes `Completion summary` from `Completion receipt`, `Task plan` from F129 `Story`, and the single `+ Add material` control from its material-source sections.
- Display locale and response preference persist independently and resume deterministically.
- No provider/model content is silently machine-translated.

### Absorbed work

F077 pseudo-locale, F078 required scanner, and F080 response-language preference are acceptance slices of F076, not separate features.

## FEATURE_094: Beta Release Readiness and Diagnostics

### User outcome

Every beta build can explain its Space/KodaX versions, capability contract, active/degraded features, Runtime form, platform, update channel, and known limitations; maintainers can reproduce a packaged smoke result and inspect a redacted diagnostic bundle.

### Design

- Enforce version agreement across root/desktop/schema/UI-kit/lockfile/release assets.
- Extend `space.version` and diagnostics with Runtime identity/capabilities and capability-ledger status.
- Generate a known-degradation list from explicit capability results, not prose guesses.
- Verify custom-provider `apiKeyEnv` and `baseUrl` guards, SSRF policy, keychain behavior, permission broker, Partner file policy, and External Agent redaction.
- Define one packaged smoke matrix for boot, session create/resume, provider config, permission/ask-user, terminal, workflow, artifacts, Partner, Memory/Learning capability gating, updater manifest, and diagnostic export.
- By v0.1.43, F130 is the sole default Partner projection and the one-release legacy Workbench/Sources flag has expired. Packaged smoke asserts that no legacy projection toggle is registered or silently restored.
- The Partner slice loads pre-F130 session/data fixtures directly into F130 and derives their transient compatibility projection without writing a `PartnerOutcomeReceipt` merely on open. A separate new-session fixture creates the persisted receipt on first accepted send and restores it after restart.
- A pre-F130-data -> transient F130 projection -> restart -> export/import round trip preserves sessions, sources, citations, Artifacts, Deliveries, proposals, checkpoints, and presentation references without rewriting owner identity; the new-session round trip separately proves persisted receipts and the authoritative `artifact`, `delivery`, and `presentation-project` Result adapters.
- Packaged diagnostic export has negative assertions for prompt text, evidence content, URLs, local file paths, account/resource identity, credentials, connector payloads, and unredacted raw task content.
- Check docs/manual/changelog/release body consistency before tag.
- Link unsupported execution isolation to a separate ADR/watchlist record; do not claim a sandbox.

### Acceptance

- A release command fails on version/asset/manifest/doc mismatch.
- Diagnostics expose capability reasons without secrets or task content.
- Unsupported SDK features are hidden or explicitly degraded.
- Packaged smoke uses the exact published SDK tarball.
- Windows/macOS/Linux release artifacts and updater manifests resolve to identically named assets.
- Restart smoke restores only valid F130 receipt, adapter, selected Result, and rail state; stale per-run follow/hold state is discarded, and no removed legacy projection can be reactivated.
- Redacted Partner diagnostics remain actionable without exposing prompt, evidence content, URL/path, account/resource identity, credential, connector, or raw task-content payloads.

## FEATURE_101: Release Channels and Distribution Trust

### Current evidence and scope correction

Windows installer, macOS DMG/ZIP, Linux AppImage/deb, GitHub Releases, updater manifests, and packaging smoke already exist. F101 no longer treats Linux packaging as future work.

Remaining outcome:

- define `dev`, `beta`, and `stable` channel semantics;
- ensure updater cannot cross channels unexpectedly;
- document and decide signing/notarization requirements per channel;
- harden installer/update asset integrity and rollback;
- verify downstream installation against KodaX package-policy changes, including KX-F262 npm/trusted-publishing migration;
- keep break-glass/manual release steps auditable and credential-minimal.

### Design

- One channel source of truth feeds build metadata, updater configuration, release body, and diagnostics.
- Stable releases require the chosen signing/notarization trust policy; beta/dev show explicit trust state.
- Updater manifests are generated once per release, merged deterministically across architectures, and validated against uploaded assets.
- CI installs the published KodaX tarball with the supported npm policy and proves required native/Worker sidecars survive install and packaging.
- Release credentials use the narrowest available mechanism; track KodaX trusted publishing as a compatibility dependency, not a Space implementation claim.

### Acceptance

- Channel switching and update eligibility have deterministic tests.
- Release staging rejects wrong version, wrong channel, missing sidecar/native binary, mismatched URL/name, duplicate/overwritten manifest, and unsigned-stable policy violations.
- Linux readiness is tested as an existing supported artifact path.
- Release documentation accurately states signature/trust behavior.

## FEATURE_128: Knowledge Quality Evaluation and Operational Diagnostics

### User outcome

Users can trust that Partner's project answers are sourced, current, access-safe, and diagnosable. When quality degrades, Space explains whether the cause is missing material/evidence, failed ingestion, weak retrieval, stale knowledge, provider degradation, citation gaps, or conflicting evidence.

F128 evaluates the F122-F127 knowledge path. F130 owns its ordinary user-facing placement: turn/result evidence is reached from the task-receipt projection or the selected result, project-wide knowledge health is managed outside the task rail, and operational diagnostics remain in Settings.

### Evaluation corpus

- Ship deterministic synthetic fixtures for PDF, DOCX, PPTX, XLSX, Markdown/text, code, task-attachment snapshots, Result snapshots, source changes, conflicts, missing/restricted evidence, and later connector snapshot adapters.
- Support an opt-in per-project set of questions, typed expected evidence owner/version/locator refs, forbidden evidence/access-policy cases, acceptable abstention, and optional expected facts.
- Keep evaluation local by default. Remote judge use is optional, clearly labeled, and never required for exact release correctness.
- Version corpus, parser/index generation, retrieval configuration, optional provider/model, prompts, and scoring rules with each result.

### Metrics

Measure at least:

- retrieval Hit@k, MRR, context precision/recall, and forbidden-evidence/access-policy leakage;
- citation presence, precision, locator resolvability, and claim-to-citation coverage;
- grounded claims, unsupported-claim rate, correct abstention, and conflict disclosure;
- stale-answer rate after source change, restricted-content leak rate after an access decision, and project-grounded exclusion rate after a material relation is removed;
- ingestion/query/rerank latency, evidence overhead, index size, and cache behavior;
- migration, restart recovery, rebuild, provider fallback, and rollback success.

LLM-as-judge output is advisory unless calibrated against deterministic or human-reviewed fixtures. It cannot replace exact access, version, and citation assertions.

### Provisional beta targets

Initial targets are calibration baselines before they become hard gates:

- retrieval Hit@5 at or above 90% on the reviewed golden set;
- claim citation coverage at or above 95% under the `project-grounded` retrieval scope;
- 100% resolution to the declared best-supported locator precision for fixtures;
- zero forbidden-evidence/access-policy leaks in deterministic suites;
- 100% explicit conflict disclosure for labeled conflict fixtures;
- warm local FTS5 retrieval p95 below 300 ms on the reference corpus;
- optional hybrid retrieval p95 below one second, excluding final answer generation;
- changed-source impact visible within the completed ingestion cycle, with no stale result presented as current afterward.

Any target change records the corpus, evidence, tradeoff, approver, and rollback threshold.

### Trace and health

Each knowledge-backed turn exposes a redacted typed trace containing:

- effective retrieval scope;
- `selectedMaterialRelationIds` as a separate relation-membership/selection fact that is never inferred from evidence owner refs;
- `selectedEvidenceOwnerRefs` and `usedEvidenceOwnerVersionRefs` across every project-source, task-attachment, result-snapshot, web-fetch, browser, and connector evidence owner;
- `selectedSourceIds`, `usedSourceIds`, and `usedSourceVersionIds` only as an exact read-only compatibility projection of the corresponding generic `project-source` refs; a mismatch fails validation;
- `usedKnowledgePageVersionRefs` for every actually injected legacy or F126 project-knowledge version;
- included Core Project Context block IDs/versions and inclusion reasons;
- eligible project-knowledge states and authority classes;
- filters, retrieval route, component ranks, fusion/rerank generation, fallback, and truncation;
- Evidence Pack/citation IDs, budget, freshness/conflict decisions, and adapter/index generation;
- version-addressed `liveAvailability`, `originAccess`, `retainedSnapshotUse`, and `retainedContentAvailability` decisions;
- excluded counts and safe reason codes without leaking restricted metadata.

The same typed turn trace opens from the relevant Result, F130's concise conversation/task-receipt projection, or a current-run Process evidence row. The task-receipt launcher creates no additional receipt owner or store. Process does not retain long-lived health history. Results may show used-evidence facts, citation coverage, freshness/conflict decisions, and a bounded retrieval-route summary; raw ranks and configuration details remain in the deeper trace. Context may show scope and eligibility but never infers `used` from `selected` or becomes a diagnostics console.

Project-wide material/evidence readiness, failed jobs, stale/restricted knowledge, evaluation history, and rebuild/rollback actions live in the project material and knowledge management surface reached from F130's context drawer. Provider/index health, configuration generations, exported traces, and advanced operational controls live under `Settings > Diagnostics`. F128 adds no permanent Partner rail, fourth top-level tab, or center-column health panel.

### Experiment and graph gate

- Compare FTS5, bounded full-context, hybrid, and hybrid-plus-rerank on the same versioned corpus.
- Optional routes begin in shadow mode and become defaults only after improving quality without violating latency, privacy, cost, or access gates.
- Configuration changes are versioned, canaryable, auditable, and rollbackable.
- F075 Knowledge Graph remains shelved unless a repeated user journey still fails after source structure, citations, hybrid retrieval, reranking, and curated knowledge are tuned, and a graph prototype materially improves the same evaluation set with approved cost/access/rollback design.

### Acceptance

- The deterministic indexing/retrieval/citation/integrity suite runs offline and fails on wrong owner/version, wrong locator, missing conflict disclosure, stale answer, or restricted evidence; final-answer evaluation follows the explicitly recorded provider/model policy.
- Results are reproducible from recorded corpus/config/index generations.
- Health and traces explain lexical-only, full-context, hybrid, provider-fallback, stale, restricted, and no-evidence routes while using `scope` for evidence eligibility and `route` for retrieval implementation; neither is presented as a Partner work mode.
- Trace redaction plus opaque non-semantic IDs prevents restricted titles/excerpts, URLs, local paths, account/external-resource identity, credentials, private prompts, and unredacted raw task content from entering exported diagnostics.
- Result and F130 task-receipt-projection trace entry, project-management health, and Settings diagnostics resolve to the same typed trace and health facts without adding a Partner rail tab or exporting unredacted raw task content.
- A selected-but-unused evidence owner never appears in the generic used set, and a selected-but-unused project source never appears in its compatibility used-source projection.
- Result, F130 task-receipt-projection, and current-run Process launchers resolve to the same trace ID and evidence facts.
- Origin-missing with retained permitted/present content, retained-content-missing, revoked-and-restricted, revoked-but-retention-permitted, audit-only, forgotten, corrupt, task-attachment, Result-snapshot, and explicit-reacquisition fixtures produce the declared surface-specific behavior without silently rehydrating an old version.
- Scope fixtures prove that selected-only/general exclude Core Project Context and that retrieval route changes never alter scope.
- Canary, default promotion, configuration rollback, index rebuild, and project-knowledge health/evaluation disablement have rehearsed audit evidence and records.

## 0.1.x exit checklist

- All active 0.1.x features are Completed or explicitly moved with a dated decision.
- `FEATURE_LIST`, capability ledger, PRD, HLD, manual, changelog, and package metadata agree.
- Typecheck, lint, unit tests, E2E, build, platform packaging, release staging, and smoke pass.
- Known limitations are concrete and capability-backed.
- Partner knowledge meets the approved retrieval, citation, freshness, access, latency, diagnostics, migration, and rollback gates, or the failing route remains explicitly disabled/degraded.
- No beta documentation promises cloud sandbox, A2A, MCP Tasks, governed HTTP agents, connector writes, desktop screen automation, or learned capability actions that are not shipped.

## Rollout and rollback

- Locale rollout defaults to the last known valid locale and falls back to `en-US` only when a key/schema failure is diagnosed; it never rewrites user content.
- Channel/updater policy is data-driven and can disable beta promotion without changing installed user data.
- Project-knowledge rollback stops pre-turn injection and new knowledge writes while preserving explicit permitted material/evidence/project-knowledge reads, accepted knowledge export, immutable citations, and fail-closed access handling.
- A rollback preserves settings, diagnostics, and Runtime-owned state; it may hide unsupported controls but must not downgrade schemas destructively.
- F094 may block release promotion or expose a typed degraded/read-only state; it never rolls Partner back to the removed Workbench/Sources projection.
