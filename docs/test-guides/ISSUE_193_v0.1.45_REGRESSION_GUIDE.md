# Issue 193 对话顺序与刷新恢复 - 人工回归测试指导

## 功能概述

**功能名称**: 对话因果顺序及 Sidecar/Interrupt 刷新恢复
**版本**: v0.1.45
**测试日期**: 2026-08-20
**测试人员**: 待填写

本次修复保证 canonical history 与 Runtime live projection 合并后仍保持思考、工具和回答
的原始因果顺序；同时保证 Ctrl+R 后 Sidecar Verifier 通知和等待中的 interrupt query
不会消失或重复。

## 测试环境

### 前置条件

- 使用包含 Issue 193 修复的 Space v0.1.45 开发构建。
- 配置支持 thinking、工具调用、Sidecar Verifier 和 interrupt input 的 Runtime。
- 保留一个长对话 Session，并允许在运行中执行 Ctrl+R。
- 打开 DevTools Console，测试期间记录未捕获错误。

### 环境要求

- 主验证环境：Windows 11、桌面应用、正常网络。
- 兼容性抽查：Windows 10；可用时补测 macOS 或 Linux。

## 测试用例

### TC-001: 长回合终态保持思考、工具与最终回答顺序

**优先级**: 高
**类型**: 正向测试

**前置条件**:

- Session 中开启 thinking，并准备一个会产生多次工具调用的任务。

**测试步骤**:

1. 提交任务，等待其产生至少两段思考、一次工具调用和最终回答。
2. 等待状态变为“运行完成”。
3. 上下滚动对话并展开各思考折叠项。
4. 按 Ctrl+R，再次检查同一回合。

**预期效果**:

- [ ] 刷新前后均按“思考/阶段回答 → 工具 → 后续思考 → 最终回答”显示。
- [ ] 思考折叠项不会集中挂在最终回答之后。
- [ ] 工具卡、思考和最终回答均不重复、不丢失。

**实际结果**: 待填写
**是否通过**: [ ] Pass / [ ] Fail

### TC-002: Provider replace 丢弃旧尝试且不制造尾部思考

**优先级**: 高
**类型**: 负向测试

**前置条件**:

- 使用可通过断网/代理故障触发 provider recovery 的测试 Provider。

**测试步骤**:

1. 启动一个带 thinking 的长回答。
2. 在首段内容出现后短暂中断网络，触发 retry/replace，再恢复网络。
3. 等待新尝试完成并落入 canonical history。
4. 检查完成态并执行 Ctrl+R。

**预期效果**:

- [ ] 被 replace 的旧思考和旧回答不再可见。
- [ ] 新尝试的思考、工具和回答顺序一致。
- [ ] Ctrl+R 不会让旧尝试复现，也不会把思考移动到末尾。

**实际结果**: 待填写
**是否通过**: [ ] Pass / [ ] Fail

### TC-003: 窄历史窗口和大量分段仍稳定合并

**优先级**: 高
**类型**: 边界测试

**前置条件**:

- Session 已有足够长的历史，可触发 bounded newest page。

**测试步骤**:

1. 在长 Session 尾部提交会产生 20 个以上 thinking/text 分段和多个工具卡的任务。
2. 任务仍在流式输出时滚动加载一页旧历史，再返回最新位置，让 canonical page 与 live
   输出在运行中至少合并一次。
3. 等待后续输出和最终 canonical page 到达，再连续执行两次 Ctrl+R。
4. 再次加载旧历史页，对照第一次完成时的顺序和数量。

**预期效果**:

- [ ] 每次重建后的可见顺序相同。
- [ ] 相邻同类分段可以视觉合并，但不能跨工具卡粘连或换位。
- [ ] 没有重复用户气泡、重复回答或不断增长的尾部内容。
- [ ] 运行中先到的 canonical page 不会导致其后的 live 内容在终态重复一次。

**实际结果**: 待填写
**是否通过**: [ ] Pass / [ ] Fail

### TC-004: Sidecar 与排队 query 在刷新期间保持可见

**优先级**: 高
**类型**: UI测试

**前置条件**:

- Sidecar Verifier 能要求主 Agent revise。

**测试步骤**:

1. 运行会被 Sidecar Verifier 打回修改的任务。
2. Sidecar 通知出现后，在当前 Run 仍活动时提交 interrupt query。
3. 确认 query 显示为排队状态，立即按 Ctrl+R。
4. query 被正式交付时再次立即按 Ctrl+R，覆盖 delivery snapshot 已到、event/history 尚未到
   的短窗口。
5. 等待 query 之后的输出和当前 Run 完成。

**预期效果**:

- [ ] 刷新后 Sidecar 通知仍在原回合中可见。
- [ ] 排队 query 在刷新后仍显示为排队气泡。
- [ ] 正式交付时排队气泡原位升级为一个用户气泡，不闪退、不重复。
- [ ] 正式用户气泡位于交付前后两段回答之间，不沉到最终回答之后。
- [ ] Sidecar 前后的回答内容不消失，Console 无 schema 或 revision 错误。

**实际结果**: 待填写
**是否通过**: [ ] Pass / [ ] Fail
