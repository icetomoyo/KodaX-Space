The release includes only:

- `frontend-slides`;
- `huashu-design`, with three ordered Space-maintained patches: no-watermark
  baseline, builtin portability, and removal of remaining promotional
  signatures/instructions.

skills because their current Anthropic terms prohibit retaining, copying,
modifying, or redistributing the material outside the service.

   `resources/builtin-skills.lock.json`.

   missing, or byte-different files must fail the release.

   `created by huashu-design`, `huashu · design`, Huashu HTML wordmarks, nor
   the promotional demo URL; demo finales must use neutral `YOUR BRAND`
   placeholders while the upstream MIT license and authorship remain
   distributed.

## 6. Release sequence

1. Complete the automated and human gates above.
2. Review `git diff`, ensure the release commit contains only intended v0.1.32
   changes, and update `Final release commit`.
3. Commit and push the reviewed candidate to `main`.
4. Run `.github/workflows/release.yml` with `workflow_dispatch` on that commit.
   This builds/uploads workflow artifacts but does not create a GitHub Release.
5. Download and inspect all four platform jobs; run the manual acceptance against
   the candidate artifacts.
6. Confirm `CHANGELOG.md` has the complete `0.1.32` section and an empty
   `Unreleased` section.
7. Create and push the stable `v0.1.32` tag only after an explicit release
   decision. The tag push triggers the production release workflow.
8. Verify the GitHub Release is stable (not prerelease), release notes were
   extracted from the `0.1.32` changelog section, every asset is present, and the
   updater manifests/downloads work.
9. In a post-release documentation commit, change “current stable v0.1.31”
   wording to published `v0.1.32`, link the Release, and open the
   next development section in `CHANGELOG.md`.

## 7. Rollback and stop conditions

Stop before tagging if any required capability is missing, package contents differ
from their integrity locks, a platform artifact cannot boot, a background
interaction can be consumed by the wrong Session, the builtin watermark reappears,
the Windows live window still shows a generic taskbar icon, query-time console
windows still flash, the tray leaves an invisible resident owner or force-stops
shared work, or the release staging script cannot assemble the exact asset matrix.

Because the stable tag automatically creates a public release, the preferred
rollback is to fix the candidate before tagging. If a tag-triggered workflow
fails, do not reuse or silently move the published tag; diagnose the failed job,
prepare a reviewed corrective commit, and follow the project's explicit release
repair policy.
